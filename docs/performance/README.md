# Производительность и потребление ресурсов

**Русский** · [English](README.en.md) · [简体中文](README.zh-CN.md)

Здесь ведутся журналы производительности модулей репозитория: время работы по
фазам, CPU, память, диск и число порождаемых процессов. У каждого модуля —
своя страница с методикой, специфичной для модуля, и журналом записей. Эта
страница задаёт общие правила, по которым такие замеры делаются и
записываются.

Журнал — это свидетельства о фактическом поведении в конкретном окружении, а
не контракт и не порог CI. Числа из него не закрепляются в коде, тестах и
проверках: другое железо, другая ОС или другой Docker дают другие значения.

## Каталог сценариев и контракт результатов

Сценарии, профили условий, граница измеряемой работы и метрики с их охватом
объявляются машинно в каталоге `benchmarks/`, а результаты измерений
записываются в версионируемом JSON. Как зарегистрировать сценарий и читать
результат — [каталог бенчмарков](benchmarks.md). Правила этой страницы
применяются и к измерениям по каталогу: точное состояние кэша каталог требует
объявить для каждого сценария, а журнал остаётся свидетельством окружения.

## Правила замера

1. **Вопрос до замера.** Сначала сформулируй, что нужно узнать (например,
   «сколько стоит повторный прогон» или «укладывается ли контейнер в лимит»), и
   выбери метрики под этот вопрос. Не собирай числа без цели.
2. **Окружение.** Фиксируй модель CPU и число потоков, объём RAM, ОС и ядро
   (включая WSL2), версии Docker, `rustc` и внешних зависимостей модуля,
   действующие лимиты (`--cpus`, `--memory`) и состояние рабочей копии (чистая
   или с изменениями).
3. **Состояние кэшей.** Каждый прогон относится к явно названному состоянию:
   - *холодный* — кэши самого модуля удалены его штатной командой;
   - *тёплый* — повтор без изменений входа;
   - *инкрементальный* — изменён только вход, который должен вызвать частичную
     пересборку.

   Точно записывай, что очищено, а что нет. Общие кэши, которыми модуль не
   владеет (например, слоевой кэш BuildKit демона или базовые образы), ради
   «полностью холодного» замера не удаляются: это затронуло бы другие проекты.
   Такой прогон помечается как холодный для модуля, но не для системы.
4. **Повторы.** Тёплое состояние измеряй минимум дважды и указывай диапазон.
   Одиночное число не сравнивай с одиночным числом другой записи.
5. **Без посторонней нагрузки.** Во время замера не запускай сборки, тесты и
   другие тяжёлые процессы. Сэмплер должен быть дешёвым: чтение `/proc` и
   cgroup раз в секунду практически не нагружает систему.
6. **Настоящая реализация.** Измеряй штатные команды модуля на штатной сборке,
   а не упрощённую копию. Отключать проверки, кэши или уборку ради лучшего
   времени нельзя.
7. **Честность.** Указывай, что не измерено. Оценку не выдавай за измерение, а
   значение окружения — за свойство кода. Оптимизация без замера, который
   показал проблему, в журнал не записывается как улучшение.

## Источники и точность метрик

| Метрика | Источник | Точность |
|---|---|---|
| Время фазы | метки времени UTC в журнале модуля | секунда; `0 с` означает «меньше секунды» |
| Пик памяти процесса | `VmHWM` в `/proc/<pid>/status` | точный пик RSS процесса без потомков |
| CPU процесса | `utime`+`stime` и `cutime`+`cstime` в `/proc/<pid>/stat` | точно; потомки учитываются, только когда процесс их дождался |
| Пик памяти контейнера | `memory.peak` cgroup v2 | точный пик, который ведёт ядро |
| CPU контейнера | `usage_usec` в `cpu.stat` cgroup | точно для суммы; средние и пиковые ядра — по разностям между сэмплами |
| Пик ядер за 1 с | разность `usage_usec` соседних сэмплов | нижняя оценка: всплески короче интервала сглаживаются |
| Загрузка и память хоста | `/proc/stat`, `MemAvailable` в `/proc/meminfo` | вся система: верхняя оценка, если у процесса нет своей cgroup |
| Диск | `du -sb`, `docker image ls`, `docker system df -v` | размеры образов с общими слоями не суммируются |

## Как оформлять запись

Запись идентифицируется датой UTC, версией модуля из `Cargo.toml`, версиями
значимых внешних зависимостей и описанием окружения. SHA коммита, номер PR,
абсолютные локальные пути и имена авторов в постоянную документацию не пишутся
(правило [`AGENTS.md`](../../AGENTS.md)). Точное состояние исходников, на
котором сделан замер, указывается в описании PR, добавляющего запись.

Записи в журнале модуля идут от новой к старой и не переписываются. Если
запись оказалась ошибочной, она помечается, а исправленная добавляется рядом.

Шаблон записи:

```markdown
### <дата UTC> · <модуль> <версия> · <ключевая зависимость и версия> · <команда>

- Окружение: …
- Состояния кэша: …
- Время по фазам: таблица по прогонам
- Ресурсы: таблица «метрика — значение — источник»
- Диск: …
- Выводы: что подтвердилось, что требует внимания
- Не измерено: …
```
