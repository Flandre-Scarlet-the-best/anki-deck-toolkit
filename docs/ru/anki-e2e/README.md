# E2E-стенд Anki Desktop

**Русский** · [English](../../en/anki-e2e/README.md) · [简体中文](../../zh-CN/anki-e2e/README.md)

`anki-e2e` — постоянный локальный E2E-стенд для группы `anki-repo anki`
([контракт](../anki-repo/desktop.md)). Rust runner на хосте собирает
воспроизводимый Docker-образ с **официальной Linux Anki Desktop**, запускает
**один изолированный контейнер** с виртуальным дисплеем Xvfb и выполняет в нём
сценарии через **настоящий** `anki-repo`, штатный установщик Anki, AnkiConnect
и CrowdAnki. Отдельно и наравне с функциональностью проверяются окна,
подтверждения и всплывающие уведомления Anki.

Стенд запускается **только явной командой**. Он не входит в `cargo test`, CI,
build scripts и hooks; модульные тесты самого runner Docker не запускают.
Проектных shell-скриптов нет: оркестрация, ожидания, клики, скриншоты, отчёт
и уборка написаны на Rust.

## Запуск

```bash
cargo run -p anki-e2e -- full
```

Выборки сценариев:

| Команда | Сценарии | Что доказывает |
|---|---|---|
| `full` | все ниже | полный прогон на чистом стенде |
| `smoke` | `smoke` | обнаружение Anki, первый запуск, `doctor` stopped/running, `launch`, отказ `stop` без владения, отказ небезопасного endpoint |
| `addons` | `addons` | чистая Anki без аддонов → `setup --apply` → штатный установщик → второй пакет через работающую Anki → no-op повторный setup |
| `patch` | `patch` | `patch install/status/repair/remove`, стёртый bootstrap, повреждённый payload, изменённый upstream, `restore`, загрузка после перезапуска |
| `crowdanki` | `crowdanki` | настоящие export/import с PNG, диалог CrowdAnki (OK и Cancel), отказы предвалидации, перенос в чистую базу с сохранением GUID, `ready` |
| `process` | `process` | `launch/restart/stop`, отказ при модальном окне и busy, смерть процесса, чужой процесс |
| `errors` | `errors` | отказ в установщике, отключённый аддон, чужой слушатель порта, чужой профиль, сломанный аддон |
| `gui` | `addons`, `crowdanki` | основные штатные диалоги и уведомления |
| `run --scenarios a,b` | список | произвольная выборка |

Полезные параметры (по порядку): воспроизвести конкретный релиз; сохранить
контейнер после неудачи; смотреть экран через `vnc://127.0.0.1:5900`; задать
ресурсы и общий таймаут; только выбрать релиз и проверить архив; удалить
ресурсы стенда.

```bash
cargo run -p anki-e2e -- full --anki-version 26.09.3
cargo run -p anki-e2e -- addons --keep-container on-failure
cargo run -p anki-e2e -- gui --vnc --keep-container always
cargo run -p anki-e2e -- full --cpus 4 --memory 6g --timeout-minutes 120
cargo run -p anki-e2e -- resolve
cargo run -p anki-e2e -- clean --images --cache
```

`--require-clean` отказывает в прогоне при незакоммиченных изменениях;
без него снимок рабочей копии всё равно фиксируется в отчёте (`dirty`,
список путей и SHA-256 дерева).

`--timeout-minutes` ограничивает только исполнение сценариев в контейнере.
Загрузку архива и сборку образов он не охватывает: загрузка без единого байта
дольше 60 с завершается ошибкой, а Ctrl+C своевременно прерывает и зависшее
чтение сети, и `docker build` (сначала SIGINT, затем SIGKILL). Частичный архив
при этом удаляется и в кэш не попадает. `--cpus`, `--memory` и `--pids-limit`
ограничивают контейнер сценариев, а не сборку образов BuildKit.
Общего срока передачи архива нет, пока поступают данные; ожидание HTTP-заголовков
также охвачено контролем отсутствия прогресса и прерывания.

## Версия Anki

- **По умолчанию — последняя стабильная версия.** При каждом запуске runner
  читает GitHub Releases API `ankitects/anki` **целиком** (до неполной
  страницы), исключает draft, prerelease и beta, сравнивает версии численно и
  выбирает максимальную стабильную с официальным артефактом
  `anki-<версия>-linux-<arch>.tar.zst`. GitHub упорядочивает релизы по дате
  публикации, поэтому поздно опубликованный бэкпорт меньшего номера не мешает
  выбору. Если индекс длиннее сетевого бюджета (5 страниц по 100), максимум не
  считается подтверждённым: `ERROR` без выбора из прочитанной части. Номер
  версии не закреплён ни в Dockerfile, ни в коде, ни в конфигурации.
- Если у максимальной стабильной нет Linux-артефакта, сеть или индекс недоступны —
  `BLOCKED`/`ERROR` без отката на прежнюю версию.
- `--anki-version X` — явный регрессионный прогон; выбор по умолчанию не меняется.
  Prerelease требует `--allow-prerelease`.
- Целостность: URL обязан совпадать с официальным
  `https://github.com/ankitects/anki/releases/download/<tag>/<asset>`; SHA-256
  загрузки сверяется с `digest`, который GitHub публикует для ассета релиза.
  Это контрольная сумма площадки релизов, а не подпись мейнтейнеров. Если
  для релиза сумма не опубликована, прогон блокируется; `--allow-unverified-archive`
  разрешает его, но отчёт помечает сумму как самостоятельно вычисленную.
- Кэш `target/anki-e2e/cache/anki/<версия>/linux-<arch>/<sha256>/` используется
  только после выбора релиза и повторной сверки SHA-256; повреждённая копия
  переносится в `*.corrupt-*` и скачивается заново.
- Офлайн-режим — только явно и только с заранее проверенным артефактом:
  `--offline --anki-version X --sha256 <hex> [--anki-archive путь]`. Свежесть
  стабильной версии в нём не проверяется, и отчёт это показывает.

Совместимость — **предмет** E2E, а не критерий выбора старой Anki. Если
свежая стабильная версия не входит в allowlist `tools/anki-repo/src/desktop/compatibility.json`,
сценарии с аддонами завершаются `BLOCKED` с причиной
`anki_version_unsupported_by_desktop_adapter`, фактической версией и стадией.

Расширять allowlist ради зелёного прогона нельзя: новая версия добавляется
только после сверки изменений upstream (код Anki, затрагивающий установщик
аддонов, загрузку и перезапуск; байты пакетов AnkiWeb для этой версии) и
полного `full` на ней. Пока версия не добавлена, отчёт честно показывает
`BLOCKED` для сценариев, которым нужны установленные аддоны.

## Образ и контейнер

Два образа с метками `io.github.anki-deck-toolkit.e2e=1`:

- `anki-e2e/anki:<версия>-<arch>-<sha12>-<ключ>` из
  [`docker/anki.Dockerfile`](../../../tools/anki-e2e/docker/anki.Dockerfile): Ubuntu 24.04,
  закреплённая по digest, зависимости официальной сборки, Xvfb, D-Bus и
  at-spi2-core, распакованный официальный архив (SHA-256 сверяется ещё раз).
  **Аддонов в образе нет**: первоначальную установку проверяет сценарий.
- `anki-e2e/run:<дерево12>-<ключ>` из [`docker/run.Dockerfile`](../../../tools/anki-e2e/docker/run.Dockerfile):
  `anki-repo` и `anki-e2e` собираются внутри Docker (`rust:<MSRV>-bookworm`,
  MSRV из корневого `Cargo.toml`) из снимка файлов рабочей копии, которые
  отслеживает или не игнорирует Git. Рабочий каталог стенда (`--work-dir`:
  кэши, снимки, отчёты) в снимок не входит при любом расположении, даже внутри
  репозитория без записи в `.gitignore`; каталог с отслеживаемыми файлами или
  содержащий сам репозиторий отвергается. Хэш дерева передаётся в образ, и
  агент сообщает его в результате, в том числе при раннем отказе: `PASS` требует
  положительного совпадения (`provenance`), достоверное несовпадение —
  самостоятельная ошибка `provenance_mismatch`, а отсутствие свидетельства при
  уже известном отказе не подменяет его первичную причину.
  Общий BuildKit target-кэш стабилен и защищён блокировкой. Перед сборкой удаляются
  оставшиеся от прежней схемы каталоги снимков с SHA-256, затем `cargo clean -p`
  очищает артефакты только `anki-repo` и `anki-e2e`. Cargo пересобирает эти пакеты
  из текущего снимка, сохраняя кэш их неизменившихся зависимостей.

Контейнер: `--init`, пользователь `10001`, `--cap-drop ALL`,
`no-new-privileges`, лимиты CPU/памяти/PID, сеть bridge без опубликованных
портов (кроме явного `--vnc` на `127.0.0.1`), **без монтирований** — ни home,
ни Docker socket, ни рабочей копии, ни `decks/**`, ни `.asset-store/`.
Свидетельства забираются `docker cp`. Отчёт фиксирует фактический
`docker inspect` и отдельные проверки этих границ. Docker-клиент по умолчанию
получает собственный пустой `DOCKER_CONFIG` (`--docker-config inherit` — для
нестандартного контекста). Каждый сценарий работает с собственной пустой
базой `anki -b`; AnkiConnect слушает loopback **внутри** контейнера.

После штатного завершения контейнер удаляется, и это проверяется. `--keep-container
on-failure|always` сохраняет его для диагностики; завершённые контейнеры удаляет
`clean`, а контейнер активного прогона пропускает. Владелец контейнера
определяется меткой `…e2e.host-runner` (machine-id, boot_id и время старта
процесса runner), а не одним PID: повторно выданный PID не считается живым
runner, контейнеры прошлой загрузки ядра — устаревшими, а контейнеры runner
другого хоста не трогаются. Контейнер прежней схемы без этой метки считается
активным, только пока по его PID работает `anki-e2e`. Оставшиеся от прерванных
прогонов контейнеры без пометки keep удаляются при следующем запуске. Ctrl+C
даёт `INTERRUPTED` и уборку.

`clean` удаляет контейнеры стенда; `--images` — также образы с меткой стенда;
`--cache` — каталоги `cache/` (архивы Anki) и `build/` (снимки исходников)
рабочего каталога и BuildKit cache mounts Cargo `anki-e2e-cargo-registry` и
`anki-e2e-cargo-target`. Cache mounts удаляются прицельно (`docker builder
prune` с фильтром по типу `exec.cachemount` и точному идентификатору) и затем
проверяются по `docker system df -v`; общий слоевой кэш BuildKit демона меток
стенда не несёт и не удаляется (его очистка — осознанный `docker builder prune`
вне стенда). При `--docker-config inherit` с нестандартным buildx builder
проверка видит только кэш сборки самого демона. Любой требуемый, но неудалённый
ресурс даёт код `3`.
После сборки нового образа запуска runner удаляет образы запуска и снимки
исходников прежних ревизий; образы Anki и кэш архивов остаются до `clean`.
Параллельные команды по очереди используют общие кэши и Docker-образы до старта
контейнера; после старта сами сценарии могут выполняться одновременно.
При нестандартном Docker context укажите `clean --docker-config inherit`, как и
для запуска; изолированный режим откажется работать с активным пользовательским context.

Снимок сохраняет Unix-права файлов и символические ссылки как ссылки, не читая
их цели. Хэш дерева учитывает байты файлов, их права и цели ссылок.

## Наблюдение за окнами и уведомлениями

Qt публикует виджеты на шине доступности AT-SPI
(`QT_LINUX_ACCESSIBILITY_ALWAYS_ON=1`). Агент **пассивно** читает роль, заголовок,
видимый текст, кнопки, выделение и координаты каждого окна верхнего уровня, а
модальность и `WM_TRANSIENT_FOR` — из свойств X11. Кода внутри Anki нет,
поэтому видны и окна, которые Anki показывает до загрузки аддонов (выбор языка,
подтверждение установки `.ankiaddon`). Каждое новое или изменившееся окно
сразу снимается скриншотом реального дисплея Xvfb и записывается в
`events.jsonl`: шаг, время, роль, заголовок, текст, кнопки, модальность,
классификация, действие теста и длительность показа.

Окно сопоставляется с каталогом `src/agent/catalog.rs` по роли, заголовку,
обязательным фрагментам текста и **точному набору кнопок**. Клик (XTEST,
как действие пользователя) выполняется только если окно совпало с правилом и
это правило ожидается текущим шагом. Неизвестное окно, известное окно в чужом
шаге (например «Installed» при no-op setup) или повтор сверх ожидаемого
останавливают сценарий с `FAIL`, свидетельствами и причиной; такие окна не
закрываются. Классы: `expected_informational`, `required_confirmation`,
`warning_or_error`, `duplicate_or_misleading`, `unknown_blocking`,
`unexpected_notice`. Скриншот сам по себе не считается доказательством текста:
текст и модальность берутся из AT-SPI и X11.

Отказ опроса AT-SPI или X11 не обновляет снимок окон: неполный опрос не
доказывает закрытия окна, но и прежний снимок не выдаётся за свежий. Условия
ожиданий проверяются только на свежем снимке, а конец наблюдения, команды и
сценария требует успешного опроса. Непрерывный отказ дольше 10 с —
`ERROR` `ui_observation_lost`; в `events.jsonl` пишутся `observation_degraded` и
`observation_restored`. Опрос окон идёт каждые 150 мс, а ожидания по
`anki-repo doctor` и `anki-repo job` запускают новый CLI не чаще раза в секунду;
число запусков — `commands_started` в результате сценария.

## Результаты

`target/anki-e2e/runs/<id>/` (игнорируется Git):

- `report.json` и `report.md` — статус `PASS`/`FAIL`/`BLOCKED`/`SKIPPED`/
  `ERROR`/`INTERRUPTED`, режим выбора версии, найденная стабильная версия, фактически
  установленная версия, URL и SHA-256 архива, ID образов, commit и хэш дерева
  toolkit, SHA-256 `anki-repo` в контейнере, сценарии с проверками и UI-событиями,
  матрица уведомлений («нормально ли», «нужно ли нажимать», «что будет без
  действия»), изоляция и уборка;
- `runner.log`, `build-*.log`;
- `agent/scenarios/<сценарий>/` — `result.json`, `events.jsonl`,
  `screenshots/`, `commands/` (argv, код, JSON вывода `anki-repo`), журналы Anki,
  копии экспортов тестовой колоды.

Обязательные свидетельства — оба отчёта, `agent-result.json`, `result.json` и
`events.jsonl` сценария, записи команд и скриншоты окон и действий. Потеря
любого из них не даёт `PASS` (`evidence_missing`, `evidence_copy_failed`, при
незаписанном отчёте — `ERROR`), а уже известная причина неуспеха остаётся
первичной `stop`; поздние остановки собираются в `secondary_stops`.

Коды завершения runner: `0` PASS, `1` FAIL, `2` BLOCKED/SKIPPED, `3` ERROR,
`130` INTERRUPTED.

## Требования

Linux или WSL2 с Docker Engine (rootful или rootless) и BuildKit, архитектура
x86_64 или aarch64, сеть до GitHub, AnkiWeb, Docker Hub и зеркал Ubuntu,
4 CPU и 6 ГБ памяти на контейнер по умолчанию. В измеренном окружении образы
стенда, Cargo-кэши и архив заняли около 6,6 ГБ диска; дополнительно нужны
базовые образы Docker, временные данные сборки и запас на рост кэшей
([подробности замера](performance.md)). Первый прогон
собирает образы; повторные используют кэш.

## Браузерный набор Forvo-Brave

`cargo run -p anki-e2e -- browser [--scenarios a,b] [--chrome <путь>] [--extension-loader flag|cdp-pipe] [--keep-profiles]` —
отдельный явный набор для адаптера [Forvo через обычный браузер](../asset-store/forvo-brave.md).
Он не требует Docker, Anki Desktop, персонального Brave, профиля и аккаунта Forvo и не
выходит во внешнюю сеть. Это минимальная изолированная граница внутри того же runner.
Docker-жизненный цикл стенда привязан к образу Anki, и встраивание браузера в контейнер
агента потребовало бы ломки его архитектуры. Поэтому набор переиспользует статусы и коды
завершения (`report::Status`), прерывание через Ctrl+C, рабочий каталог
`target/anki-e2e` и отчёты JSON/Markdown, а Docker-сценарии Anki не меняются.
Образ Anki собирается с `--no-default-features` без этой feature.

Каждый сценарий запускает собственный тестовый Chromium:
- headless, временный профиль в каталоге прогона;
- `--no-proxy-server`;
- `--host-resolver-rules` направляет `forvo.com` на локальный HTTPS fixture, а остальные имена — в `NOTFOUND`;
- самоподписанный сертификат допускается только в этом профиле.

В браузер устанавливается то же production-расширение, что ставит `pronunciation-assets
forvo browser setup`: manifest и ограничение `https://forvo.com` не расширяются. Bridge
настоящий, проверки — Rust-контракты `asset-store`. CDP управляет только тестовым
браузером: действиями «пользователя» в других вкладках и остановкой service worker.

Браузер задаётся `--chrome` (или `CHROME_BIN`, `CHROMIUM_BIN`, `PATH`). Его разновидность
определяется по `--version` так же, как у `forvo browser discover`. Подходят Chromium,
Chrome for Testing, Google Chrome, Microsoft Edge, Vivaldi и Brave для Linux. Цель
адаптера — `brave` для Chromium и Brave (сценарии `cli_*` вызывают прежний
`forvo brave`), иначе имя браузера (`forvo browser --target <имя>`). Способ
установки расширения во **временный** профиль:
- `flag` — `--load-extension`: Chromium, Chrome for Testing, Edge, Vivaldi, Brave;
- `cdp-pipe` — CDP `Extensions.loadUnpacked` через `--remote-debugging-pipe` и
  `--enable-unsafe-extension-debugging`, как «Загрузить распакованное». Это значение по
  умолчанию для Google Chrome, который с версии 137 игнорирует `--load-extension`.

Это способ только для тестового профиля стенда. Пользовательским способом установки он не
является. Профиль создаётся с включённым режимом разработчика. У каждого сценария свой
профиль, а значит, свой экземпляр расширения, поэтому перед сценарием выполняется
`setup --repin` цели. Нужны `ffmpeg`/`ffprobe` и `openssl`; без них итог — `BLOCKED`
с причиной.

Временный профиль получает `vivaldi.downloads.start_automatically` в паре с
`prompt_for_download` (другие браузеры этот ключ не читают): Vivaldi по умолчанию
подтверждает каждую загрузку в своём интерфейсе. Под Vivaldi вкладка, к которой
подключился CDP-клиент стенда, не завершает навигацию. Поэтому сценарии, открывающие
«вкладку пользователя» через CDP (`extension_bridge_tab`, `concurrent_downloads`,
`browser_restart`, `cli_fetch`, `cli_batch_recovery`, `cli_foreign_downloads`), для
Vivaldi получают `BLOCKED` с этой причиной. Вкладка пользователя открывается не дольше 30 с.

| Сценарий | Что доказывает |
|---|---|
| `extension_bridge_tab` | HMAC-сопряжение настоящего расширения, контракт команд, неактивная вкладка в свёрнутой группе, вкладки пользователя не изменены |
| `auth_and_candidates` | японские записи и кнопки, неверный `record_id`, вход, изменённый DOM, другой язык, phrases, чужая кнопка |
| `full_download` | `smoke` целиком: клик → загрузка → владение → `complete` → байты → SHA/`probe_mp3` → очистка; `--keep-download` |
| `concurrent_downloads` | параллельные загрузки пользователя (другая запись Forvo, другой сайт) неизменны; та же запись из другой вкладки → `download_conflict`, ничего не удалено |
| `download_failures` | `.crdownload` не принимается, таймаут, обрыв, не-MP3, неверный адрес, чужой download ID |
| `service_worker_restart` | рестарт до связывания → `ownership_unproven`; после связывания операция доводится до конца |
| `bridge_reconnect` | разрыв bridge не теряет связанную операцию |
| `own_tab_closed` | закрытие собственной вкладки до начала загрузки |
| `interrupt` | прерывание как Ctrl+C: `INTERRUPTED`, собственная загрузка отменена |
| `save_as_prompt` | профиль с «Спрашивать, куда сохранять» → `BLOCKED save_as_required` (Edge: `save_as_suspected`; Vivaldi без автоматического начала загрузок: `download_not_started` с действием) |
| `browser_restart` | перезапуск браузера с восстановлением сессии: восстановленная группа адаптера закрыта перед первой командой, вкладка пользователя на `forvo.com` осталась, новая вкладка — в единственной группе |
| `cli_fetch` | настоящий `pronunciation-assets forvo brave fetch`: импорт оригинального MP3 в отдельное тестовое хранилище (SHA, не `Verified`), одна сетевая загрузка, файл удалён, копий в `evidence/` нет; повтор тех же байтов; без `ffprobe` — `technical_validation_failed` без импорта |
| `cli_batch` | пакет из трёх разных слов: не-MP3 лучшей записи → следующий кандидат с попытками в `ForvoEvidence`, ровно одна загрузка на попытку, resume без загрузок, `--max-items`, CDP-resume пакета Brave и Brave-resume состояния v1 → `transport_mismatch` без браузера |
| `cli_batch_recovery` | Ctrl+C во время загрузки (отмена собственной загрузки, `paused interrupted`, resume), `batch-status` и `batch-cancel` во время работы при параллельной загрузке пользователя, второй исполнитель того же пакета, SIGKILL во время загрузки и освобождение операции следующим запуском, resume после checkpoint и после импорта без загрузок |
| `cli_foreign_downloads` | загрузка той же записи из чужой вкладки во время пакета → `paused download_conflict`, файлы пользователя целы; повторный запуск завершает пакет |
| `adapter_doctor` | `doctor --forvo --reconnect --reload` цели: ID из каталога цели, закреплённый экземпляр, версия как у CLI, установка по исполняемому файлу, бренды браузера (`PASS`; у Vivaldi — `NOT_TESTED`), все нужные API от самого браузера, `download_settings` — `NOT_TESTED` |
| `extension_update` | установлена старая версия → следующая команда обновляет файлы и штатно перезагружает расширение с тем же ID, экземпляром и секретом; при незавершённой связанной загрузке перезагрузка откладывается, операция освобождается восстановлением, обновление выполняет следующая команда |
| `target_isolation` | вторая цель в том же `state.json`: свои каталог, порт, секрет и ID; оба расширения в одном профиле подключаются каждое к своей цели; тот же каталог в другом профиле → `instance_mismatch`; `setup --repin` закрепляет новый экземпляр с прежним секретом |

Сценарии `cli_*` запускают собранный `pronunciation-assets` (`--cli`,
`PRONUNCIATION_ASSETS_BIN` или файл рядом с `anki-e2e`; без него — `BLOCKED`):
`cargo build -p asset-store --bin pronunciation-assets`. Fixture содержит минимально
необходимые независимые слова `水` и `山` с собственными записями и байтами. Каждое
тестовое хранилище создаётся в каталоге сценария.

Отчёт `target/anki-e2e/browser-runs/<run_id>/report.{json,md}` содержит:
- ревизию, версию браузера и флаги;
- SHA-256 синтетических MP3 fixture;
- проверки каждого сценария с доказательствами и итоговое содержимое каталога загрузок.

`PASS` получает только завершённый сценарий, в котором все проверки истинны. Итог — худший
статус, код завершения — как у стенда. Профили и каталог сопряжения с тестовым секретом
удаляются после прогона, если не задан `--keep-profiles`. Живой Forvo в основном браузере
пользователя этим набором не заменяется.

## Real-Site стенд Forvo-Brave

`cargo run -p anki-e2e -- real-site <up|run|status|down|purge>` — ручной стенд для
адаптера [Forvo через обычный Brave](../asset-store/forvo-brave.md) на **настоящем**
`forvo.com`: без fixture, моков и подмены ответов. Он дополняет изолированный браузерный
набор и не заменяет его. Вход в аккаунт и проверки сайта (Cloudflare) пользователь
проходит вручную, поэтому стенд не запускается в CI и `cargo test`.

```bash
cargo run -p anki-e2e -- real-site up        # образ, контейнер, Brave; печатает адрес noVNC
cargo run -p anki-e2e -- real-site run       # doctor --forvo, smoke 元気/げんき, fetch и пакет 元気+猫
cargo run -p anki-e2e -- real-site down      # штатно закрыть Brave, удалить контейнер
cargo run -p anki-e2e -- real-site purge --yes   # удалить также volumes с авторизацией и образы
```

Устройство:
- образ `anki-e2e/real-site`: закреплённый Ubuntu 24.04, Brave Stable для Linux из
  [официального репозитория](https://brave.com/linux/), Xvfb, x11vnc и noVNC,
  `pronunciation-assets`, собранный внутри Docker из снимка исходников (как образ запуска Anki);
- Brave запускается без CDP и `--remote-debugging-port`. `up` сначала выполняет
  `pronunciation-assets forvo brave setup`, затем запускает Brave с `--load-extension`
  каталога адаптера (Brave для Linux этот флаг принимает, режим разработчика не нужен).
  ID расширения тот же, что при ручной загрузке. bridge работает на `127.0.0.1`
  в собственном network namespace контейнера;
- управляемая политика **только этого образа** выключает менеджер паролей (в контейнере
  нет связки ключей, Brave работает с `--password-store=basic`) и запрос места сохранения
  (`PromptForDownloadLocation`). Пользовательский Brave не меняется;
- noVNC (`--vnc-port`, по умолчанию 6080) и VNC для нативного клиента (`--rfb-port`,
  по умолчанию 5900) публикуются только на `127.0.0.1` хоста. Пароль VNC случайный,
  хранится в volume состояния (0600): `docker exec anki-e2e-real-site cat /home/tester/state/vnc.txt`.
  Нативный клиент (например, TigerVNC Viewer) надёжнее браузерного noVNC передаёт буфер
  обмена и раскладку. x11vnc запущен с `-skip_lockkeys`: регистр берётся из символа клиента,
  и Caps Lock не применяется повторно;
- прокси для Brave берётся из `docker info` (Docker Desktop), явно — `--proxy`,
  отключается `--no-proxy`.

Изоляция контейнера: `--cap-drop ALL --cap-add SYS_CHROOT`, `no-new-privileges`, без
`privileged` и без `seccomp=unconfined`. Процесс Brave работает от uid 1000 без действующих
capabilities. `SYS_CHROOT` в bounding set нужен песочнице только внутри её user namespace:
без него zygote падает на `chroot`. Стандартный профиль seccomp не даёт песочнице Chromium создать
namespaces, а отключать песочницу (`--no-sandbox`) стенд не стал. Поэтому runner берёт профиль Docker
по умолчанию ([moby/profiles](https://github.com/moby/profiles), закреплён коммитом и
SHA-256) и добавляет одно правило: `clone` и `unshare` разрешены только без флагов
mount-, cgroup-, UTS- и IPC-namespaces. Brave получает user-, PID- и network-namespaces,
`setns` не разрешается. Профиль лежит в `target/anki-e2e/real-site/`.

**Volumes — чувствительные локальные данные.** `anki-e2e-real-site-profile` хранит профиль
Brave с авторизацией Forvo, `anki-e2e-real-site-state` — сопряжение адаптера, журналы,
evidence и пароль VNC, `anki-e2e-real-site-downloads` — загрузки. Ресурсы помечены
собственной меткой `io.github.anki-deck-toolkit.e2e.real-site`. `clean` их не трогает,
`down` сохраняет volumes, удаляет их только `purge --yes`. В образ, отчёты и Git они не попадают.

Отчёт `target/anki-e2e/real-site-runs/<run_id>/report.{json,md}` содержит:
- версию Brave, образ и коммит исходников;
- шаги `doctor`/`smoke` по их машинному контракту и подсказку для `BLOCKED`;
- production-шаги после зелёного `smoke` (`--acceptance-only` их отключает):
  - `fetch` в отдельное тестовое хранилище: SHA ресурса равен `downloaded_sha256`,
    ресурс не `Verified`, вкладки пользователя не изменены, `verify` проходит;
  - пакет из `--surface` и `--batch-surface` (по умолчанию `猫`/`ねこ`): `batch-start
    --max-items 1` обрабатывает одно слово, `batch-resume` завершает второе. Число
    начатых загрузок в журнале запуска равно числу попыток второго слова;
  - повторный `batch-resume` не меняет ревизию и не начинает загрузок.

Тестовые хранилища лежат в volume состояния
(`/home/tester/state/real-site-stores/<run_id>`). Они не попадают в Git и
пользовательский `AssetStore`.

`up` и `run` проверяют песочницу: каждый renderer должен жить в собственном user namespace.
Иначе `up` завершается ошибкой, а `run` получает `FAIL`. `smoke` запускается только после
зелёного `doctor`. Перед записью отчёт сверяется с секретом
сопряжения: при совпадении отчёт не пишется (`ERROR`). Коды завершения — как у стенда.
Внешние ограничения (`login_required`, `challenge_required`, 429) дают `BLOCKED` и не
считаются дефектом адаптера.

## Границы

Стенд проверяет **Linux** Anki и не доказывает Windows/WSL-интеграцию из
`desktop.md`. Он не читает и не пишет пользовательские `Anki2`, `decks/**` и
`.asset-store/`. Набор расширяется новым сценарием в
`src/agent/scenarios.rs` без изменения Docker-архитектуры — например, для
будущего обмена `Anki → input → output → Anki`.
