# Speech Enhancement для японских MP3 (DeepFilterNet3, опционально Resemble Enhance)

Подкоманды `pronunciation-assets enhancer` решают для каждого входа
[Balanced Normalizer](normalizer.md), нужно ли нейросетевое улучшение речи, и,
если нужно, получают улучшенный вариант локальной моделью DeepFilterNet3 на CPU,
проверяют его и автоматически выбирают байты. Иначе остаются **точные байты**,
ранее выбранные Balanced. Каждое решение машинно объяснено и содержит следующее
автоматическое действие. Человек не требуется ни на одном шаге: прослушивание и
оценки — добровольная диагностика, а не условие обработки.

## Границы

- **Без сети при обработке.** Анализ, пакет, повтор и отчёт не обращаются к
  сети, Forvo и API. Веса ставит отдельная явная команда `model-install` из
  локального файла или каталога; при обработке они не скачиваются.
- **Основной путь без Python и GPU.** Backend по умолчанию — Rust: воркер
  `speech-enhance-dfn` (`tools/speech-enhance`, crate `deep-filter-rt` на
  `tract`). Нативных библиотек инференса, CUDA и PyTorch в нём нет.
  Экспериментальный [Resemble Enhance](#дополнительный-backend-resemble-enhance)
  (Python, PyTorch, CUDA при наличии) включается только явным профилем.
- **Вход только читается.** Корпус открывается тем же обходом без перехода по
  ссылкам, что у Balanced. Каталог весов, рабочий каталог и отчёт проверяются
  на пересечение со входом, `decks/**` и друг с другом до первой записи
  (`boundary_violation`).
- **Ничего не публикуется.** Улучшенные варианты живут в кэше рабочего
  каталога. В основное хранилище, `Verified` и `HumanAttestation` этап не пишет;
  отдельной команды публикации нет.
- **Не доказывает фонетику.** QC — сигнальные эвристики: сохранность слабых
  звуков, оглушённых гласных, фрикативов, `っ` и тонального рисунка оценена по
  уровням окон и полосам, без ASR и без эталона. Сомнение всегда оставляет вход.

## Почему воркер, а не встроенная библиотека

| Решение | Причина |
|---|---|
| Отдельный процесс | `prlimit` (адресное пространство 4 GiB, CPU, дескрипторы) и предел времени отделяют аварию, нехватку памяти и зависание модели от пакета; `asset-store` не связывается с `tract` |
| `deep-filter-rt` 0.1.1 | инференсная часть upstream `libDF` с веса́ми DeepFilterNet3; версия на crates.io `deep_filter` 0.2.5 (2022) инференса не содержит, а upstream CLI по умолчанию берёт DeepFilterNet2 |
| CPU, один поток | инференс клипа 1–3 с занимает десятки миллисекунд, а время процесса — запуск, загрузка модели и FFmpeg; детерминированный CPU-путь стабилизирует ключ кэша. Пакет параллелится по входам (`--jobs`) |

## Модель и её идентичность

Закреплённый манифест — четыре файла архива `models/DeepFilterNet3_onnx.tar.gz`
репозитория [Rikorose/DeepFilterNet](https://github.com/Rikorose/DeepFilterNet)
на коммите `d375b2d8309e0935d165700c91da9de862a99c31` (SHA-256 архива
`c94d91f7…3616`). Те же байты лежат в каталоге `models/DeepFilterNet3` crate
`deep-filter-rt` 0.1.1. Отпечаток манифеста —
`8b378da4a759b6a244bb6bc9786e7ffd74c67f3f878dbd40e53c2f6565d05e5d`.

| Файл | Байт | SHA-256 |
|---|---|---|
| `config.ini` | 2067 | `415eb925…4290` |
| `enc.onnx` | 1954042 | `7c5399d3…1916` |
| `erb_dec.onnx` | 3292397 | `ab669a1d…d895` |
| `df_dec.onnx` | 3340803 | `23114ce3…f278a` |

Воркер при каждом запуске читает файлы без перехода по ссылкам, сначала
сверяет вариант модели (`[train] model = deepfilternet3`) и частоту
(`[df] sr = 48000`), затем длины и SHA-256. Отказы различаются: `model_missing`,
`model_not_regular_file`, `model_wrong_version` (например, DeepFilterNet2),
`model_corrupt`. `asset-store` дополнительно сверяет отчёт `identify` с
закреплёнными ожиданиями (backend, имя, вариант, манифест, частота, протокол).
Расхождение — `enhancer_identity_mismatch`, а не незаметная подмена.

Идентичность backend в отпечатке конфигурации: SHA-256 исполняемого файла
воркера, его отчёт `identify` (версии воркера и `deep-filter-rt`, устройство,
задержка 1440 отсчётов), манифест весов и параметры инференса.

### Лицензии и распространение

Код и веса DeepFilterNet распространяются upstream под MIT OR Apache-2.0, так
же лицензированы `deep-filter-rt` и `tract`. Решение репозитория: веса **не
коммитятся и не распространяются** вместе с кодом. Воркер их не встраивает
(неиспользуемая встроенная копия crate не попадает в сборку), а читает из
каталога, который пользователь установил сам. Сторонние уведомления —
[THIRD-PARTY-NOTICES.md](../../../tools/speech-enhance/THIRD-PARTY-NOTICES.md).

## Команды

```bash
cargo build --release -p asset-store --bin pronunciation-assets -p speech-enhance
B=target/release/pronunciation-assets
# Явная установка весов без сети (одно из трёх):
$B enhancer model-install --source /path/DeepFilterNet3_onnx.tar.gz
$B enhancer model-install --source /path/dir-with-four-files
$B enhancer model-install            # копия crate из локального реестра Cargo
$B enhancer model-identify
$B enhancer profile > .codex/local/enhancer/profile.json
$B enhancer analyze --file word.mp3 [--out /private/out/word.mp3]
$B enhancer batch-start --batch-id enh-1 --base-batch-id corpus-1 \
  --workspace .codex/local/normalizer/work [--jobs 8] [--max-items N] [--profile FILE]
$B enhancer batch-status|batch-cancel|batch-verify-sources --batch-id enh-1 --workspace …
$B enhancer batch-resume --batch-id enh-1 --workspace … [--jobs N]
$B enhancer batch-report --batch-id enh-1 --workspace … --out .codex/local/enhancer/report-1
```

Корень моделей по умолчанию — `$XDG_DATA_HOME/anki-deck-toolkit/speech-models`
(иначе `~/.local/share/…`), вне рабочей копии. Веса ставятся в
`deepfilternet3/<отпечаток манифеста>/` атомарно и идемпотентно; повреждённая
установка не «чинится» молча, а даёт отказ с путём. `--model-dir` и
`--backend-bin` задают каталог весов и воркер явно. По умолчанию воркер ищется
рядом с `pronunciation-assets`, затем в `PATH`. Коды выхода и формат JSON — как у
[нормализатора](normalizer.md#команды).

## Конвейер одного входа

```text
исходный MP3 + результат Balanced (schema 2, normalize)
  → REJECT у Balanced → INPUT_REJECTED
  → probe_mp3 и декодирование ИСХОДНИКА (не Balanced MP3)
  → триаж по измерениям: шум не мешает → NOT_NEEDED (точные байты Balanced)
  → модель неприменима (короче 250 мс, больше двух каналов) → DEFERRED
  → явный ресэмплинг libswresample в 48 kHz → DeepFilterNet3 по каналам → обратно
  → Enhancement QC улучшенного PCM против исходного PCM
  → Balanced над улучшенным PCM: одно кодирование libmp3lame и обычный пост-QC
  → ENHANCED либо ENHANCEMENT_REJECTED (точные байты Balanced)
```

Штатного пути `MP3 → Balanced MP3 → улучшенный MP3` нет: улучшается
декодированный исходник, а Balanced применяется к улучшенному PCM один раз
(`normalizer::prepare_from`). Края обрезки, отказ и свойства источника
определяются по **исходному** PCM, где видны слабые звуки. Громкость, true peak
и шумовой потолок — по фактически кодируемому улучшенному сигналу. Поэтому
усиление, обрезка и фейд не удваиваются, а громкость результата — цель профиля
(на корпусе медиана −23,0 LUFS).

### Триаж

Кандидат — запись с хотя бы одним измеренным признаком (без имён файлов и SHA
корпуса):

| Признак | По умолчанию |
|---|---|
| оценка SNR (речь p95 минус шумовой пол Balanced) ниже | 35 dB |
| шумовой пол выше | −55 dBFS |
| усиление Balanced ограничено шумовым потолком | `limited_by: noise_floor` |

Отложенность у Balanced (`deferred_automatic_processing`) сама по себе
кандидатом не делает: большинство отложенных записей ограничены неуверенными
краями, а не шумом. Шумовой пол, оценённый без пауз (`all_windows_p10`), даёт
предупреждение `noise_estimate_unreliable`.

### Инференс

- Каналы обрабатываются **независимо**, без сведения в моно: противофазное
  стерео не гасится. Побайтно одинаковые каналы обрабатываются один раз,
  что эквивалентно независимой обработке.
- Состояние модели между входами не переносится: каждый канал каждого клипа
  получает клон только что созданного экземпляра. Результат не зависит от
  соседей и порядка.
- Задержка модели (1440 отсчётов: перекрытие STFT и lookahead) компенсируется
  точно. Конец дополняется нулями на задержку и до целого кадра (сброс хвоста),
  длина выхода равна длине входа. Расхождение длины, неконечные отсчёты или
  несогласованная диагностика — сбой протокола, а не «улучшение».
- Контекст прогрева (`context_ms`, по умолчанию 200 мс): зеркальное
  продолжение клипа на обоих краях обрабатывается и отбрасывается. Потоковая
  модель стартует с нулевых состояний и без контекста подавляет начало слова.
- Предел ослабления (`atten_lim_db`, по умолчанию 18 dB): без предела модель
  полностью гасит слабые края и хвосты слов.

## Enhancement QC

Снижение шума — необходимое, но не достаточное условие. Окна 10 мс
исходника `a` и улучшенного сигнала `b` той же длины; шумовой пол — p10 окон;
«сильная речь» — окна не ниже «речь p95 − 15 dB» и выше шума на 10 dB.
Каждая проверка всегда присутствует. `resolved: false` (величину нельзя
вычислить) — отказ. `samples: 0` — проверяемых окон нет, проверка вакуумно
пройдена.

| Проверка | Предел | Что ловит |
|---|---|---|
| `length_preserved` | ≤ 1 кадр после обратного ресэмплинга | добавленная тишина, обрезка |
| `alignment_lag` | ≤ 1 мс | некомпенсированная задержка |
| `noise_reduction` | ≥ 6 dB | нет пользы; отказ — `enhancement_benefit_insufficient` |
| `strong_speech_preserved` / `strong_speech_p90` | медиана ≤ 1,5 dB, p90 ≤ 3 dB падения | ослабление голоса |
| `no_segment_loss` | серия окон речи с падением > 10 dB ≤ 30 мс | пропажа мора, короткого слова |
| `weak_sounds_preserved` | медиана падения ≤ 6 dB | согласные и переходы у речи (до 150 мс от сильной речи) |
| `edges_preserved` | худшая медиана трёх первых/последних окон непрерывной звучащей области ≤ 6 dB | срезанные начальные согласные и хвосты слов |
| `separated_activity_preserved` | падение ≤ 10 dB | отделённый звук не тише «речь − 25 dB» (возможная часть слова); тихие вдохи и щелчки модель гасит законно |
| `no_added_energy` | p95 роста тихих окон ≤ 3 dB | «галлюцинации» модели (окна рядом со звуком и ниже −90 dBFS не учитываются) |
| `spectral_balance` | полосы речевой части: ослабление ≤ 6 dB, подъём ≤ 3 dB | потеря фрикативов, артефакты |
| `loudness_preserved` | падение ≤ 4 dB | подавление голоса |
| `no_new_clipping` | отсчётов у полной шкалы не больше, чем в исходнике | перегрузка |

В `spectral_balance` сравнивается не энергия полосы исходника, а её речевая
часть (мощность в окнах сильной речи минус мощность в тихих окнах). Полосы, где
речь не выше шума, не оцениваются. `codec_snr` между шумным входом и очищенным
выходом мерой пользы не служит: выход отличается от входа намеренно. Польза на
синтетике проверяется против известного чистого эталона (тесты
`tools/speech-enhance`).

## QualityGate этапа

| Исход | Выбор | `next_action` |
|---|---|---|
| `NOT_NEEDED` | вход (точные байты Balanced) | `use_input`, при ограничениях Balanced — `deferred_automatic_processing` |
| `ENHANCED` | улучшенный MP3 | `use_enhanced`, при ограничениях — `deferred_automatic_processing` |
| `ENHANCEMENT_REJECTED` | вход | всегда `deferred_automatic_processing` (шум остался) |
| `DEFERRED` | вход | `deferred_automatic_processing` |
| `INPUT_REJECTED` | нет | `discard_input` |

Сочетание исхода, выбора, действия и фактических данных (инференс, QC,
Balanced над улучшенным сигналом, вывод) проверяет `EnhancementResult::validate`.
Противоречивый (подделанный или изменённый) результат кэш отвергает и
пересчитывает. `ENHANCED` требует пройденного QC и пройденного пост-QC Balanced.
`REJECT` этап не выдаёт: непригодность входа решает только Balanced.

Ограничения Balanced (например, `uncertain_*_boundary`) переносятся в решение
для выбранного входа. Новые причины имеют источники `enhancement_qc` (провал
проверки нейроварианта, `enhancement_qc_<проверка>`), `enhancement_policy`
(`enhancement_not_applicable`) и `post_qc` (`enhancement_balanced_post_qc_failed`).

## Сбои среды

Сбой backend или FFmpeg — не исход входа: вход остаётся незавершённым, в кэш не
пишется, повторяется следующим запуском, восемь сбоев подряд останавливают
пакет. Коды `details.blocker`:

| Код | Когда |
|---|---|
| `enhancer_backend_unavailable` | воркер не найден, не исполняемый, prlimit не смог его запустить |
| `enhancer_model_unavailable` | веса пропали или повреждены во время пакета (выход воркера 3) |
| `enhancer_backend_timeout` | предел времени (`timeout_seconds`) или CPU |
| `enhancer_backend_crashed` | завершение сигналом (авария, нехватка памяти) |
| `enhancer_backend_failed` | иной ненулевой код выхода |
| `enhancer_backend_protocol` | неразбираемый отчёт, другая модель, другая длина или SHA вывода |
| `interrupted` | результат получен после Ctrl+C/SIGTERM |

`enhancer_identity_mismatch` и `enhancer_backend_changed` (воркер или веса
изменились после старта) — отказ старта или продолжения, а не повтор: смешивать
результаты разных моделей нельзя.

Результат, завершившийся после сигнала остановки, не принимается ни этим этапом,
ни Balanced (общий исполнитель `run_items`). Ctrl+C получает вся группа
процессов, и FFmpeg, перехватив SIGINT, завершается обычным ненулевым кодом. Без
этой проверки такой отказ выглядел бы свойством входа.

## Пакет, кэш и воспроизводимость

Пакет улучшения живёт в рабочем каталоге **завершённого** пакета Balanced
(режим `normalize`, текущая схема). Неполный базовый пакет — отказ
`base_batch_incomplete` с числом недостающих результатов. Инвентаризация, корень
входа, безопасное чтение и ограниченный исполнитель — те же, что у Balanced:

```text
<workspace>/.runtime/batches/<batch-id>/state.json
<workspace>/.runtime/batches/enhancer-cache/results/<sha входа>.<sha конфигурации>.json
<workspace>/.runtime/batches/enhancer-cache/candidates/<sha улучшенного MP3>.mp3
```

Отпечаток конфигурации — SHA-256 схемы результата, версии алгоритмов
(`speech-enhancement-gate/1`), режима исполнения (`cpu-tract-single-thread`),
профиля, идентичности backend (SHA воркера, манифест весов, параметры) и
отпечатка Balanced (его профиль, FFmpeg, ffprobe, кодировщик, анализатор).
Смена любого из них — новый ключ. Любое изменение логики триажа, QC или
маршрутизации обязано менять версию алгоритмов, иначе прежние результаты будут
ложно переиспользованы. Запись кэша годна, только если JSON соответствует ключу и
согласован, указанный MP3 существует и совпадает по SHA и длине, а вход
перечитан и совпадает с инвентаризацией. `batch-resume` заново проверяет FFmpeg
и идентичность backend: другая сборка — отказ, новый пакет.

ID `enhancer-cache` и `normalizer-cache` зарезервированы. ID пакета улучшения
должен отличаться от ID базового пакета.

## Отчёт

`batch-report` атомарно создаёт новый каталог (общий механизм с отчётом Balanced):

- `summary.json` — полнота отдельно по уникальным SHA и по файлам; исходы,
  действия и выбор по SHA и по файлам; причины, источники ограничений, причины
  отложенных; сбои QC; признаки триажа; переходы «исход Balanced → исход
  улучшения»; та же сводка по входам, отложенным Balanced (`base_deferred`);
  сбои backend; модель, воркер и профиль; ресурсы (запуски, секунды аудио,
  время воркера, RTF); распределения метрик QC;
- `items.jsonl` — полный результат и пути каждого уникального входа;
- `items.tsv`, `base_deferred.tsv` — строка на вход: исходы, выбранные байты,
  метрики до/после, причины.

## Калибровка и live-приёмка

Состояние на сегодня, по приватному корпусу из нескольких тысяч реальных MP3.
Корпус в Git не входит, числа — результат прогона, а не пороги тестов:

- Все уникальные входы получили автоматическое решение, сбоев backend нет.
  Около 15 % стали кандидатами триажа. Из них примерно каждый седьмой принят
  (`ENHANCED`), остальные отклонены с сохранением входа: чаще всего из-за
  падения краёв и хвостов слов (`edges_preserved`), потери части сильной речи
  у самых шумных записей (`strong_speech_p90`) и недостаточной пользы.
- Среди отложенных Balanced (по текущей инвентаризации) большинство получили
  `NOT_NEEDED`: их ограничения — неуверенные края, а не шум. Ограничения
  сохранены, действие остаётся `deferred_automatic_processing`.
- Без предела ослабления медианное падение начала и хвостов слов у кандидатов
  — 6–28 dB, а у четверти клипов край обнулялся. С пределом 18 dB и контекстом
  200 мс — 4–5 dB при снижении шума ≈ 11,6 dB (медиана).
- Решения и выбранные байты воспроизводятся побайтно: прерванный по SIGINT и
  возобновлённый пакет совпал с непрерывным прогоном по всем входам.

Производительность — [страница модуля](performance.md#улучшение-речи).

Автоматически **не** доказаны соответствие чтению, сохранность фонетики и
тонального акцента на настоящей речи сверх сигнальных проверок. Это задача
будущего этапа выбора записи (ASR и проверка человеком).

## Дополнительный backend: Resemble Enhance

Статус: **экспериментальный, опциональный**, только denoiser. По умолчанию
не используется; включается профилем `resemble-denoise-conservative`. Triage,
Enhancement QC, QualityGate, кэш, отчёт и fallback к точным байтам Balanced —
те же, что у DeepFilterNet3. Отличаются только backend, его идентичность и
пределы процесса.

### Почему только denoiser

Resemble Enhance состоит из двух частей: denoiser (маска на спектрограмме) и
генеративного enhancer (латентный CFM и вокодер), который синтезирует речь
заново. Генеративную часть этап не допускает. Она способна заменить или сдвинуть
звуки, а сигнальный QC такую подмену фонемы не докажет. Замер подтвердил это:
на первых 150 из 755 кандидатов генеративный режим принят 5 раз. Отказы — в
основном `alignment_lag` (117), `strong_speech_p90` (74) и `edges_preserved`
(47): выход сдвинут во времени и меняет сильную речь.

### Совместимость и граница доверия

| Наблюдение | Решение |
|---|---|
| Последний выпуск `resemble-enhance` 0.0.1 (2023) закрепляет `torch==2.1.1`, `deepspeed==0.12.4`, `gradio==4.8.0`; колёс torch 2.1 для Python новее 3.11 нет | отдельное окружение Python 3.11 с точными версиями `tools/speech-enhance/resemble/requirements.txt`, вне сборки Cargo |
| Штатная загрузка без `run_dir` выполняет `git pull` плавающей ревизии Hugging Face при каждом вызове | воркер всегда передаёт каталог весов; сеть не нужна (проверено запуском в `unshare -rn`) |
| Чекпойнт — pickle; `torch.load(weights_only=True)` в torch 2.1 его не читает (`set`), а `add_safe_globals` появился позже | SHA-256 файлов проверяется **до** разбора, разбор — ограниченным unpickler: разрешены только `OrderedDict`, `set`, `HalfStorage` и `_rebuild_tensor_v2`, на которые ссылается чекпойнт |
| `hparams.yaml` содержит теги `!!python/object/apply` | `yaml.SafeLoader`, разрешён только `pathlib.PosixPath` |
| CUDA резервирует виртуальную память с запасом: под `--as=4GiB` процесс падает с `MemoryError` | предел адресного пространства процесса этого backend — 16 GiB |
| Вывод на CUDA и на CPU различается побайтно, внутри устройства детерминирован | устройство (`runtime.device`, GPU, версии CUDA/torch) входит в идентичность и ключ кэша; смена устройства между запусками — `enhancer_backend_changed` |

Закреплённые веса — `enhancer_stage2` репозитория
[ResembleAI/resemble-enhance](https://huggingface.co/ResembleAI/resemble-enhance)
на ревизии `4e3510ce4a8391159f665903544c5150bee7b2cb`: чекпойнт
`ds/G/default/mp_rank_00_model_states.pt` (713176232 байт, `f9d035f3…d9d6`)
и `hparams.yaml` (717 байт, `80c3f15b…aeac`). Отпечаток манифеста —
`58f26fd76b782e165581c7114b3e9046a9d8b3986d47f36f6e0d8818c4e897d3`. Из
чекпойнта загружается только `denoiser.*` в строгом режиме.

Воркер `speech_enhance_resemble.py` реализует тот же протокол, что
`speech-enhance-dfn`: `identify`, `process`, `install-model`, один процесс на
клип, коды выхода 3/4/5. В `identify` он сообщает SHA-256 собственного
исходника и версии окружения. Исполняемый файл, который запускает
`asset-store`, — запускатель окружения, поэтому снимок файла во время пакета
покрывает только его. Замену исходника воркера ловит повторный `identify` при
`batch-resume`. Задержки нет (`delay_samples: 0`), ресэмплинг 48 → 44,1 → 48 kHz
выполняется внутри воркера, длина выхода равна длине входа.

### Установка и запуск

```bash
uv venv --python 3.11 /private/resemble/.venv
uv pip install --python /private/resemble/.venv/bin/python \
  -r tools/speech-enhance/resemble/requirements.txt
printf '#!/bin/sh\nexec %s -I %s "$@"\n' /private/resemble/.venv/bin/python \
  "$PWD/tools/speech-enhance/resemble/speech_enhance_resemble.py" > /private/resemble/speech-enhance-resemble
chmod +x /private/resemble/speech-enhance-resemble
# Веса: три файла ревизии выше, скачанные заранее в /private/resemble/weights.
$B enhancer model-install --backend resemble-enhance-denoise \
  --source /private/resemble/weights --backend-bin /private/resemble/speech-enhance-resemble
$B enhancer profile --backend resemble-enhance-denoise > /private/resemble/profile.json
$B enhancer batch-start --batch-id res-1 --base-batch-id corpus-1 --workspace … \
  --profile /private/resemble/profile.json --backend-bin /private/resemble/speech-enhance-resemble --jobs 4
```

Веса ставятся только из локального каталога (`--source`), в
`resemble-enhance-denoise/<отпечаток манифеста>/`. `SPEECH_ENHANCE_RESEMBLE_DEVICE=cpu`
принудительно выбирает CPU. Параметры `atten_lim_db`, `post_filter_beta` и
`context_ms` к этому backend не относятся: в его профиле они обязаны остаться
значениями по умолчанию, иначе профиль некорректен. Улучшенный вариант получает
причину `enhanced_by_resemble_enhance_denoise`.

### Результат на корпусе

Состояние на сегодня, тот же приватный корпус и тот же завершённый пакет
Balanced, что у DeepFilterNet3. Весь прогон шёл без сети, на CUDA:

- Все уникальные входы получили решение, сбоев backend нет. До модели дошли
  те же кандидаты триажа. Принято (`ENHANCED`) примерно на 40 % больше, чем у
  DeepFilterNet3.
- Профиль отказов другой. Denoiser почти не трогает речь: провалы проверок
  речи и краёв единичны. Но у большинства отклонённых он недостаточно снижает
  шум (`enhancement_benefit_insufficient`). Если снижает, то сильно: медиана
  снижения шумового пола у принятых ≈ 24,6 dB против ≈ 7,7 dB у DeepFilterNet3.
- Принятые множества backend пересекаются мало: менее 10 % принятых хотя бы
  одним из них приняты обоими. Выбор backend — профиль пакета;
  автоматической цепочки «DF3, затем Resemble» этап пока не делает.
- Решения воспроизводятся: повторный пакет полностью берётся из кэша.
- Цена — время. Каждый вызов — новый процесс с загрузкой PyTorch, CUDA и
  чекпойнта (≈ 3,5 с при инференсе в доли секунды). Поэтому пакет медленнее
  DeepFilterNet3 примерно в 8 раз, а GPU здесь ускоряет инференс, но не
  процесс. Числа — на [странице производительности](performance.md#улучшение-речи).

Автоматически не доказано то же, что и для DeepFilterNet3: фонетика и тональный
рисунок сверх сигнальных проверок.
