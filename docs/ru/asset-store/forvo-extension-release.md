# Выпуски адаптера Forvo: канал, подпись и сопровождение

Распакованное MV3-расширение адаптера ([forvo-brave.md](forvo-brave.md)) обновляется
без магазинов расширений, CRX и внешних update-серверов: GitHub Actions публикует
версионированный ZIP в GitHub Releases, а `pronunciation-assets forvo browser update`
проверяет и устанавливает его в уже настроенный каталог цели. Первичная установка
по-прежнему одно ручное действие пользователя в режиме разработчика браузера.

## Владелец версии

Единственный владелец версии адаптера — поле `version` в
`tools/asset-store/src/forvo/brave/extension/manifest.json` (формат Chromium: 1–4
числа через точку). От версии Cargo и workspace она не зависит. Из неё выводятся
тег `forvo-extension-v<версия>`, имя архива `forvo-extension-<версия>.zip`,
`version` подписанных метаданных и версия, которую расширение сообщает bridge
(`chrome.runtime.getManifest().version`).

## Пакет

`forvo/brave/package.rs` — единственный источник runtime-файлов: `manifest.json`,
`background.js` и генерируемый из общих `forvo/dom.js` и `forvo/auth.js`
`forvo_page.js`. Тот же набор разворачивает `setup` (вместе с индивидуальным
`pairing.json`) и упаковывает релизный ZIP. В ZIP нет `pairing.json`, секретов,
состояния, профилей, загрузок, журналов и тестовых данных: допустимы только файлы
`.js`, `.json`, `.png` с именами `[a-z0-9][a-z0-9_.-]*` не глубже одного каталога.
ZIP детерминирован: файлы по имени, без сжатия, время 1980-01-01, права 0644.
Одинаковые исходники дают одинаковые байты архива — на этом держится защита от
«разных ZIP под одной версией».

## Цепочка доверия

| Звено | Что доказывает |
|---|---|
| `forvo-extension-release.json` | канал `forvo-extension`, версия и тег, репозиторий, 40-символьный коммит `main`, протокол bridge и разрешения manifest, имя, SHA-256 и размер ZIP, точный состав ZIP с SHA-256 каждого файла |
| `forvo-extension-release.json.sig` | подпись Ed25519 точных байтов метаданных, `key_id` — первые 16 hex SHA-256 открытого ключа |
| `tools/asset-store/src/forvo/brave/release_keys.json` | закреплённые открытые ключи; встраиваются в CLI при сборке и не берутся из источника выпуска |

SHA-256 архива доверен только потому, что он внутри подписанных метаданных: файл
SHA рядом с архивом аутентификацией не является. Установщик проверяет подпись до
разбора метаданных, затем всё остальное ([порядок `update`](forvo-brave.md#обновление-из-выпусков)).
Подмена байта, SHA, версии, тега, репозитория, канала, состава, подпись чужим ключом
и опасный архив отвергаются до изменения каталога установки.

Границы доверия. Ключ подписи — секрет окружения GitHub `forvo-extension-release`:
тот, кто может запускать workflow в этом окружении или прочитать секрет, может
подписать выпуск. Доверенный корень — исходники CLI: кто может изменить
`release_keys.json` в `main`, тот меняет доверие следующих сборок CLI. Атаку
«заморозки» (канал не показывает новые выпуски) подпись не предотвращает; понижение
версии установщик отвергает. Протокол bridge и разрешения manifest ограничены
самим CLI: выпуск с новым разрешением или протоколом требует нового CLI.

GitHub artifact attestation в этой схеме не используется: проверку выполняет сам CLI
по закреплённому ключу, офлайн и без сервисов Sigstore.

## Workflow

`.github/workflows/forvo-extension-release.yml`:

- **`pull_request`** (без секретов, права `contents: read`) — сборка пакета тем же
  кодом, что у `setup`. Если базовый commit уже содержит релизный упаковщик, CLI
  строит ZIP из базового checkout и PR; при различии байтов `check-bump` требует
  версию выше базовой. Это учитывает фактическое влияние упаковщика и всех его
  входов, не требуя bump для изменений вне ZIP. Если упаковщик ещё не входил в
  базу (bootstrap этого канала), `check-bump` требует первичное повышение версии.
  Затем workflow строит план по GitHub Releases; стабильный опубликованный выпуск
  той же версии проходит полную проверку подписи, метаданных и ZIP до сравнения с
  локальной сборкой. Ничего не публикуется.
- **`push` в основную ветку и `workflow_dispatch` на ней** — задание `check`, затем
  публикация с правом `contents: write` и окружением `forvo-extension-release`, если
  тег свободен и план требует новый выпуск. Подписываются метаданные; выпуск
  проверяется встроенным корнем CLI. После публикации workflow загружает его,
  заново проверяет подпись и содержимое, сравнивает с текущей сборкой и сверяет,
  что Git-тег указывает на коммит из подписанных метаданных. Публикация выполняется
  с `--latest=false` и не меняет общий «Latest» репозитория.
- Стабильным каналом считаются только опубликованные выпуски без `draft` и
  `prerelease`. Черновик или предварительный выпуск не повышает максимальную
  стабильную версию, но выпуск/тег с тем же именем нельзя считать свободным:
  такой план блокируется, как и любой уже занятый Git-тег без единственного
  проверяемого стабильного выпуска. Черновики автоматически не удаляются.
- Очередь публикаций одна и не отменяется (`concurrency`). Повторный запуск после
  публикации находит стабильный выпуск и выполняет только проверку; опубликованное
  содержимое не перезаписывается. Несовпадающий ZIP приводит к отказу
  `published_release_differs`, версия не выше максимальной стабильной — к
  `version_not_increased`. При bootstrap (стабильных выпусков пока нет) версия не
  сравнивается с несуществующей, но занятого целевого тега всё равно быть не должно.
- Всё делается в одном запуске: события, созданные `GITHUB_TOKEN`, другие workflow не
  запускают, и выпуск на них не полагается.

## Повышение версии агентом

Если фактические байты релизного ZIP изменились, в том же PR нужно повысить
`version` в `manifest.json`. Это проверяется сравнением ZIP, которые один и тот же
CLI строит из базового и текущего checkout; правило охватывает генератор и все
файлы, от которых зависит пакет, и не срабатывает для изменений вне ZIP. После
слияния при успешных проверках выпуск публикуется автоматически. Локальная команда
`check-bump` проверяет только строгое увеличение версии; решение о том, изменился
ли ZIP, принимает workflow сравнением контрольных сумм собранных архивов:

```bash
cargo build --locked -p asset-store --bin forvo-extension-release
target/debug/forvo-extension-release build --out /tmp/forvo-dist \
  --repository Flandre-Scarlet-the-best/anki-deck-toolkit --commit "$(git rev-parse HEAD)"
target/debug/forvo-extension-release check-bump --base-version "$(git show origin/main:tools/asset-store/src/forvo/brave/extension/manifest.json | jq -r .version)"
```

Workflow и `setup` используют одну реализацию упаковки в `package.rs`; когда упаковщик
есть в base, тот же CLI собирает архив из base и head. Команда `sources` удалена:
вручную перечислять отдельные входы было недостаточно для гарантии, что изменение
упаковки будет замечено. Публиковать настоящий Release ради проверки PR нельзя.

## Первый выпуск и внешние шаги сопровождающего

До первого выпуска нужно (статус — **BLOCKED** до выполнения владельцем):

1. Создать ключ на доверенной машине вне CI:
   `forvo-extension-release keygen --out <файл>` — файл (0600) содержит PKCS#8 в
   base64, вывод — `key_id`, открытый ключ и строку для `release_keys.json`.
2. PR с записью ключа в `release_keys.json` (только открытый ключ).
3. Окружение GitHub `forvo-extension-release`: секрет `FORVO_EXTENSION_SIGNING_KEY` с
   содержимым файла ключа; правило окружения — только ветка `main`. Файл ключа
   хранить офлайн, в репозиторий не добавлять.
4. Рекомендуется ruleset тегов `forvo-extension-v*` (создание только Actions, без
   удаления и перезаписи) и включение immutable releases.

Первый запуск без опубликованных стабильных выпусков — план `publish` с
`bootstrap=true`: версия не сравнивается с несуществующей, но целевой тег обязан
быть свободен, а ZIP, подпись, проверка встроенным корнем и сверка после публикации
выполняются полностью. Предварительные выпуски не становятся стабильной базой.
Черновик или тег с точным целевым именем блокирует публикацию и требует ручного
разбора; workflow их не удаляет. Без шагов 1–3 публикация завершается отказом
`signing_key_missing`/`signing_key_untrusted`, а не ложным успехом. Пока в CLI нет
закреплённого ключа, сетевые `update` и `update-check` отказывают
`release_trust_root_missing` (`BLOCKED`); встроенная версия адаптера продолжает
работать.

## Ротация и отзыв ключа

Новый ключ добавляется в `release_keys.json` рядом со старым; выпуски подписываются
новым после того, как CLI с обоими ключами распространился. Отзыв — удаление ключа
из `release_keys.json`: CLI новых сборок перестаёт принимать выпуски, подписанные им.
Уже установленный адаптер это не затрагивает. При компрометации секрета: удалить
секрет окружения, выпустить CLI без скомпрометированного ключа, переподписать
нужные выпуски нельзя (тег не перетирается) — опубликовать следующую версию.

## Команды инструмента

```bash
forvo-extension-release build --out <каталог> --repository <owner/name> --commit <SHA> [--notes-out <файл>]
forvo-extension-release sign --dir <каталог> [--key-env FORVO_EXTENSION_SIGNING_KEY]
forvo-extension-release verify --dir <каталог> [--trusted-public-key <файл>]
forvo-extension-release plan --releases <json из gh api --paginate --slurp>
forvo-extension-release compare --dir <собранный> --published <опубликованный>
forvo-extension-release check-bump --base-version <версия>
forvo-extension-release keygen --out <файл>
```

`verify` ограниченно читает только обычные файлы выпуска внутри `--dir`: сначала
проверяет формат метаданных и допустимую версию, затем проверяет подпись и читает
архив установленного размера. Для автономного тестового выпуска можно явно передать
открытый тестовый ключ через `--trusted-public-key`; секретный ключ для проверки не
нужен. Команда `compare` перед сравнением локальной сборки полностью проверяет
подпись и содержимое опубликованного выпуска закреплённым ключом. Неподписанный
опубликованный ZIP не переиспользуется.

Результат — одна строка JSON `{"outcome":"ok","result":…}` или
`{"outcome":"error","code":…,"details":…}` с кодом выхода 1. Сеть инструмент не
использует: список выпусков и опубликованные файлы передаёт workflow.
