# Balanced Normalizer и технический QualityGate для японских MP3

Подкоманды `pronunciation-assets normalizer` измеряют MP3 произношений, бережно
обрезают **только краевую** тишину, выравнивают воспринимаемую громкость одним
линейным усилением и проверяют фактически декодированный результат. Итог
каждого входа — объяснимое техническое решение QualityGate. Выбранный вариант
попадает в [аудиохранилище](pronunciation.md) только отдельной явной командой
`publish` и только через CAS с новым подтверждением человека.

## Границы

- **Только локальные файлы.** Ни одна подкоманда не обращается к Forvo,
  браузеру, сети или API. Источник — явно заданный каталог MP3 либо файл.
- **Вход только читается.** Каталог входа не изменяется: в нём не появляются
  временные файлы, блокировки, отчёты или результаты. Обход не следует
  символическим ссылкам, каждый файл открывается относительно дескриптора корня
  с `NOFOLLOW`. Вход и рабочий каталог не могут быть вложены друг в друга или в
  `decks/**`. `batch-verify-sources` повторно хеширует вход после работы.
- **Пара `surface + reading` не угадывается по имени файла.** Пакетная
  обработка работает с байтами и SHA-256; пара задаётся пользователем только
  при публикации.
- **`ACCEPT` — техническая пригодность варианта, а не правильность чтения.**
  Модуль не распознаёт японскую речь: RMS, LUFS, true peak и уровни окон —
  эвристики сигнала. Нет ASR, forced alignment, нейросетевого шумоподавления,
  time-stretch, pitch shift, компрессии, лимитера и «коррекции произношения».
- Существующие `AudioTechnicalValidator`, `Uncertain`/`Quarantined`,
  `HumanAttestation`, `Verified` и проверка по текущему SHA сохраняют свою роль.
  Политика Kanji и Pitch Accent не меняется.

## Конвейер одного входа

```text
байты MP3 → probe_mp3 (та же техническая проверка, что у хранилища)
          → декодирование в f32 той же частоты и раскладки
          → анализ → план (края, усиление, раскладка вывода)
          → [normalize] одно кодирование libmp3lame → probe_mp3 и декодирование
            результата → пост-QC → QualityGate
```

Режим `analyze` останавливается на плане: исход QualityGate в нём —
прогноз без проверки результата (`gate.post_qc_verified: false`). Публикуется
только результат режима `normalize`.

Если изменение не нужно, кодирования нет: хороший исходник получает
`KEEP_ORIGINAL` без потерь повторного lossy-кодирования.

## Измерения

Все величины конечны; неопределённое значение — `null`, а не 0 или NaN.
Цифровая тишина представлена уровнем −120 dB.

| Поле | Смысл |
|---|---|
| `integrated_lufs`, `integrated_blocks` | BS.1770: блоки 400 мс, шаг 100 мс, пороги −70 LUFS и −10 LU; K-фильтр рассчитывается для фактической частоты |
| `short_window_lufs`, `short_window_blocks` | те же пороги на окнах 100 мс с шагом 25 мс — для слов короче устойчивого интегрального измерения |
| `true_peak_dbtp` | максимум после передискретизации 4× (полифазный FIR, 64 отвода), не ниже пика отсчётов |
| `sample_peak_dbfs`, `rms_dbfs` | пик отсчётов и RMS всего сигнала |
| `max_window_dbfs`, `speech_level_dbfs` | максимум и p95 уровней окон 10 мс (максимум RMS по каналам) |
| `noise_floor_dbfs`, `noise_floor_method` | оценка шума: медиана окон ниже порога речи (`quiet_windows`); если таких окон меньше трёх — консервативная p10 всех окон (`all_windows_p10`), она завышает шум и сильнее ограничивает усиление |
| `leading_/trailing_below_threshold_ms`, `..._below_weak_ms` | длительность края ниже порога речи и ниже порога слабого звука |
| `active_ms`, `longest_internal_pause_ms`, `internal_pauses` | длительность окон не ниже порога речи; внутренние паузы только измеряются |
| `clipping` | отсчёты у полной шкалы, выше неё и серии из трёх и более подряд |
| `dc_offset`, `stereo_difference_db` | постоянная составляющая; уровень разности каналов относительно сигнала |

## Профиль Balanced

Профиль — типизированный JSON со строгой схемой (`schema_version: 1`,
неизвестные поля отвергаются) и собственными `id`/`version`. Значение по
умолчанию печатает `normalizer profile`; собственный профиль передаётся
`--profile FILE`. Отпечаток конфигурации — SHA-256 профиля, режима,
`schema_version` результата и окружения (`ffmpeg`/`libavcodec`/
`libswresample` и версия анализатора `balanced-analyzer/1`). Любое изменение
параметра или сборки FFmpeg даёт новый отпечаток: прежние результаты не
переиспользуются и не смешиваются с новыми.

Исходные ориентиры — гипотеза ранней небольшой выборки. Значения ниже
сверены на корпусе реальных произношений (см. «Калибровка»); их обоснование —
данные, а не исключения под отдельные файлы.

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `analysis.frame_ms` | 10 | окно уровней |
| `analysis.signal_floor_dbfs` | −70 | максимум окна ниже — сигнала нет (`REJECT`) |
| `analysis.min_duration_ms` | 120 | короче — `very_short_clip` (прослушивание) |
| `analysis.long_internal_pause_ms` | 1200 | длиннее — предупреждение: возможны два слова или дубль |
| `trim.silence_threshold_dbfs` | −50 | порог уверенного сигнала |
| `trim.weak_sound_margin_db` | 10 | окна от −60 до −50 dBFS — возможный слабый звук, никогда не удаляются |
| `trim.min_edge_silence_ms` | 150 | край тише слабого порога короче этого не обрезается |
| `trim.guard_leading_ms` / `guard_trailing_ms` | 60 / 80 | сохраняемая тишина перед первым и после последнего возможного звука |
| `trim.fade_ms` | 5 | полукосинусный фейд внутри сохранённого запаса на обрезанном крае |
| `trim.uncertain_floor_margin_db` | 6 | медиана удаляемого края не ниже −66 dBFS — граница неуверенна, край не трогается |
| `trim.min_speech_margin_db` | 15 | p95 окон должен быть выше порога речи хотя бы на столько |
| `loudness.target_lufs` | −23 | цель |
| `loudness.gain_tolerance_db` | 1 | меньшее отклонение не исправляется |
| `loudness.max_gain_db` / `max_attenuation_db` | 12 / 20 | пределы линейного усиления |
| `loudness.true_peak_ceiling_dbtp` | −2 | потолок true peak результата |
| `loudness.encode_headroom_db` | 0.5 | запас под рост true peak при кодировании |
| `loudness.max_noise_floor_after_dbfs` | −55 | усиление не поднимает оценку шума выше |
| `loudness.review_shortfall_db` | 6 | недобор цели больше — прослушивание |
| `loudness.min_integrated_blocks` | 3 | меньше блоков — короткие окна |
| `output.sample_rate` | `{"mode":"source"}` | либо `{"mode":"fixed","hz":…}` |
| `output.channels` | `source` | `mono_if_identical` (разность каналов ≤ −60 dB) или `mono` |
| `output.encoder` | `{"mode":"vbr","quality":2}` | либо `{"mode":"cbr","kbps":…}` |
| `gate.max_true_peak_overshoot_db` | 0.5 | допуск true peak результата над потолком |
| `gate.max_duration_error_ms` | 10 | допуск длительности результата относительно плана |
| `gate.max_active_change_ms` / `_ratio` | 30 / 0.05 | допуск изменения активной части |
| `gate.min_codec_snr_db` | 15 | минимальный SNR результата относительно подготовленного PCM |
| `gate.max_loudness_error_db` | 1 | допуск громкости результата относительно плана |
| `gate.max_new_clipped_samples` | 0 | новых отсчётов у полной шкалы не допускается |
| `gate.review_clip_ratio` | 0.0005 | доля отсчётов у полной шкалы, требующая прослушивания исходника |
| `gate.max_alignment_lag_ms` | 5 | допуск сдвига результата (задержка кодировщика) |

### Края

Окна не ниже −60 dBFS (порог речи минус запас слабого звука) считаются
возможным звуком. Удаляется только тишина **до первого** и **после
последнего** такого окна, за вычетом защитного запаса, и только если она не
короче 150 мс. Внутренние паузы, долгие гласные, `っ` и всё между первым и
последним возможным звуком не изменяются. Отдельная слабая активность у края
(дыхание, шум, слабый звук, отделённый тишиной) сохраняется и помечается
предупреждением. Если уровень удаляемого края близок к порогу слабого звука или
речь слабо выделяется над порогом, граница считается неуверенной: край не
обрезается, а запись получает `REVIEW_REQUIRED`.

### Громкость

Используется интегральная громкость, если прошло стробирование хотя бы три
блока 400 мс, иначе — короткие окна (`short_clip_loudness`), иначе громкость
недоступна и усиление не применяется. Желаемое усиление ограничивается
пределами профиля, потолком true peak с запасом на кодирование и шумовым
потолком; ограничение не превращает тихую запись в ещё более тихую.
Недостижимая цель видна в `shortfall_db` и `limited_by`. Нет ни `loudnorm`, ни
лимитера, ни компрессии: результат — исходный PCM, умноженный на одно число.
Исходник, уже бывший выше потолка true peak, не ослабляется только ради
потолка; это отмечается `source_true_peak_above_ceiling`.

### Вывод

Одно кодирование libmp3lame с `-bitexact`: одинаковые вход, профиль и сборка
FFmpeg дают одинаковые байты. Частота и раскладка по умолчанию сохраняются.
Метаданные источника, ID3 и обложки в вариант не переносятся; Xing/LAME-тег
записывается, чтобы декодер учитывал задержку кодировщика. Вариант снова
проходит `probe_mp3` и декодируется для пост-QC.

## QualityGate

| Исход | Значение | `proposed_variant` |
|---|---|---|
| `ACCEPT` | обработанный вариант прошёл пост-QC, причин для прослушивания нет | `processed` |
| `KEEP_ORIGINAL` | исходник уже в допусках профиля; кодирования не было | `original` |
| `REVIEW_REQUIRED` | нужен человек; предлагаемый вариант указан явно | `processed` или `original` |
| `REJECT` | сигнал технически непригоден: MP3 не прошёл проверку, нет сигнала | нет |

Сомнение не становится `REJECT`: неуверенная граница, недостижимая цель,
перегрузка исходника и сбой пост-QC дают `REVIEW_REQUIRED`. Сбой пост-QC
всегда предлагает исходник. Каждая причина имеет `code`, `severity`
(`info`/`warning`/`review`/`reject`) и сообщение:

| Код | Важность | Когда |
|---|---|---|
| `source_invalid` | reject | `probe_mp3` отверг файл |
| `no_signal` | reject | цифровая тишина или максимум окна ниже −70 dBFS |
| `source_rejected_by_store_validator` | review | файл декодируется полностью, а расхождение кадровой и декодированной длительности **точно до отсчёта** объясняет тег LAME, но текущая проверка хранилища такой файл не принимает |
| `uncertain_leading_boundary`, `uncertain_trailing_boundary` | review | край близок к порогу слабого звука, не обрезан |
| `low_signal_margin` | review | речь слабо выделяется над порогом |
| `loudness_unavailable` | review | громкость не измерима |
| `target_shortfall` | review | цель недостижима больше чем на 6 dB |
| `very_short_clip` | review | запись короче 120 мс |
| `source_clipping` | review | признаки перегрузки исходника; этап их не исправляет |
| `encode_failed`, `post_qc_<проверка>` | review | вариант не получен или не прошёл пост-QC |
| `processing_failed_repeatedly` | review | три сбоя среды подряд на одном входе |
| `leading_weak_activity_kept`, `trailing_weak_activity_kept` | warning | отдельная слабая активность у края сохранена |
| `source_true_peak_above_ceiling`, `long_internal_pause`, `dc_offset` | warning | диагностика исходника без изменения |
| `short_clip_loudness`, `gain_limited`, `already_within_profile` | info | способ измерения и ограничения |

Пост-QC проверяет фактически декодированный вариант: `output_technical_probe`,
`output_layout`, `duration_matches_plan`, `true_peak_within_ceiling`,
`no_new_clipping`, `loudness_matches_plan`, `leading_edge_quiet`/
`trailing_edge_quiet` (на обрезанном крае первое/последнее окно ниже порога
речи — признак, что звук не срезан), `active_duration_preserved`,
`alignment_lag` и `codec_snr`. Каждая проверка хранит значение и предел.

`gate.unresolved` всегда перечисляет то, что этап не проверяет: соответствие
чтению и фонетике и эвристический характер границ речи. Это решает человек.

## Команды

Все подкоманды печатают JSON schema 1 (`outcome`, `result` или `error`) и
поддерживают общие `--repository-root` и `--output json|text`.

```bash
B="cargo run --locked --release --bin pronunciation-assets --"
$B normalizer profile > .codex/local/normalizer/profile.json
$B normalizer analyze --file /path/to/word.mp3 [--profile FILE] [--mode normalize]
$B normalizer trial --file /path/to/word.mp3 --out /private/out/word.mp3
$B normalizer batch-start --batch-id corpus-1 --input-dir /path/to/mp3 \
  --workspace .codex/local/normalizer/work [--mode analyze|normalize] \
  [--jobs 4] [--max-items N] [--max-files 20000] [--max-total-bytes 4294967296]
$B normalizer batch-status --batch-id corpus-1 --workspace .codex/local/normalizer/work
$B normalizer batch-resume --batch-id corpus-1 --workspace .codex/local/normalizer/work
$B normalizer batch-cancel --batch-id corpus-1 --workspace .codex/local/normalizer/work
$B normalizer batch-report --batch-id corpus-1 --workspace .codex/local/normalizer/work \
  --out .codex/local/normalizer/report-1 --html [--include problems|all|sample] \
  [--sample FILE] [--media-limit 400]
$B normalizer batch-sample --batch-id corpus-1 --workspace .codex/local/normalizer/work \
  --seed 20261106 --per-stratum 5 --out .codex/local/normalizer/sample-1.json
$B normalizer batch-review-summary --batch-id corpus-1 \
  --workspace .codex/local/normalizer/work --decisions decisions.json [--sample FILE]
$B normalizer batch-verify-sources --batch-id corpus-1 --workspace .codex/local/normalizer/work
$B normalizer publish --batch-id corpus-1 --workspace .codex/local/normalizer/work \
  --input-sha256 <sha входа> --surface こいつ --reading こいつ \
  --replace-expected-sha256 <sha текущей записи> [--allow-replace-verified] [--override-gate]
```

`analyze` ничего не пишет. `trial` пишет вариант в **новый** файл вне
каталога исходника и `decks/**`, и только если QualityGate предлагает
обработанный вариант. Рабочий каталог, отчёты и выборки держите в
игнорируемой `.codex/local/` или другом приватном каталоге.

Коды выхода общие для CLI: 0 — успех (в том числе пакет, остановленный
`--max-items`, с `run.outcome: "paused"`), 130 — отмена или Ctrl+C,
3/4/5 — отказ ввода/перехода, нарушение границы или целостности, I/O.

## Пакет и восстановление

`batch-start` фиксирует инвентаризацию (относительные пути, размеры, SHA-256)
и конфигурацию, затем обрабатывает недостающие результаты. Пропущенные записи
(ссылки, не `*.mp3`, небезопасные имена, глубина больше 16) учитываются в
инвентаризации с причиной. Пределы `--max-files` и `--max-total-bytes`
проверяются до обработки, файл больше 8 MiB получает собственную ошибку.

Состояние живёт в штатной области `SafeBatchRuntime` рабочего каталога:

```text
<workspace>/.runtime/batches/<batch-id>/state.json      # конфигурация, прогресс, отмена
<workspace>/.runtime/batches/<batch-id>/data/inventory.json
<workspace>/.runtime/batches/normalizer-cache/results/<sha входа>.<sha конфигурации>.json
<workspace>/.runtime/batches/normalizer-cache/candidates/<sha варианта>.mp3
```

Результат каждого уникального входа — отдельная атомарная контрольная точка.
Дубли байтов обрабатываются один раз. Повторный запуск того же пакета и новый
пакет той же конфигурации в том же рабочем каталоге переиспользуют готовые
результаты без повторной работы. Изменённая сборка FFmpeg останавливает
`batch-resume`: смешивать результаты разных сборок нельзя.

Обработка идёт в `--jobs` потоках (1–32, каждый внешний процесс
однопоточный) через ограниченную очередь: в памяти одновременно не больше
`2 × jobs` результатов. Каждый запуск FFmpeg ограничен как в
[технической проверке](pronunciation.md#зависимости-и-ограничения).
Счётчики `state.json` обновляются не реже раза в две секунды; на них же
проверяется отмена. Ctrl+C и SIGTERM останавливают выдачу новых входов,
сохраняют завершённые результаты и дают `outcome: "paused"` с
`paused.code: "interrupted"` (код 130). Сбой среды (нет FFmpeg, ошибка
временных файлов, процесс убит сигналом) не превращается в исход входа: вход
повторяется при следующем запуске, после трёх сбоев получает
`REVIEW_REQUIRED`; восемь сбоев подряд останавливают пакет. Ошибка записи
результата (например, нет места) останавливает пакет без частичных файлов.
Изменение входа после инвентаризации фиксируется в `progress.source_errors`.
`batch-cancel` терминален для будущих `batch-resume`.

Исполнитель держит исключительную блокировку кэша рабочего каталога на всё
время работы: `batch-report`, `batch-sample` и второй исполнитель того же
рабочего каталога ждут его завершения. `batch-status` и `batch-cancel`
не ждут.

## Отчёты, выборка и ручные решения

`batch-report` создаёт **новый** каталог (существующий не перезаписывается):

- `summary.json` — инвентаризация (файлы, уникальные SHA, группы дублей,
  пропуски по причинам), исходы, причины, методы громкости, уверенность краёв,
  сбои пост-QC, частоты и раскладки, распределения метрик с квантилями
  p00…p100;
- `items.jsonl` — полный результат и все пути каждого уникального входа;
- `items.tsv` — одна строка на вход с исходом, причинами и метриками до/после;
- `report.html` и `media/` (с `--html`) — сравнение оригинала и варианта
  рядом, причины, неуспешные проверки, фильтры по исходу и причине, поиск.

HTML автономен: Content-Security-Policy запрещает сеть, данные встроены как JSON
с экранированием `<`, `>`, `&`, а все строки вставляются через `textContent`.
Копии MP3 называются `<sha256>.mp3`; исходные имена в файловую систему отчёта
не попадают. `--include problems` (по умолчанию) показывает всё, кроме
`KEEP_ORIGINAL` и `ACCEPT` без предупреждений; `--media-limit` ограничивает
число записей с копиями.

`batch-sample` строит воспроизводимую стратифицированную выборку: случайные
`ACCEPT`/`KEEP_ORIGINAL`/`REVIEW_REQUIRED`/`REJECT` (порядок — SHA-256 от
seed и входа) и крайние значения: самые тихие и громкие, наибольшее
усиление и ослабление, наибольшая обрезка каждого края, минимальный запас перед
речью, неуверенные границы, слабая активность у края, длинные паузы,
перегрузка, шумный пол, самые короткие и длинные, громкость по коротким
окнам, наименьший SNR кодирования, сбои пост-QC. Файл выборки хранит seed,
число на страту, отпечаток конфигурации, SHA инвентаризации и SHA входов.
Отчёт по выборке: `batch-report --include sample --sample FILE --html`.

В HTML для каждой записи выбирается оценка: `acceptable`, `bad_trim`,
`degraded`, `source_problem`, `unsure` и заметка. Оценки сохраняются в
браузере и выгружаются кнопкой в JSON:

```json
{"schema_version":1,"kind":"normalizer_review_decisions","batch_id":"corpus-1",
 "config_sha256":"<sha>","decisions":[{"input_sha256":"<sha>","verdict":"bad_trim","note":""}]}
```

`batch-review-summary` проверяет, что решения относятся к тому же пакету и
конфигурации, и сводит их с исходами и стратами: ложные `ACCEPT` (оценка
`bad_trim`/`degraded`), излишне осторожные `REVIEW_REQUIRED`/`REJECT`
(оценка `acceptable`) и распределения метрик по оценкам. По этой сводке
пересматривается профиль: новая версия профиля — новый пакет.

## Публикация в хранилище

`publish` — единственный путь варианта в хранилище. Условия:

1. результат режима `normalize`, пост-QC пройден, исход `ACCEPT` с
   предложенным `processed`; `REVIEW_REQUIRED` — только с `--override-gate`
   после прослушивания;
2. байты варианта и исходника сверены с результатом, исходник перечитан из
   входа по SHA;
3. у пары есть текущая запись хранилища, её SHA равен SHA входа и
   `--replace-expected-sha256`. Корпус без пары сначала импортируется штатным
   `import` с явными `surface`/`reading`;
4. запись в `Verified` заменяется только с `--allow-replace-verified`;
   производный вариант повторно не обрабатывается.

Перед записью исходные байты сохраняются в `normalizer-cache/candidates/`, а
после — запись `publications/<sha входа>.<sha варианта>.json`. Вариант
импортируется общим путём `asset-store` (CAS, блокировки, журнал,
`AudioTechnicalValidator`) с происхождением `audio_derivative` /
`balanced_normalizer-<первые 16 символов SHA входа>.mp3`. Метаданные:

```json
{"surface":"…","reading":"…","derivation":{
  "schema_version":1,"kind":"balanced_normalizer",
  "source_sha256":"…","source_provenance":{"source_kind":"forvo_web","source_name":"forvo-ja-101.mp3"},
  "source_metadata":{"surface":"…","reading":"…","forvo":{…}},
  "output_sha256":"…","mode":"normalize","profile":{…},"toolchain":{…},
  "config_sha256":"…","plan":{…},"gate":{…},"gate_overridden":false}}
```

Происхождение Forvo исходника сохраняется целиком и проверяется для его SHA;
производный MP3 не выдаётся за `forvo_web`. Проверка записи сверяет
отпечаток конфигурации с профилем и инструментами. Новый SHA получает
`Uncertain`/`Quarantined` и никогда не наследует прежнее `Approve`: доверие
появляется только после нового `attest` этого SHA. Предпросмотр, пакет и отчёты
хранилище не открывают.

## Калибровка

Состояние на сегодня, по приватному корпусу из нескольких тысяч реальных
MP3 произношений; корпус не является эталоном качества и в Git не входит.
Числа ниже — результат одного полного прогона текущего профиля, а не пороги
тестов.

- Почти все записи — 44.1 kHz, моно и стерео; стереозаписи в основном
  фактически моно (разность каналов −120 dB).
- Около 6 % файлов — gapless-MP3 LAME 3.98 с дополнением кодировщика
  1800–2300 отсчётов. Тег LAME объясняет расхождение длительностей точно до
  отсчёта во всех случаях, но действующая проверка хранилища
  (`pronunciation-mp3-technical` v1) допускает не более трёх кадров и отвергает
  их. Нормализатор не меняет эту проверку и помечает такие файлы
  `source_rejected_by_store_validator`; исправление допуска требует новой
  версии валидатора и повторной проверки существующих записей.
- Рост true peak после кодирования профилем по умолчанию — p99 0.23 dB,
  максимум 0.45 dB: запас 0.5 dB покрыл весь корпус. Задержка кодировщика
  компенсируется полностью (сдвиг 0, ошибка длительности не больше 1 мс).
  Минимальный SNR кодирования — 18.5 dB.
- Короткие окна дают на 0.2–0.6 dB (медиана) большую громкость, чем
  интегральное измерение тех же записей, — меньше допуска усиления 1 dB,
  поэтому поправка не вводится.
- После нормализации громкость результатов — −23.0 LUFS (p05–p95 в пределах
  ±0.03 dB), кроме записей с ограниченным усилением.
- Удаляемые края всегда тише −60 dBFS.
- Оценка шума по окнам ниже порога речи вместо p10 всех окон сократила число
  записей с усилением, ограниченным шумовым потолком, примерно на треть: прежняя
  оценка для записей почти без пауз принимала речь за шум.
- Исходов `REJECT` на корпусе нет; `REVIEW_REQUIRED` — около 8 %, из них три
  четверти — файлы с дополнением LAME из пункта выше.

Что **не** проверено автоматически и требует прослушивания стратифицированной
выборки: фактическая сохранность слабых начальных и конечных звуков, внутренних
пауз и тонального рисунка на настоящей речи, приемлемость звучания после
кодирования. Ложные отказы и ложные принятия на настоящих записях оцениваются
только ручными решениями (`batch-review-summary`).
