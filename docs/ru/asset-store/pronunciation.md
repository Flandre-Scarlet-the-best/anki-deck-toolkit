# Японские MP3: `pronunciation-assets`

Домен `pronunciation_audio` хранит независимые произношения в
`.asset-store/pronunciation-audio/`. Локальный импорт оригинальных MP3 требует технической проверки
и явного решения человека. [Forvo](forvo.md) получает исходник только по написанию
и сохраняет его в Forvo-пакете без чтения и без импорта в этот домен.
Последующая явная связь с парой принадлежит [Selection](selection.md);
исторические Forvo-ресурсы домена продолжают читаться. Импорт и проверка не требуют ASR и DSP: хранится
точный оригинал. Измерение, бережная обрезка краёв, выравнивание громкости и
технический QualityGate — отдельный [Balanced Normalizer](normalizer.md); его
вариант попадает в корпус только явной командой `normalizer publish` как новая
запись с происхождением `audio_derivative`. Выбранный интервал или производный
кандидат из [выбора аудиокандидатов](selection.md) публикуется командой
`pronunciation-selection promote` как запись с происхождением
`selection_derivative`: в ней хранятся SHA исходника, интервал, преобразование,
цепочка, отпечатки инструментов и конфигурации; оригинал не заменяется.
Выбор кандидата для пары без обязательного прослушивания, полномочия решений и
офлайн-обзор — [выбор аудиокандидатов](selection.md); он не меняет правил
`Verified` и не создаёт `HumanAttestation` без заявленного прослушивания.
`asset-store` не открывает `decks/**`, не меняет `deck.json`, `media_files`
и не материализует файлы в колоды. Обработчика аудио в `anki-repo create` пока нет.

## Зависимости и ограничения

Поддерживается Linux, включая WSL. Нужны `ffmpeg`, `ffprobe` и `prlimit`
(util-linux) в `PATH`; тестам дополнительно нужен encoder `libmp3lame`.
Например, Debian/Ubuntu: `sudo apt-get install ffmpeg util-linux`.
Отсутствие инструмента даёт `validator_failure`, без доверенной публикации.
Новых Rust-зависимостей нет.

Ресурс ограничен 8 MiB и 30 секундами декодированного аудио. Пакет содержит
1–128 элементов и суммарно не более 64 MiB исходных снимков; JSON-план и выбор
потребителя ограничены 1 MiB. Поддерживается MPEG-1/2/2.5 Layer III с постоянными
частотой и числом каналов, CBR/VBR, ID3v2.2–2.4 и ID3v1. Free bitrate,
произвольный мусор между кадрами, несколько аудиопотоков и другие
контейнеры отвергаются. Обложки ID3 не декодируются и не участвуют в доверии. Импорт не обрезает, не
обрабатывает и не перекодирует байты: обработанный вариант — другие байты с
собственным SHA, свидетельством происхождения и новым решением человека
([нормализатор](normalizer.md#публикация-в-хранилище)).

Каждый внешний процесс получает 1 GiB адресного пространства, 12 CPU-секунд,
64 файловых дескриптора и 15 секунд wall time. Запуск — отдельные argv через
`prlimit`, без shell. stdin закрыт, потоки вывода читаются параллельно с пределами
64 KiB для ffprobe, 6 MiB для PCM, 16 KiB для stderr. Timeout убивает и дожидается
процесса. Внешний stderr не сохраняется в происхождении: он может содержать
пути и метаданные источника. Временные снимки принадлежат `TempWorkspace`.

## Идентичность и имена

`Pronunciation::new(surface, reading)` нормализует обе строки только в NFC.
NFKC не применяется: `ｶﾞ` и `ガ` остаются разными написаниями.
Поля непустые, до 180 UTF-8 байт каждое, без управляющих символов и краевых
пробелов; итоговый сериализованный ключ ограничен общим лимитом идентичности.
Ключ — каноническая JSON-пара `[surface, reading]` в namespace
`pronunciation_audio`. Чтение никогда не угадывается по файлу.

### Имя потребителя

Имя готового MP3 пары у потребителя — `<surface>.mp3` (`こいつ.mp3`; исходный
файл `pronunciation_ja_こいつ.mp3` на имя не влияет). Исключение — одиночный
кандзи (`kanji_domain::parse_kanji_character`): у него разные чтения одного
написания — обычное дело, поэтому имя `<surface>_<reading>.mp3` (`生_せい.mp3`,
`生_なま.mp3`), и чтения не конфликтуют. Это имя **результата**, а не запроса
Forvo: поиск идёт только по написанию. Чтобы граница была однозначной, чтение
одиночного кандзи не может содержать `_`, `/`, `\`, `:`, `<`, `>`, `"`, `|`,
`?`, `*`, `[`, `]` и оканчиваться точкой или пробелом; это ограничение новых
пар. Историческая запись одиночного кандзи с таким чтением (прежний импорт его
не вводил) по-прежнему открывается и сохраняет имя `<surface>.mp3`. Написание — прежние
ограничения (`<`, `>`, `"`, `|`, `?`, `*`, `[`, `]`, `.`/`..`); зарезервированные
имена устройств и имена длиннее 255 байт отвергаются. Слово не сокращается и не
заменяется безопасным суррогатом. Два чтения слова (не одиночного кандзи)
по-прежнему делят одно имя и вместе не выдаются.

Запись одиночного кандзи, созданная раньше с именем `<surface>.mp3`
(`Pronunciation::legacy_consumer_filename`), сохраняет его: проверка манифеста
принимает у записи либо текущее имя, либо историческое имя её же пары
(`AssetDomainPolicy::accepts_historical_consumer_filename`), и записи не
переименовываются молча. Новая запись и замена записи по CAS получают
`<surface>_<reading>.mp3`. Домен доказывает принадлежность `<surface>.mp3`
своей паре (`proves_legacy_consumer_filename`), но `anki-repo migrate-media`
пока не обрабатывает `pronunciation_audio` (отказ `media_domain_unknown`) и
ссылки колод на прежнее имя не переводит.

Внутренний путь — `assets/<sha256(identity.key)>/<content-sha256>.mp3`.
Разночтения одного написания имеют независимые объекты, решения и CAS-слоты,
даже если байты одинаковые. Повторные имена разрешены только в этом домене.
При выборе для одного `media/` весь набор проверяется до первого результата:
разные идентичности с эквивалентным именем вызывают `identity_conflict`, даже
при одинаковых SHA. Сравнение имён использует NFC и Unicode lowercase.
Нормализованные эквивалентные surface/reading — одна идентичность: вторые
байты требуют CAS. Потребитель обязан выбирать **весь** набор для одного
каталога одной операцией и отдельно учитывать уже существующие файлы media.
Отдельные вызовы чтения не резервируют имя на диске потребителя.

## Проверка и доверие

Сигнатура `DetectedFormat::Mp3` — только классификация. Вариант добавлен после
`Unknown`, порядок прежних форматов и схема 6 не меняются. Доверие требует
полной технической проверки:

1. Обход всех границ MPEG Layer III, ID3 и длины каждого кадра. Усечённые кадры,
   пустой файл, HTML, WAV с расширением `.mp3` и поток с меняющимися параметрами
   отвергаются до декодера.
2. ffprobe подтверждает один поток `mp3`, формат, частоту и каналы.
3. FFmpeg полностью декодирует его в ограниченный PCM s16le без изменения
   частоты и каналов. Проверяются ошибки stderr, объём вывода и реальное число
   отсчётов, а не только exit code.
4. Длительность PCM сравнивается с длительностью ffprobe и числом отсчётов
   полных кадров. Абсолютный допуск — три MPEG-1 кадра при фактической частоте
   плюс 2 ms: он учитывает Xing/Info, encoder delay/padding и не растёт
   пропорционально длине записи. Существенная ложная длительность отвергается.
5. Gapless-MP3 (например, LAME 3.98 с дополнением около 2000 отсчётов, которое
   больше допуска) принимается вместо допуска по **точному равенству**, и
   только если тег структурно доказан в **первом** кадре потока: `Xing`/`Info`
   ровно после побочной информации кадра без CRC; поле `frames` равно числу
   остальных кадров; поле `bytes` (если есть) и длина музыки LAME равны длине
   аудиоданных; расширение LAME целиком внутри кадра и его CRC-16 (как у LAME:
   полином 0xA001, всё от начала кадра до поля CRC) верен; строка кодировщика —
   `LAME`, `Lavf` или `Lavc`, то есть та, чьи задержки применяет FFmpeg; неизвестные
   флаги отсутствуют. Тогда FFmpeg обязан выдать ровно
   `frames × spf − delay − max(padding, 529)` отсчётов (`spf` — 1152 для
   MPEG-1 и 576 для MPEG-2/2.5, 529 — задержка декодера, см. `mp3dec.c`).
   Длительность ffprobe для такого тега сверяется с обычным допуском в любой
   из двух конвенций FFmpeg: FFmpeg 8.0 и новее вычитают задержку и
   дополнение, прежние версии (например, 6.1 из Ubuntu 24.04) сообщают полную
   длину `frames × spf`. Тег, которому декодер противоречит, — отказ. Байты `Xing`/`LAME` в другом месте
   файла, поддельный, усечённый или чужой тег ничего не доказывают: такой файл
   проходит только обычный допуск. Общего расширения допуска нет.

Свидетельство `mp3_technical_v2` содержит `request` с surface/reading и `probe`
(`schema_version: 2`): `codec`, `sha256`, `byte_length`, `sample_rate`,
`channels`, `frames`, `declared_duration_seconds`, `decoded_duration_seconds`,
`decoded_samples` и, если тег доказан, `gapless` (`encoder`, `delay`,
`padding`, `xing_frames`); проверка записи сверяет и это равенство.
Технический отказ содержит причину, SHA и размер в `details`. Точкой версии
`ValidationRecord` служит `pronunciation-mp3-technical` / `2`.

Свидетельство версии 1 (`mp3_technical_v1`) остаётся читаемыми данными и не
теряется, но доверия не даёт: публичное чтение такой записи отказывает.
Безопасная повторная проверка — штатный `validate --surface … --reading …
--sha256 …` для точной пары/SHA (в библиотеке — `AssetStore::validate` в
режиме `SelectionMode::New`, который выбирает все записи без актуального
свидетельства) или повторный `import` тех же байтов. Повторная проверка
заново декодирует текущие байты, записывает свидетельство версии 2 и
сохраняет прежнее `HumanAttestation` той же пары/SHA без изменений. Новое
решение человека при этом не создаётся, а запись, которую версия 2 не
принимает, доверие не получает.

Успех проверки даёт **UNCERTAIN**, а не фонетическое соответствие. Кандидат
переходит из `Pending` в `Quarantined` с техническим свидетельством: это
ожидание ручного прослушивания, а не автоматический запрет записи.
Явный `Approve` конкретной пары/SHA сохраняет `HumanAttestation` и переводит
запись в `Verified`; исходный `ValidationRecord` остаётся `Uncertain`.
`Reject` отзывает доверие и возвращает ресурс в карантин. Позднее точное
положительное решение может заменить отрицательное.

Одобрение требует актуального технического свидетельства и повторного
декодирования нынешних байтов. При старой версии валидатора сначала повторите
`import` тех же байтов или `validate` для текущих пары/SHA, затем `attest`.
Отказ не публикует `Verified` и не записывает предоставление доверия.
Публичное доверенное чтение требует вместе актуальную версию технической проверки
и явное положительное решение человека,
проверяет SHA/размер/формат и снова декодирует полученные байты. Другой SHA,
reading, surface, устаревшее свидетельство, symlink и изменение байтов не
приобретают доверия. Техническое декодирование не заменяет прослушивание.

Замена требует `replace_expected_sha256` текущей записи. Она сбрасывает прежние
решения и требует нового подтверждения. При замене неподтверждённого кандидата
(`Pending`/`Quarantined`) его прежние байты остаются в `.runtime` во вложенной
CAS-раскладке `assets/<sha256(identity.key)>/`, в том числе после подтверждения
нового кандидата; такой файл допустим, только если его имя совпадает с
фактическим SHA-256. Запись `Verified` при замене покидает канонический
манифест вместе со своими байтами. Повтор тех же байтов идемпотентен,
включая отрицательное решение: повторный импорт сам его не отменяет.
Запись идёт через существующие блокировки, CAS, атомарные манифесты и журнал
`asset-store`; отдельного реестра доверия нет.

Технически полный MP3 без исходной длительности может быть корректной более
короткой записью. Нельзя доказать потерю целых завершающих кадров такого файла,
если у него нет противоречащих метаданных; неполный кадр и ложный Xing timeline
отвергаются. Техническая проверка также не определяет, что на записи есть речь.

## Команды

Все команды поддерживают `--repository-root`, `--store` и `--output json|text`;
по умолчанию JSON schema 1. `text` печатает тот же документ с отступами.
Путь хранилища по умолчанию считается от `--repository-root` (по умолчанию `.`).
Пути источников не должны содержать `..` или symlink в любом компоненте;
защищённый `decks/` данного репозитория и корней, найденных по хранилищу,
не открывается. Независимый внешний каталог с именем `decks` допустим.
Источник читается один раз с открытого дескриптора, снимок связывает проверку
и импорт SHA. В provenance остаётся
только одноуровневое имя файла, без абсолютного пути.

```bash
cargo run --locked --bin pronunciation-assets -- init
cargo run --locked --bin pronunciation-assets -- probe --file /tmp/pronunciation_ja_こいつ.mp3
cargo run --locked --bin pronunciation-assets -- import \
  --surface こいつ --reading こいつ --file /tmp/pronunciation_ja_こいつ.mp3
cargo run --locked --bin pronunciation-assets -- inspect
cargo run --locked --bin pronunciation-assets -- validate \
  --surface こいつ --reading こいつ --sha256 <текущий-sha256>
cargo run --locked --bin pronunciation-assets -- attest \
  --surface こいつ --reading こいつ --sha256 <текущий-sha256> \
  --decision approve --reason 'Прослушано: произнесено ожидаемое чтение'
cargo run --locked --bin pronunciation-assets -- verify
```

`probe` работает без инициализации корпуса. `import` инициализирует корпус при
необходимости, проверяет MP3, сохраняет кандидата и технический ValidationRecord.
Опциональный `--expected-source-sha256` защищает от смены исходника; для замены
нужен `--replace-expected-sha256`. `inspect` показывает весь текущий корпус и
кандидатов с решениями. `validate` перепроверяет точную пару/SHA.
`verify` проверяет целостность корпуса и повторяет техническую проверку всех
записей, сохраняя результат и исходное решение человека; он не подтверждает речь.
Для отзыва используется `attest --decision reject` с текущими парой/SHA и причиной.

Успех содержит `schema_version: 1`, `outcome: "ok"`, `result`; ошибка —
`outcome: "error"` и `error {code,message,details}`. Коды выхода наследуются
от общего CLI: 0 — операция завершилась, 2 — синтаксис аргументов clap,
3 — отказ ввода/CAS/перехода, 4 — нарушение границы/целостности/схемы,
5 — I/O/технический валидатор. Пакетная команда завершает обработку даже при
ошибке отдельных элементов: итог каждого элемента находится в `outcome`,
а не теряется из-за первого технического отказа. `imported` означает сохранение
кандидата; текущий статус доверия следует брать из манифеста, не из истории пакета.

## Пакет и восстановление

Строгий план schema 1: неизвестные и повторные поля, повтор нормализованной
идентичности, неверная версия или SHA отвергаются. `file` считается от каталога
плана; допускается абсолютный локальный путь. SHA источника обязателен.
Планы и результаты держите в игнорируемой `.codex/local/`, аудио и corpus —
в `.asset-store/` либо другом приватном локальном каталоге вне tracked-дерева.

```json
{
  "schema_version": 1,
  "items": [
    {
      "surface": "こいつ",
      "reading": "こいつ",
      "file": "pronunciation_ja_こいつ.mp3",
      "expected_source_sha256": "<64-символа-sha256>",
      "replace_expected_sha256": null
    }
  ]
}
```

```bash
cargo run --locked --bin pronunciation-assets -- batch-start \
  --batch-id local-audio --plan .codex/local/audio/plan.json --max-items 1
cargo run --locked --bin pronunciation-assets -- batch-status --batch-id local-audio
cargo run --locked --bin pronunciation-assets -- batch-resume --batch-id local-audio
cargo run --locked --bin pronunciation-assets -- batch-cancel --batch-id local-audio
```

Перед обработкой сохраняются неизменяемые blobs всех доступных источников и
атомарное состояние `.runtime/batches/<batch-id>/state.json`. Недоступный
источник или SHA mismatch получает собственный терминальный исход.
Смена/удаление источника после старта не влияет на resume. Ошибка одного
кандидата сохраняется, остальные обрабатываются. `--max-items 0` позволяет
только зафиксировать план; положительное значение ограничивает число новых
попыток команды. `batch-status` проверяет состояние и blobs.

На каждый исход записывается checkpoint. Пакетная блокировка сериализует
исполнителей, повторное продолжение пропускает завершённые элементы.
Прерывание SIGINT/SIGTERM оставляет атомарные изменения и незавершённую работу
для resume; при смерти между импортом и checkpoint тот же снимок повторяется
идемпотентно. Подтверждённые записи не теряются и не подтверждаются заново.
`batch-cancel` делает отмену терминальной для будущих resume; уже выполненные
импорты и решения остаются в общем корпусе. Конкурентная отмена ждёт текущего
исполнителя под общей блокировкой пакета. Для исправленного плана нужен новый
batch-id; завершённые ошибки автоматически не переигрываются.

## API потребителя

```rust
use asset_store::pronunciation::{Pronunciation, read_trusted};

let requests = vec![Pronunciation::new("こいつ", "こいつ")?];
let assets = read_trusted(store_root, &requests)?;
// Слово (не одиночный кандзи): имя `<surface>.mp3` и у новой, и у исторической записи.
assert_eq!(assets[0].record.consumer_filename, "こいつ.mp3");
// assets[0].bytes — точные оригинальные MP3, проверенные в этом чтении.
```

`read_trusted` — read-only API: не создаёт store/runtime, не пишет манифест
или журнал, не открывает колоды. Совместная выдача читает согласованный снимок
под общей блокировкой. Для CLI используется `read --requests PATH` с документом
`{"schema_version":1,"items":[{"surface":"こいつ","reading":"こいつ"}]}`;
он показывает проверенные записи с именами и SHA, без base64 аудио.
CLI проверяет байты по одной записи под общей блокировкой, накапливая только
метаданные в порядке запроса. Ошибка любого элемента отклоняет весь ответ;
конфликты имён проверяются до первого результата.
Файлы в media CLI не создаёт. Общий `read_verified_with_policy` с
`PronunciationDomainPolicy` применяет ту же проверку конфликтов и доверия.
