# Доверенный экспорт Anki в input

Владелец — закрытый модуль `anki_repo::desktop::input`, команды
`anki-repo anki sync-input` и `input-status`. Он соединяет
[Desktop](desktop.md), оригинальный CrowdAnki exporter и
[exchange](exchange.md). Экспорт запускается только по команде пользователя.
`decks/output/`, база A и последнее подтверждение импорта не изменяются.

## Запуск и план

Подготовьте Anki штатными `anki setup`, `anki patch install` и перезапуском.
Для уже установленного патча предыдущего поколения выполните его обновление
при остановленной Anki. В `doctor` должны быть загружены оба аддона и текущий
патч; отсутствие функционального evidence импорта не мешает экспорту.

```bash
anki-repo --json anki --executable <anki> --data-dir <Anki2> \
  --profile 'Selected profile' sync-input --repository . \
  --deck 'Selected root' --deck 'Another root'

anki-repo --json anki --executable <anki> --data-dir <Anki2> \
  --profile 'Selected profile' sync-input --repository . \
  --deck 'Selected root' --deck 'Another root' --apply

anki-repo anki --profile 'Selected profile' sync-input --all --apply
anki-repo --json anki input-status --repository .
```

Без `--apply` показывается план: выбранная база, профиль, колоды, необходимость
первой привязки. Остановленная Anki не запускается: план сообщает
`needs_launch`, список из неё пока не получен. План не создаёт `input` или
`exchange`, не назначает идентичности и не вызывает exporter.

С `--apply` подготовленная остановленная Anki запускается существующим
управляемым механизмом; CLI ждёт handshake до 90 секунд. Уже работающую Anki
он использует только с выбранным профилем, без переключения или перезапуска.
Занятие, модальное окно, фоновая операция или другой профиль требуют действий
пользователя. Установка аддонов и открытый порт сами по себе недостаточны.

Повторяющийся `--deck` означает точные имена из живого каталога Anki.
Выбранные предок и потомок экспортируются одним поддеревом.
`--all` получает обычные колоды живого профиля, исключает filtered decks и
выбирает верхние доступные корни. Данные `input`/`output` для перечисления
не используются. При адресном выборе имена проверяются только у выбранных
корней и их потомков: несвязанная колода с непригодным для файлового экспорта
именем не мешает работе. Непригодное выбранное имя даёт
`invalid_export_deck_name`. Другие профили не открываются.

## Идентичность и свидетельство

При первом применении namespaced action `toolkitBindProfile` сохраняет два
случайных UUID в `ProfileManager`: UUID базы в глобальной записи `prefs21.db`
и UUID профиля в его записи. SHA-256 пары становится `ProfileId`.
`ProfileManager.save()` фиксирует их штатно. Переименование профиля переносит
ту же запись и сохраняет идентичность. Одноимённые профили разных баз имеют
разные UUID. Дубликат UUID среди записей одной базы, повреждённая запись или
противоречивая привязка дают отказ.

UUID профилей дополнительно учитываются по именам в глобальном реестре
`anki_deck_toolkit_identity_profiles`, а запись профиля получает метку
`anki_deck_toolkit_identity_bound`. Новый профиль той же базы имеет собственный
UUID и использует существующий UUID базы. Реестр и метка отличают его от
утраты UUID уже привязанного профиля, в том числе после переименования.
Переименование при `toolkitBindProfile` обновляет имя в реестре без смены UUID.
Для прежней привязки без реестра сначала явно подтвердите существующий профиль
через `sync-input --apply`: реестр заполняется из сохранённых UUID без их
генерации заново. Неполная прежняя привязка отвергается; повторное использование
имени удалённого привязанного профиля требует отдельного согласования.

База дополнительно привязана к её каноническому **native** пути, полученному
в Anki. Linux CLI в WSL не превращает Windows-путь в самостоятельную
идентичность. Перенос или копия уже привязанной `prefs21.db` в другую базу
отклоняются: следует выбрать исходную базу или отдельно согласовать перенос;
автоматического переприсвоения потока нет. Это не механизм миграции профилей.

Каталог `toolkitCatalog` и все новые actions проходят прежние apiKey,
capability, installation/profile handshake, проверку владельца порта и
готовности аддонов. Новый exporter или отдельный аддон не устанавливаются.

До HTTP admission сохраняются одноразовый ticket и устойчивый ID задания.
Ticket связывает профиль, `ProfileId`, процесс Anki, числовой ID колоды,
её точное имя и известный CrowdAnki UUID. Exporter может впервые назначить
UUID в самой Anki. Завершённый job содержит фактический UUID и полный набор
SHA-256 `deck.json` и физических media. Только живой `toolkitJob` со
`succeeded` и `action=export` допускает проверку spool. Сохранённый результат
без ответа живого API, `ready`, `submitted` и каталог на диске этого права
не дают. Путь spool строится из выбранной локальной базы и проверенного ID;
полученный от Windows `export_dir` не используется как Linux-путь.

Владелец читает полные байты, применяет общий parser, структурный validator и
`Snapshot::from_bytes`, проверяет UUID, имя, отсутствующие media и полный
inventory живого job. Неизвестные JSON-свойства сохраняются. Дочерние имена
CrowdAnki проверяются по полному пути дерева: одинаковые листья у разных
родителей допустимы, коллизии нормализованных полных путей — нет.

## Публикация и восстановление

Один адрес потока — `decks/input/<полный SHA-256 DeckIdentity>/current/`.
Внутри `current` остаются оригинальные `deck.json`, `media/` и, при наличии,
`import_config.yaml`. Имя колоды не входит в адрес; существующая привязка
`exchange.output_directory` сохраняется при её переименовании.

Операции сериализуются advisory-блокировкой каталога `input`. Конкурентная
команда получает немедленный отказ `input_busy`, если
блокировка `input` или его родительского каталога занята, и не отправляет
экспорт. При `--apply` блокировка берётся до запуска Anki и привязки профиля;
занятый владелец не вызывает этих побочных действий. Режим без `--apply`
хранилище не открывает. Дождитесь завершения владельца и повторите вызов. `--wait-seconds`
ограничивает только опрос экспорта, а не получение блокировки. Владелец использует
директории через dirfd, `NOFOLLOW`, проверяет inode, обычный тип файлов,
единственную hardlink, изменения при чтении и коллизии имён media.
`input` требует принадлежности текущему UID и прав 0700.

До создания первого каталога потока владелец надёжно сохраняет
`.new-stream.json` в корне input: исходный снимок, полный inventory и
свидетельство задания. После сбоя этот журнал доказывает принадлежность
ещё не зарегистрированного каталога. Полный staging завершается тем же CAS;
неполный убирается только если каждый присутствующий файл совпал с inventory.
Неучтённые имена, подменённые байты и каталог без такого доказательства
сохраняются с отказом. После завершения журнал создания удаляется.
`input-status` при нём требует восстановления.

Протокол одной публикации:

1. Полный экспорт пишется в `stage` на той же файловой системе; каждый файл
   и изменённые каталоги синхронизируются. Повторное чтение доказывает байты.
2. Надёжно записывается `transaction.json`: проверенный снимок, inventory,
   прежний C, следующий sequence и evidence задания.
3. Старый `current` переименовывается в `previous`, затем `stage` в `current`.
   Для обоих rename запрещена замена существующего назначения; после каждого
   требуется успешный fsync каталога. Rename поверх непустого каталога нет.
4. Новый `current` проверяется, вызывается настоящий `ExchangeStore.record_input`
   с актуальным CAS-токеном. Несвязанное изменение метаданных перечитывается;
   изменение того же потока вне протокола даёт отказ.
5. Сохраняется `receipt.json`, удаляются `previous` и intent. В штатном
   состоянии остаётся один полный снимок, без истории поколений.

Между двумя rename `current` может отсутствовать, а между его переключением
и `record_input` файлы и метаданные ещё не согласованы. Это **незавершённая**
публикация, которую нельзя читать как подтверждённую. `input-status` отказывает
при intent; следующий `sync-input --apply` под блокировкой проверяет сохранённое
поколение и завершает именно тот intent. Подтверждение идёт только после
проверки нового полного каталога. Прежний каталог сохраняется до commit C.
Повреждённый intent, несовпавшие байты или конфликт CAS не сбрасываются.

Ошибка fsync после фактически выполненного rename/commit означает неизвестный
результат. Повтор сначала читает действительное состояние: уже записанный
sequence/evidence распознаётся идемпотентно. Самостоятельно удалять intent,
обнулять `revisions.json` или подменять файлы для продолжения нельзя.
`input-status` работает без Anki, проверяет receipt, физические байты и C;
возвращает только идентичности, хеши, sequence и evidence, без содержимого
карточек или media. Он не инициализирует хранилище и не выполняет recovery.
Перечень каталогов
должен точно соответствовать потокам `revisions.json`; внутри подтверждённого
потока допустимы только `current` и `receipt.json`. Неучтённые каталоги,
лишние файлы и отсутствующие потоки дают отказ без удаления найденных данных.

Каждое **новое живое подтверждение** увеличивает `source_sequence` данного
потока. При прежнем семантическом снимке `revision` остаётся прежним,
`content_changed=false`. Физическое изменение определяется отдельно по полному
inventory: `files_changed=true` означает замену поколения, в том числе при
изменении или удалении `import_config.yaml` без изменения ревизии. Если весь
inventory совпадает, `files_changed=false`: файлы JSON/media сохраняют inode.
При замене поколения неизменные JSON/media также копируются в новое поколение.
Evidence нового job связывается с той же семантической ревизией и inventory
живого экспорта; receipt описывает фактически сохранённые байты. Для прежних
намерений без `files_changed` сохраняется прежнее правило восстановления,
но хеш inventory в свидетельстве также обязан совпадать. Старый журнал с
противоречивым inventory даёт отказ и сохраняется для восстановления. Повтор
**того же job** не увеличивает sequence. A, B и published этим не меняются.

## Исходы и повтор

`--json` возвращает исход каждой выбранной колоды. Для `published` доступны
`identity`, `revision`, `source_sequence`, `job_id`, `evidence`,
`input_directory`, `inventory`, `content_changed`, `files_changed` и `input_confirmed=true`.
Успешное завершение всей группы — `succeeded`, код 0; неполный пакет —
`partial`, код 6. Отсутствующая колода имеет `deck_not_found`; прежний снимок
не удаляется. Если с прежним именем связан pending, CLI опрашивает его и
возвращает `pending_export_source_missing`, `pending_jobs` с ID и результатом
опроса, а также `anki_export_may_have_completed=true`. Удаление или
переименование колоды не доказывает, что прежняя отправка не выполнялась.
Подтверждение и новая отправка при этом запрещены, pending сохраняется.
Другие выбранные колоды продолжаются независимо.

`export_wait_timeout` (предел ожидания задаёт `--wait-seconds`, 1–3600),
потеря связи и неопределённый admission сохраняют ID. Повторите **ту же
команду**: сначала будет опрошен этот job. Новый ID вслепую не назначается.
`prepared` допускает отправку того же ID только при совпадении процесса,
который его наблюдает, с исходным процессом Anki. Перед HTTP владелец надёжно
сохраняет `admission_started=true`; новое явное применение может продлить ещё
не использованный ticket на 600 секунд. Если Anki перезапущена до сохранения
намерения отправки, отсутствие отправки доказано и следующий вызов обновит
источник. Если намерение уже было сохранено, а result после рестарта отсутствует,
`prepared` не доказывает, что операция не исполнялась: CLI сохраняет ID и выдаёт
`export_completion_unknown_after_restart`, не создавая новый export. Нужно
проверить `anki job ID` и восстановить проверенное свидетельство из сохранённого
spool/backup; обнуление pending не является восстановлением. Старый журнал без
поля намерения трактуется как неопределённый, а не как «никогда не отправлялся».
Доказанный отказ до HTTP или `anki_busy`/`addons_not_ready` до принятия
первой отправки надёжно возвращает `admission_started=false` в том же pending.
После рестарта этот ID можно безопасно заменить по правилу неотправленного
задания. Если раньше уже была неопределённая отправка, новый отказ её не
отменяет. `unknown`, `consumed_ticket` и внутренний API-сбой не считаются
доказанным отсутствием принятия; ошибка сохранения признака также не скрывается.

Доказанные `failed`, `cancelled` и `interrupted` завершают
попытку; следующий явный вызов создаёт новое задание.

Окончательно невалидные inventory, структура или физические байты живого
`succeeded` завершают попытку только после надёжного сохранения записи отказа
в `.owner.json`: ID, исходный источник и класс причины. Ответ содержит
`attempt_closed=true` и `job_id`, а `input-status` — `rejected_jobs` с ID и
причиной без содержимого карточек. Spool не удаляется. Следующий **явный**
вызов создаёт новое задание; в том же вызове повторной отправки нет.
Недоступность Anki, ошибка чтения файлов или записи отказа не доказывают
окончательный отказ и сохраняют pending. При несовпадении исходного имени,
числового ID или известного UUID выдаётся `pending_export_identity_mismatch`;
восстановите исходный источник и опросите прежний ID. Переход от отсутствующего
UUID к впервые назначенному CrowdAnki UUID допустим.

После частичного успеха новый вызов снова подтверждает уже завершённые колоды
новыми живыми jobs, а неразрешённые продолжает по прежним ID. Anki может
изменяться между jobs: пакет не является транзакцией всей коллекции, каждый
снимок относится к собственному моменту экспорта. Переименование/смена UUID
или источника незавершённой операции не подменяют её молча.

`input_state_corrupt`, `input_unsafe_path`, `input_cas_conflict`,
`input_durability_failure` и `input_recovery_required` означают, что нельзя
объявить публикацию завершённой. Сохраните журнал, восстановите правильное
расположение/права или проверенную резервную копию, затем повторите применение.
Содержимое заметок, JSON и байты media в диагностике не печатаются.

## Границы и ограничения

Оригинальный CrowdAnki при экспорте меняет UUID/метаданные Anki и может создать
backup. Ошибка последующей публикации не откатывает эти изменения. В отчёте
успех Anki и `input_confirmed` различаются. Его Desktop spool сохраняется
отдельно по прежнему контракту jobs; это не история снимков внутри `input`.

Реализация рассчитана на Linux CLI и файловую систему с рабочими dirfd,
`renameat2(NOREPLACE)`, flock и fsync каталогов. В WSL данные Anki берутся через
существующее отображение Windows-путей; гарантии публикации требуют такой же
поддержки FS назначения. Ошибки этих операций не заменяются успешным ответом.
Native Windows Rust CLI и перенос базы Anki не реализованы.

Приватность 0700 и принадлежность UID требуются также для `toolkit-desktop`
со spool внутри выбранной базы Anki. В WSL DrvFS без `metadata` это нельзя
доказать по Unix-правам; такой режим не поддерживается и получает
`export_spool_not_private` до создания билета/отправки задания. Нужны реально
проверяемые права и поддержка файловых операций; проверка не заменяется
доверием к виртуальным правам или непроверенным Windows ACL. Контракт не
обещает поддержку произвольной конфигурации DrvFS.

Один файл ограничен 256 MiB, полный экспорт — 1 GiB и 16 384 файлами media.
Проверка держит полные байты в памяти. Это проверка корректности, без заявления
об ускорении. Процесс с тем же UID всё ещё может менять Anki или файлы напрямую;
границы API и advisory-блокировки не являются изоляцией от такого процесса.

Обычные `inspect`/`find`/`edit`/`create`/`validate`/`visual-report` и остальные
команды по-прежнему не получают доступа к `input`, в том числе через ссылки,
`..` и alias. `--repository` нельзя направить внутрь `input`. Произвольного
`--source` или `--allow-input` у доверенного владельца нет. Экспорт не переносит
данные в `output`, не импортирует их в Anki, не разрешает конфликты A/C/B,
не удаляет колоды и не устанавливает фоновый сервис.
