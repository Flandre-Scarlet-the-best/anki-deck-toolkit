# Управляемый цикл input ↔ output ↔ Anki

Владелец — закрытый модуль `anki_repo::desktop::input` (подмодули `prepare`,
`publication`, `work`) и команды `anki-repo anki prepare-output`,
`publish-output` и `exchange-status`. Он соединяет уже существующих владельцев:
[доверенный экспорт](input-export.md) (`sync-input`, `input-status`),
[exchange](exchange.md) (решения A/C/B и происхождение) и
[Desktop](desktop.md) (оригинальные CrowdAnki exporter и importer). Новой схемы
идентичностей, ревизий или второго хранилища истины нет. Все изменения — только
по явной команде пользователя; фонового синхронизатора нет.

## Обычный цикл

```bash
# 1. Подтверждённый живой экспорт в закрытый input (см. input-export.md)
anki-repo anki --profile 'Профиль' sync-input --deck 'Колода' --apply

# 2. Состояние обмена: адрес output, ревизии A/C/B, решение и незавершённые операции
anki-repo --json anki exchange-status

# 3. План подготовки без записи, затем применение
anki-repo anki prepare-output --output '<каталог из exchange-status>'
anki-repo anki prepare-output --output '<каталог>' --apply
anki-repo anki prepare-output --all --apply

# 4. Правка рабочей копии штатными командами (edit/create/retire …)
anki-repo edit decks/output/<каталог> --guid G --field Поле --set 'значение' --apply

# 5. План импорта без Anki и без записи, затем проверенный импорт
anki-repo anki --profile 'Профиль' publish-output --output '<каталог>'
anki-repo anki --profile 'Профиль' publish-output --output '<каталог>' --apply
```

`--output` принимает только каталог уже зарегистрированной привязки
(`decks/output/<имя>__<SHA-256 идентичности>`, как его показывает
`exchange-status`); префикс `decks/output/` допустим. Выбор по имени колоды,
уровню JLPT, модели или пути вне привязки не выполняется. Каждая колода пакета
получает собственный исход; общий `succeeded` (код 0) означает, что все
выбранные колоды завершились разрешённо, иначе `partial` (код 6).

## Подготовка output

`prepare-output` без `--apply` показывает решение `plan_preparation`, причину
блокировки, C/A/B, сравнение (только адреса и признаки конфликта, без значений
полей), ожидаемые изменения и следующий шаг. Он не создаёт каталогов.
`input-status` остаётся аудитом и не копирует данные.

| Решение exchange | Что делает `--apply` |
| --- | --- |
| `prepare_first` | создаёт рабочую копию из подтверждённого C |
| `refresh_unchanged` | заменяет неизменённую с момента базы рабочую копию свежим C |
| `keep` | ничего не переписывает и базу не продвигает |
| `blocked` | ничего не меняет; показывает причину и следующий шаг |

Блокировки (`untracked_output`, `working_missing`, `stale_or_unproven_base`,
`input_unproven` и др.) не имеют режима overwrite, force или merge: существующий
каталог без базы не присваивается даже при совпадении байтов, двусторонние
изменения требуют отдельного явного согласования.

Переносится **полный** экспорт: `deck.json`, `media/` и, если есть,
`import_config.yaml`. Каждый файл копируется потоково (буфер 1 MiB) с проверкой
SHA-256 по инвентарю подтверждённого receipt, затем семантический снимок копии
сверяется с C. Неизвестные JSON-ключи и байты не меняются. Доступ к `input`
выдаётся только этому владельцу узким методом `confirmed_source` под
блокировкой владельца input; обычные команды по-прежнему не читают `input`.

`import_config.yaml` не входит в семантическую ревизию. При `keep` его
расхождение с C показывается в `physical_differences` без перезаписи. При
`refresh_unchanged` отличающийся YAML рабочей копии даёт
`working_import_config_differs`: иначе его байты были бы потеряны. Посторонние
файлы в рабочей копии дают `unexpected_export_entries` и не удаляются.

Повторная подготовка идемпотентна: при `keep` файлы не переписываются (inode
сохраняется), новый `source_sequence` при том же снимке базу не продвигает.

### Протокол и восстановление

1. Под блокировкой владельца input (`input_busy` при занятости) — свежий план и
   доверенный C; ревизия C обязана совпасть с планом.
2. Полная копия в приватный `decks/.roundtrip/<ключ>/stage` и её проверка.
3. Надёжный intent `prepare.json`: C, инвентарь, прежняя ревизия и инвентарь B.
4. Под `write::ExportLock` рабочей копии B перечитывается без вложенных
   блокировок; изменение после плана — `working_changed_since_plan`. B уходит в
   `previous`, `stage` переименовывается в рабочую копию (`renameat2` без замены,
   fsync каталогов). Ожидающий `edit`/`create` после замены получает
   `export_directory_changed`.
5. `ExportLock` отпускается, затем `ExchangeStore::record_prepared` того же плана
   (порядок блокировок exchange → экспорт не нарушается).
6. Удаляются `previous` (только если его байты равны записанному инвентарю) и intent.

План exchange не сериализуется, поэтому после остановки процесса между шагами 3
и 5 повторный `--apply` **откатывает** только доказанно собственные перемещения
(рабочая копия возвращается в `stage`, только если её байты равны инвентарю
intent; `previous` возвращается на место) и выполняет подготовку заново. Если
база уже записана, остаётся уборка шага 6. Правка рабочей копии в окне между
переключением и фиксацией базы даёт `working_changed_after_swap`: intent,
`previous` и новая рабочая копия сохраняются для ручного разбора. Неизвестные
объекты в `decks/.roundtrip` дают `unknown_work_entries` и не удаляются;
symlink, hardlink, FIFO и выход через `..` отвергаются общими dirfd-проверками.

## Проверенный импорт

`publish-output` без `--apply` не обращается к Anki: показывает разрешение
`plan_publication`, сравнение A→B и ожидаемое действие пользователя. Если B
равен C — `nothing_to_publish`.

С `--apply` для каждой колоды:

1. Профиль Anki обязан иметь тот же `ProfileId`, что идентичность потока
   (`profile_mismatch`), колода ищется по корневому CrowdAnki UUID.
2. `plan_publication` (A == C, совместимый B).
3. **Проверка актуальности Anki:** свежий живой экспорт той же колоды тем же
   доверенным путём, что `sync-input`. Его результат сохраняется как новый C.
   Если живая Anki изменилась относительно C, на котором основан B, повторный
   `plan_publication` отказывает и возвращается `anki_changed_since_input`:
   импорт не отправляется, изменения пользователя в Anki сохранены как C,
   следующий шаг — `prepare-output`. Старые `revisions.json` и `doctor`
   доказательством актуальности не считаются.
4. B копируется под `ExportLock` в приватный spool Desktop и сверяется с
   ревизией разрешения; ticket импорта связан с `ProfileId`.
5. Журнал `decks/.roundtrip/<ключ>/publish.json` надёжно сохраняется **до** HTTP,
   включая признак начатой отправки.
6. Оригинальный CrowdAnki importer (`toolkitImport`) показывает штатный диалог.
   CLI ждёт до `--wait-seconds` (1–3600, по умолчанию 600) и не нажимает кнопки.
7. **Readback** — новый живой экспорт той же колоды того же профиля, с полной
   проверкой JSON, UUID/GUID, моделей, семантического снимка и физических media.
8. Readback == B: тот же протокол публикации input (stage → intent → current)
   завершается `ExchangeStore::record_published` с заново выданным и
   сверенным с журналом разрешением. Только тогда исход `published`.

### Исходы

| Исход | Значение |
| --- | --- |
| `published` | readback совпал с B; exchange, receipt и `input/current` описывают одну ревизию |
| `nothing_to_publish` | B уже равен C |
| `blocked` | `publication_blocked`, `anki_changed_since_input`, `profile_mismatch`, `deck_not_found_in_anki`, `freshness_unconfirmed` и др.; импорт не отправлялся |
| `import_not_submitted` | доказано, что импорт не отправлен (отказ до admission или рестарт до отправки) |
| `pending` | `import_awaiting_user` (ответьте на диалог), `import_submission_unknown`, `import_status_unknown`, `readback_unconfirmed`: повторите ту же команду |
| `import_not_applied` | readback равен прежнему C: `import_cancelled`, `import_failed` или неприменённый импорт |
| `readback_mismatch` | фактическое состояние Anki отличается и от B, и от прежнего C |
| `import_applied_unconfirmed` | Anki совпала с B, но рабочая копия изменилась до фиксации |

Во всех исходах кроме `published` флаг `published` не устанавливается. Readback,
отличный от B, сохраняется доверенным путём как новый C (`record_input`), B не
трогается, в ответ попадают только адреса различий. Например, CrowdAnki **не
удаляет** из Anki заметку, отсутствующую в JSON: её удаление в B даёт
`readback_mismatch`, а не ложный успех.

### Повтор и восстановление

Повтор той же команды сначала завершает незавершённые intent input (`recover`),
затем продолжает журнал: опрашивает **тот же** job. Импорт повторно не
отправляется вслепую:

- `prepared` в том же процессе Anki — отправки не было, допустима отправка того
  же ID с продлением ticket;
- `prepared` после рестарта: без признака начатой отправки — `import_not_submitted`,
  с ним — исход неизвестен, судьбу определяет readback (без повторного импорта);
- `failed`/`cancelled`/`interrupted` и неизвестный исход также завершаются
  readback, который фиксирует фактическое состояние Anki.

Если exchange уже содержит подтверждение именно этой попытки (сбой после
фиксации, до уборки журнала), повтор возвращает `published` с `recovered: true`.
Пока журнал публикации существует, `sync-input` этой колоды отказывает с
`publication_pending`, а `prepare-output` — тоже: свежий C сделал бы разрешение
устаревшим до проверки readback.

Если фиксация readback прервана между файлами input, exchange и receipt,
следующий вызов (`publish-output --apply` или `sync-input --apply`) завершает
intent input. Разрешение выдаётся заново и обязано совпасть с журналом
(ревизия B, номер проверенного C и базы); если B изменился, readback
сохраняется как наблюдённый C без `published` (`publication_confirmed=false`).
Состояние, в котором метаданные считают B опубликованным, а `input/current`
содержит старый экспорт, протоколом исключено: `record_published` вызывается
только после проверки нового `current`.

## Пользовательский сценарий

V1 из Anki → `prepare_first` → агентская правка V2 → `publish-output --apply`
(`published`, A == C == V2) → правка пользователя в Anki V3 → `sync-input` →
`prepare-output` даёт `refresh_unchanged`, если рабочую копию не правили после
базы. Одновременные изменения Anki и output, разные правки одной заметки и
несовместимая модель остаются `blocked`; автоматического слияния нет.

## Границы

- Удаление заметок, колод и автоматическая миграция моделей не выполняются;
  несовместимые изменения модели отклоняются до импорта
  (`*_requires_manual_import`).
- Импорт создаёт backup коллекции средствами CrowdAnki; ошибка может оставить
  частичные изменения (`partial_changes_possible`), которые фиксирует readback.
- Вывод не содержит содержимого карточек, путей spool, credential/capability и
  байтов media; только идентичности, ревизии, адреса различий, `job_id`.
- Рабочая область `decks/.roundtrip/` содержит не более одного `stage`,
  `previous` и журналов на колоду, без истории копий; игнорируется Git вместе
  с `decks/`.
- Проверка держит в памяти только `deck.json` и один файл media за раз; лимиты —
  256 MiB на файл и 1 GiB на экспорт, как у владельца input.
- Это граница программного владения, а не OS-level изоляция от процессов того же
  пользователя.

## Проверки

Синтетические unit-тесты (`cargo test -p anki-repo --lib desktop::input`) без
Docker и пользовательских данных проверяют матрицу подготовки, сбои на каждой
границе, гонку с `ExportLock`, журнал импорта, решения по readback и фиксацию
публикации. Живой полный цикл — сценарий `roundtrip` E2E-стенда
([anki-e2e](../anki-e2e/README.md)), запускается только вручную.
