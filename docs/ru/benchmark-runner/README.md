# Исполнитель бенчмарков: `benchmark-runner`

**Русский** · [English](../../en/benchmark-runner/README.md) · [简体中文](../../zh-CN/benchmark-runner/README.md)

`benchmark-runner` — CLI для Linux, который запускает сценарии каталога
`benchmarks/` по ID и профилю, измеряет цель через Hyperfine 2.0, добавляет
системные метрики Linux (cgroup v2, `/proc`, машинный отчёт модуля, файловая
система) и записывает результат в формате `benchmark-contract`. Результат
проверяется `benchmark_contract::result::check` вместе с каталогом до того, как
будет принят; непрошедший проверку результат финальным не становится.

Смысл полей сценария, профилей и метрик — [руководство по
каталогу](../../docs/performance/benchmarks.md); схемами каталога и результата
владеет [`benchmark-contract`](../benchmark-contract/README.md); общие правила
замеров — [методика](../performance/README.md); измерения самого
исполнителя — [страница производительности](performance.md);
локальная история результатов — [`benchmark-history`](../benchmark-history/README.md).

Исполнитель не меняет пользовательские экспорты и профили Anki, не читает
`decks/input/`, не вызывает `sudo`, не чистит кэши Docker (`docker system prune`
и подобное) и не отправляет данные в сеть сам. Принятый результат он передаёт в
локальную историю пользователя (см. ниже), но сам её не ведёт.
Пути к пользовательским данным он получает только параметрами запуска.

## Команды

```bash
cargo run -p benchmark-runner -- list
cargo run -p benchmark-runner -- check anki-repo.validate --profile warm --param export_dir=/path/to/export
cargo run -p benchmark-runner -- run anki-repo.validate --profile warm --param export_dir=/path/to/export
cargo run -p benchmark-runner -- run anki-repo.validate --profile warm --param export_dir=/path/to/export --runs 20 --output validate-warm.json
cargo run -p benchmark-runner -- check anki-e2e.smoke --profile warm --runs 2
cargo run -p benchmark-runner -- --json run anki-e2e.smoke --profile warm --runs 2
```

| Команда | Что делает |
|---|---|
| `list` | исполняемые сценарии: ID, вид, профили, допустимое число прогонов; учебные `example` не показываются |
| `check <id> --profile P` | реальная готовность окружения к серии: Hyperfine и его метрики пробным запуском, исполняемые файлы, демон Docker, cgroup v2 и делегирование, `perf_event`, сеть, офлайн-изоляция; для каждой метрики — будет ли она измерена и почему нет. Ничего не собирает и не запускает цель |
| `run <id> --profile P` | полная серия и проверенный результат |

Параметры `check` и `run`:

| Параметр | Смысл |
|---|---|
| `--param <имя>=<значение>` | значение объявленного параметра; неизвестное имя, значение вне `choices` и пропуск обязательного — ошибка использования |
| `--runs N` | число измеряемых прогонов; по умолчанию `min_runs`. Для `long-e2e` обязательно: долгая серия никогда не выбирается неявно. Диапазон — от `min_runs` (или 1 при `single_run_allowed`) до `max_runs` |
| `--no-sampling` | не опрашивать `/proc` и cgroup во время прогона; сэмплируемые метрики станут `unavailable` с причиной. Группа контейнера наблюдается только во время прогона, поэтому для сценария с `container` недоступны все метрики `cgroup`, а обязательная из них даёт итог `unsupported` |
| `--output FILE` | файл результата (только `run`); существующий файл не перезаписывается |
| `--artifacts-dir DIR` | корень артефактов (только `run`); по умолчанию `target/benchmark-runner` репозитория |
| `--build-timeout S` | предел сборки каждого `cargo-bin`, секунд (только `run`), по умолчанию 3600 |
| `--no-history` | не сохранять принятый результат в локальную историю (только `run`) |

Глобальные параметры: `--catalog DIR` — каталог с `catalog.toml` (по умолчанию
`benchmarks/` ближайшего родителя текущего каталога); `--json` — машинный JSON
в stdout. Ход серии всегда пишется в stderr и в `runner.log`.

## Коды возврата

| Код | `exit` | Значение |
|---|---|---|
| `0` | `success` | все прогоны успешны, результат принят; `check` — серия может измеряться |
| `1` | `partial` | результат принят, но серия неполна: прогон не удался после успешного, исчерпан бюджет, обязательная метрика неполна, прогонов меньше `min_runs` или не удалась уборка |
| `2` | `usage` | неверные аргументы, неизвестный сценарий или параметр, учебный сценарий, существующий `--output` |
| `3` | `error` | внутренняя ошибка или недоступный каталог; результат не записан. Если после серии не удалась запись принятого результата в итоговый файл, его копия сохраняется как `result.unwritten.json` в артефактах |
| `4` | `failure` | результат принят, успешных прогонов нет (в том числе отказ `setup`) |
| `5` | `unsupported` | окружение не позволяет честно измерить серию (нет Hyperfine 2.x, обязательной метрики, Docker, изоляции сети); результат с этим итогом записан, прогонов нет; `check` — то же без записи |
| `6` | `interrupted` | серия прервана сигналом; записанные прогоны сохранены, уборка выполнена |
| `7` | `busy` | серия того же модуля уже идёт |
| `8` | `rejected` | собранный результат не прошёл проверку контракта; он сохранён как `result.rejected.json` в артефактах, финального файла нет |

С `--json` команда `run` печатает сводку: `ok`, `exit_code`, `exit`,
`scenario`, `profile`, `outcome`, `reason`, `result`, `artifacts`, `runs`,
`successful_runs`, `cleanup`, `history`, `warnings`, `diagnostics`. Та же сводка
лежит в `summary.json` каталога артефактов.

## Локальная история

После записи принятого результата `run` передаёт его в локальную историю
[`benchmark-history`](../benchmark-history/README.md) тем же контрактом и
каталогом, без повторного измерения: `BENCHMARK_HISTORY_DIR`, иначе каталог
данных XDG пользователя. Хранилище внутри рабочей копии отвергается. Поле
`history` сводки: `status` — `archived`, `already-archived`, `disabled`
(`--no-history`), `failed` (с `reason`) или `not-recorded` (принятого результата
нет), и `id` записи. Хранилище, занятое другой командой `benchmark-history`, исполнитель ждёт не дольше 10 секунд, после чего сохранение — `failed`. Отказ истории не удаляет результат и не меняет код
возврата серии, но печатается предупреждением и попадает в `warnings`; результат
можно сохранить позже командой `benchmark-history import`.

## Установка Hyperfine 2.0

Нужен Hyperfine 2.x: экспорт `schema_version = 2`, режим без shell (`-N`) и
`--metrics`. Hyperfine 1.x исполнитель распознаёт по версии и честно отказывает
с кодом `5`. Если пакет дистрибутива старше, подойдёт статический релиз:

```bash
curl -fsSLO https://github.com/sharkdp/hyperfine/releases/download/v2.0.0/hyperfine-v2.0.0-x86_64-unknown-linux-musl.tar.gz
sha256sum hyperfine-v2.0.0-x86_64-unknown-linux-musl.tar.gz
tar -xzf hyperfine-v2.0.0-x86_64-unknown-linux-musl.tar.gz
install -D -m 0755 hyperfine-v2.0.0-x86_64-unknown-linux-musl/hyperfine ~/.local/bin/hyperfine
hyperfine --version
```

Сверьте сумму с digest на странице релиза; CI устанавливает этот же архив с
закреплённой суммой. Счётчики процессора (`instructions`, `cpu_cycles`…)
требуют доступа к `perf_event` (обычно `kernel.perf_event_paranoid ≤ 2` для
своих процессов): без него Hyperfine их не экспортирует, а метрики становятся
`unsupported`.

## Порядок серии

1. Выбор сценария, профиля, параметров и числа прогонов; блокировка модуля
   в самой рабочей копии (`target/benchmark-runner/locks/<модуль>.lock`).
   От `--artifacts-dir` она не зависит: серии одного модуля одной рабочей
   копии исключают друг друга при любых каталогах артефактов и любом пути к
   ней, а независимые рабочие копии не мешают друг другу.
2. Проверка готовности; при блокерах — итог `unsupported` без прогонов.
3. Подготовка: снимок происхождения кода (коммит, признак изменений,
   `source_tree_sha256`), сборка `cargo-bin` (`cargo build --locked`),
   разрешение исполняемых файлов из `PATH`, идентичность и объём входов, затем
   повторный снимок. Если рабочая копия за подготовку изменилась или
   идентичность `repo-tree` расходится со снимком, серия не измеряется (итог
   `failure`). Подготовка не входит в измерение и в бюджет серии.
4. `setup` сценария, затем `setup` профиля.
5. Прогревы: `prepare` → цель → `conclude`; значения не сохраняются.
6. Измеряемые прогоны: `prepare` → **цель** → `conclude`.
7. `cleanup` сценария — всегда, после успеха, отказа и прерывания.

Шаги жизненного цикла исполнитель выполняет сам по argv без shell, каждый в
своей группе процессов и со своим `timeout_seconds`. Цель измеряет Hyperfine:
отдельный вызов `-N --runs 1 --export-json` на каждый прогон, потому что
Hyperfine 2.0 при отказе посреди серии не пишет экспорт вовсе. Аргументы цели
подставляются один раз (`{param.*}`, `{input.*}`, удвоенные скобки — литерал),
окружение цели — только `env.inherit` и `env.set` декларации. Вывод цели
`short-cli` отбрасывается, вывод `long-e2e` сохраняется в артефактах.

Таймаут шага, `run_timeout_seconds` прогона и `total_budget_seconds` серии
соблюдаются жёстко. Бюджет отсчитывается от начала `setup` и охватывает
`setup`, прогревы, прогоны с их `prepare` и `conclude`. Вне бюджета остаются
подготовка (её ограничивают `--build-timeout` на каждый `cargo-bin` и
`timeout_seconds` проб входов) и `cleanup`, которая выполняется и после
исчерпания бюджета, ограниченная `timeout_seconds` каждого своего шага.
Поэтому верхняя граница работы исполнителя — сумма этих пределов, а не один
`total_budget_seconds`. Завершение ступенчатое: SIGINT, затем SIGTERM, затем
SIGKILL всей группы процессов. Исполнитель становится subreaper, поэтому
потомок, покинувший группу, всё равно найдётся и будет убран; такой
«сбежавший» процесс делает прогон неуспешным, а в прогреве останавливает
серию. Шаг жизненного цикла, после успешного выхода которого остались его
процессы, тоже не считается выполненным: потомков завершает уборка посреди их
работы, и эффект шага не доказан. Такой `setup`, `prepare` или `conclude`
останавливает серию, такая `cleanup` делает уборку неполной.

Неуспех прогона (неожиданный код, таймаут, остаток процессов) прекращает
серию. Итог — `partial`, если до этого был успешный прогон, иначе `failure`.
Неудачная уборка понижает `success` до `partial` и отражается в `cleanup`.

## Сигналы и отмена

Первый SIGINT, SIGTERM или SIGHUP прерывает текущий шаг или прогон и
останавливает серию; уборка `cleanup` после этого всё равно выполняется.
Второй сигнал прерывает и уборку. Прерванный прогон записывается со статусом
`interrupted`, код возврата — `6`. Финальный файл пишется атомарно (временный
файл и жёсткая ссылка): частичного результата нет, существующий файл не
перезаписывается.

## Метрики Linux и их охват

| Источник | Как собирается | Охват |
|---|---|---|
| `hyperfine` | экспорт Hyperfine каждого прогона | процесс цели и дождавшиеся потомки |
| `procfs` / `host` | опрос `/proc/stat` и `MemAvailable` во время прогона | вся система: наблюдение хоста, не граница — включает чужие выделения и смещается одновременными освобождениями |
| `cgroup-v2` / `cgroup` без контейнера | своя подгруппа на каждый прогон, `cpu.stat`, `memory.peak` | цель, все её потомки и сам процесс Hyperfine; средняя загрузка — процессорное время группы за время её жизни |
| `cgroup-v2` / `cgroup` с `container` | cgroup контейнера Docker, найденная во время прогона | процессы контейнера |
| `module-report` | машинный отчёт модуля, появившийся за этот прогон | значения по JSON Pointer декларации |
| `filesystem` | размер пути после прогона | только названный путь |

Отчёт модуля относится ровно к одному прогону: это единственный новый каталог
в `runs_dir`, появившийся за этот прогон. Если декларация берёт из отчёта
идентичность или объём входа, каждый прогон обязан подтвердить их своим
отчётом: без нового, разбираемого и полного отчёта прогон — `failure`, даже
если прошлые прогоны вход уже записали. Изменение идентичности или объёма
между прогонами — тоже `failure`. Отчёт, из которого берутся только
необязательные метрики и факты, может отсутствовать: метрика тогда неполна,
а прогон остаётся успешным.

Отсутствующее значение никогда не записывается нулём: метрика становится
`unavailable` или `unsupported` с причиной. Метрики, для которых в
репозитории нет машинного источника (например, `phase_duration` при
человекочитаемом журнале модуля), — `unsupported`.

### Собственная cgroup

Для метрик `cgroup` без контейнера исполнитель создаёт подгруппу на каждый
прогон. Создавать подгруппы без root можно только в делегированной группе,
поэтому `run` при необходимости перезапускает себя через
`systemd-run --user --scope -p Delegate=yes` (команда выполняется на месте, без
отдельного сервиса) и переносит себя в подгруппу `benchmark-runner`, чтобы
соблюсти правило cgroup v2 «нет внутренних процессов». Если пользовательского
systemd или делегирования нет, необязательные метрики становятся
`unsupported` с причиной, а обязательные — итог `unsupported`.

В группу прогона переносится процесс Hyperfine до начала измерения, а не цель:
перенос процесса между группами перед созданием потоков стоит около 17 мс
ожидания ядра и исказил бы время цели. Поэтому значения группы включают
небольшие накладные расходы самого Hyperfine (несколько миллисекунд процессора
и около 1 МиБ памяти), что отражено в описании охвата.

### Контейнер Docker

Если сценарий объявляет `container`, исполнитель во время прогона ищет
контейнер по метке декларации и принимает его только тогда, когда PID
создателя из метки `owner_pid_label` — потомок текущего прогона, а путь cgroup
процесса контейнера содержит его ID. Чужие контейнеры с той же меткой не
приписываются. Проверка готовности (`check`, требование `docker`), факт
`docker_version` и опрос контейнера вызывают Docker CLI только с окружением
цели (`env.inherit` и `env.set` декларации): `DOCKER_HOST`, `DOCKER_CONTEXT` и
`DOCKER_CONFIG` исполнителя, которых цель не получила, не направят их к
другому демону. Если демон цели недоступен, серия — `unsupported`, даже когда
демон исполнителя отвечает. Значения — последнее наблюдение перед удалением контейнера:
scope systemd удаляется сразу после его выхода. Время процессора Hyperfine для
такого сценария охватывает только процессы на хосте, а не контейнер.

### Офлайн-профиль

Офлайн-профиль запускается, только когда изоляция действительно обеспечена:
цель выполняется в отдельном пространстве имён сети
(`unshare --user --map-current-user --net`), а проба подтверждает, что
доступен только `lo`. Демон Docker и BuildKit этой изоляцией не охватываются,
поэтому офлайн-профиль сценария, требующего `docker`, — итог `unsupported`.
Без пользовательских пространств имён — тоже `unsupported`.

### Влияние сэмплера

Опрос `/proc` и cgroup идёт только во время измеряемого прогона, раз в
`sample_interval`. Измерения влияния на время цели —
[страница исполнителя](performance.md);
`--no-sampling` полностью отключает опрос.

## Что публикуется

Результат содержит ID и ревизию сценария, профиль, записываемые параметры,
идентичность и объём входов, факты окружения и provenance: коммит, признак
изменений рабочей копии, `source_tree_sha256` и версии исполнителя и
Hyperfine. Коммит, признак изменений и `source_tree_sha256` — снимок,
подтверждённый до измерений, из которого собраны программы и вычислена
идентичность `repo-tree`, а не состояние после серии. Git для снимка
вызывается без унаследованных переменных, привязывающих его к другому
репозиторию (`git rev-parse --local-env-vars`: `GIT_DIR`, `GIT_WORK_TREE`,
`GIT_INDEX_FILE` и другие), поэтому запуск из Git-хука не подменяет
происхождение чужим коммитом или индексом. После уборки снимок
сверяется ещё раз: если отслеживаемые или неигнорируемые файлы либо коммит
изменились, итог не `success` (`partial` или хуже) с причиной. Игнорируемые
Git файлы (например, `target/`) в сверку не входят, поэтому временные данные
сценария не должны лежать в неигнорируемых путях после `cleanup`. Абсолютные пути, параметры с `record = false`, секреты и сырой
вывод цели в результат не попадают; причины, содержащие такие данные,
заменяются нейтральным текстом.

Каталог артефактов `<артефакты>/runs/<id>/<UTC>-<профиль>-<случайный>/`
содержит `runner.log`, `summary.json`, журналы шагов (`steps/`), экспорты и
журналы Hyperfine (`hyperfine/`), вывод цели (`output/`), сэмплы (`samples/`)
и найденные отчёты модуля (`reports/`). Артефакты могут содержать локальные
пути и вывод программ: это локальные данные прогона, их не публикуют и не
коммитят.

## Linux и WSL2

Поддерживается Linux с cgroup v2 и `/proc`; macOS и Windows не поддерживаются.
WSL2 — обычное окружение Linux: исполнитель записывает его в факт
`virtualization = wsl2`, но не опирается на Windows-пути, `/mnt/c` или Docker
Desktop. Нужны `systemd --user` для собственной cgroup, Docker с cgroup v2 для
метрик контейнера, `unshare` из util-linux для офлайн-профиля.

## Диагностика

| Симптом | Причина и что делать |
|---|---|
| `hyperfine` — `unsupported`, код `5` | нет Hyperfine 2.x в `PATH`; установите релиз 2.0 |
| счётчики процессора `unsupported` | нет доступа к `perf_event`: проверьте `kernel.perf_event_paranoid` |
| метрики `cgroup` `unsupported` | нет делегирования: проверьте `systemctl --user status` и `systemd-run --user --scope true` |
| офлайн-профиль `unsupported` | нет пользовательских пространств имён или сценарий требует Docker |
| код `7` | серия того же модуля в этой рабочей копии уже идёт (с любым `--artifacts-dir`); дождитесь её завершения |
| код `8` | результат нарушил контракт: см. `diagnostics` в сводке и `result.rejected.json` |
| прогон `failure` с остатком процессов | цель оставила процессы после выхода; они убраны, подробности в `runner.log` |
| серия остановлена: «после выхода шага остались его процессы» | шаг жизненного цикла оставил потомков; они завершены, эффект шага не доказан |
| `partial`: «рабочая копия изменилась за серию» | во время серии изменились коммит или неигнорируемые файлы; provenance описывает снимок до измерений |
| `docker` — «недоступен в окружении цели» | демон, к которому ведут `env.inherit`/`env.set` цели, не отвечает; переменные Docker исполнителя не используются |

## Проверки

Интеграционные тесты (`tests/runner.rs`) строят синтетический каталог и
модуль во временном каталоге и запускают настоящий Hyperfine с нагрузкой
`benchmark-workload`: память и CPU, порядок жизненного цикла, отказы всех
шагов и остатки процессов шагов, таймаут и SIGINT без процессов-сирот, офлайн,
собственную cgroup, отчёт модуля каждого прогона, снимок provenance и его
дрейф в рабочей копии Git, окружение Docker цели с подставным `docker`, отказ
для Hyperfine 1.x, запрет перезаписи, параллельные серии с разными каталогами
артефактов, отсутствие приватных путей в результате, факты отчёта модуля
только при согласии всех успешных прогонов и сохранение в локальную историю,
включая её отключение и отказ. Без Hyperfine 2.x они пропускаются
локально и падают в CI. `decks/**` тесты не читают. Набор входит в
`cargo test --workspace --locked`.

## Блочный ввод-вывод

`io_read_bytes`, `io_write_bytes`, `io_read_operations` и `io_write_operations`
снимаются с `io.stat` собственной делегированной cgroup или обнаруженного контейнера.
Неделегированный или не включившийся `io` не отключает CPU/RAM: включение
проверяется по `cgroup.subtree_control`, отказ — `unsupported` с причиной. Охват, единицы, атрибуция writeback,
ограничения виртуальных/многослойных устройств и ревизии деклараций —
[контракт метрик](../performance/benchmarks.md#блочный-ввод-вывод).
`benchmark-runner.calibration-io` выполняет контролируемый файловый цикл с `fsync`
и сбросом только собственных чистых страниц. Существующий файл не перезаписывается;
при принудительном уничтожении процесса он может остаться, и следующий запуск
откажет до его явной очистки владельцем.
