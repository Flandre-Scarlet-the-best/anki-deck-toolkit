# Производительность и потребление ресурсов

**Русский** · [English](../../en/performance/docs/ru/README.md) · [简体中文](../../zh-CN/performance/docs/ru/README.md)

Здесь собраны общая методика и ссылки на **последние подтверждённые показатели** производительности и
потребления ресурсов модулей репозитория: время, CPU, память, диск. У каждого
модуля — своя страница с методикой, определениями метрик и снимками по
сценариям и профилям в явно названном эталонном окружении. Эта страница задаёт
общие правила, по которым замеры делаются, хранятся и публикуются.

Снимок — свидетельство о фактическом поведении в конкретном окружении, а не
контракт, не норматив скорости для чужих систем и не порог CI. Числа из него не
закрепляются в коде, тестах и проверках: другое железо, другая ОС или другой
Docker дают другие значения.

## Где живёт история

| Что | Где | Кто видит |
|---|---|---|
| Полная история каждого замера | локальная история [`benchmark-history`](../benchmark-history/docs/ru/README.md): неизменяемый архив исходных JSON и индекс SQLite в каталоге данных пользователя | только её владелец |
| Полный отчёт задачи | неизменённый `benchmark-history report` в Gist задачи с manifest | все, по ссылке в PR |
| Публичная историческая запись | раздел `## Производительность` PR: компактная сводка сценария, базы, кандидата, результатов, выводов и существенных регрессий | все, через историю PR |
| Актуальный снимок | страницы `tools/<модуль>/performance.md`: последнее подтверждённое измерение каждой пары «сценарий × профиль» | все |

Страницы не накапливают записи всех PR: новое подтверждённое измерение
заменяет снимок той же пары, а прежние значения остаются в истории Git и в
описаниях PR. Публичный эталон — измерения владельца проекта в окружении,
описанном в снимке. У остальных пользователей свои локальные результаты; они не
правят публичные страницы автоматически, а снимок из другого окружения не
заменяет эталонный без явного подтверждения.

## Каталог сценариев и контракт результатов

Сценарии, профили условий, граница измеряемой работы и метрики с их охватом
объявляются машинно в каталоге `benchmarks/`, а результаты измерений
записываются в версионируемом JSON. Как зарегистрировать сценарий и читать
результат — [каталог бенчмарков](benchmarks.md); выполняет серии
[`benchmark-runner`](../benchmark-runner/docs/ru/README.md). Правила этой страницы
применяются и к измерениям по каталогу: точное состояние кэша каталог требует
объявить для каждого сценария, а снимок остаётся свидетельством окружения.

## Правила замера

1. **Вопрос до замера.** Сначала сформулируй, что нужно узнать (например,
   «сколько стоит повторный прогон» или «укладывается ли контейнер в лимит»), и
   выбери метрики под этот вопрос. Не собирай числа без цели.
2. **Окружение.** Фиксируй модель CPU и число потоков, объём RAM, ОС и ядро
   (включая WSL2), версии Docker, `rustc` и внешних зависимостей модуля,
   действующие лимиты (`--cpus`, `--memory`) и состояние рабочей копии (чистая
   или с изменениями).
3. **Состояние кэшей.** Каждый прогон относится к явно названному состоянию:
   - *холодный* — кэши самого модуля удалены его штатной командой;
   - *тёплый* — повтор без изменений входа;
   - *инкрементальный* — изменён только вход, который должен вызвать частичную
     пересборку.

   Точно записывай, что очищено, а что нет. Общие кэши, которыми модуль не
   владеет (например, слоевой кэш BuildKit демона или базовые образы), ради
   «полностью холодного» замера не удаляются: это затронуло бы другие проекты.
   Такой прогон помечается как холодный для модуля, но не для системы.
4. **Повторы.** Тёплое состояние измеряй минимум дважды и указывай диапазон.
   Одиночное число не сравнивай с одиночным числом другой записи.
5. **Без посторонней нагрузки.** Во время замера не запускай сборки, тесты и
   другие тяжёлые процессы. Сэмплер должен быть дешёвым: чтение `/proc` и
   cgroup раз в секунду практически не нагружает систему.
6. **Настоящая реализация.** Измеряй штатные команды модуля на штатной сборке,
   а не упрощённую копию. Отключать проверки, кэши или уборку ради лучшего
   времени нельзя.
7. **Честность.** Указывай, что не измерено. Оценку не выдавай за измерение, а
   значение окружения — за свойство кода. Оптимизация без замера, который
   показал проблему, не публикуется как улучшение.

Порядок работы агента над оптимизацией или подозрением на регрессию —
гипотеза, база прежней реализации до изменения, сопоставимая серия после
него, анализ и отчёт — описан в skill
[`performance-benchmarking`](../../../.agents/skills/performance-benchmarking/SKILL.md).
Он опирается на эти правила и на штатные `benchmark-runner` и
`benchmark-history`, не заменяя их.

## Источники и точность метрик

| Метрика | Источник | Точность |
|---|---|---|
| Время фазы | метки времени UTC в журнале модуля | секунда; `0 с` означает «меньше секунды» |
| Пик памяти процесса | `VmHWM` в `/proc/<pid>/status` | точный пик RSS процесса без потомков |
| CPU процесса | `utime`+`stime` и `cutime`+`cstime` в `/proc/<pid>/stat` | точно; потомки учитываются, только когда процесс их дождался |
| Пик памяти контейнера | `memory.peak` cgroup v2 | точный пик, который ведёт ядро |
| CPU контейнера | `usage_usec` в `cpu.stat` cgroup | точно для суммы; средние и пиковые ядра — по разностям между сэмплами |
| Пик ядер за 1 с | разность `usage_usec` соседних сэмплов | нижняя оценка: всплески короче интервала сглаживаются |
| Загрузка и память хоста | `/proc/stat`, `MemAvailable` в `/proc/meminfo` | вся система: наблюдение хоста, а не граница — включает чужие выделения и смещается одновременными освобождениями |
| Диск | `du -sb`, `docker image ls`, `docker system df -v` | размеры образов с общими слоями не суммируются |

## Как обновлять снимок

1. Выполни сценарий каталога штатным `benchmark-runner run`; принятый результат
   сам попадает в локальную историю.
2. Найди результат (`benchmark-history list`) и проверь его итог, прогоны,
   окружение и недоступные метрики (`benchmark-history show`).
3. Посмотри изменение страницы без записи:
   `benchmark-history snapshot <ID> --page tools/<модуль>/performance.md`, затем
   запиши его с `--apply`. Инструмент обновляет блок пары на трёх языках сразу и
   отказывается, если серия неполна, рабочая копия изменена, окружение отличается
   от эталонного или на странице более новое измерение.
4. Сохрани полный неизменённый `benchmark-history report` для того же результата
   в обязательном Gist с manifest. В PR оставь компактную сводку: сценарий,
   измеренные база/кандидат, ключевые числа, вывод и все существенные регрессии.

В постоянной документации нет SHA коммитов, номеров PR, абсолютных локальных
путей, идентичностей входов и имён авторов (правило
[`AGENTS.md`](../../../AGENTS.md)); эти детали — в Gist задачи, сводке PR и в локальной
истории. Снимки внутри маркеров `benchmark-snapshot` вручную не правятся.

Ручные наблюдения, записанные до появления истории, остаются на страницах
модулей с явной пометкой, что первичных JSON-результатов у них нет: их нельзя
выдавать за подтверждённый снимок и нельзя восстанавливать задним числом в
виде результатов. Их заменяет первый подтверждённый снимок той же пары или
новый раздел с ручным наблюдением, если сценария в каталоге нет. `snapshot
--apply` добавляет снимок перед якорем и разделы без маркеров не трогает, поэтому
устаревшее ручное наблюдение удаляют вручную в том же изменении, что и первый
снимок.
