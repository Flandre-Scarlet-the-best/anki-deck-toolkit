# Проверка изменений CrowdAnki JSON

Для адаптера Desktop синтетические Rust-контракты находятся в модуле `desktop`,
а Python-контракты payload — в `.github/scripts/test_desktop_bridge.py` и входят
в обычный `unittest discover` CI. Они не читают пользовательские колоды и не
подтверждают живую загрузку аддонов. Контракт диагностики и отдельной фактической
приёмки — `tools/anki-repo/desktop.md`; процедуру живых прогонов определяет
`anki-live-testing`.

## Автоматическая проверка toolkit'ом

Toolkit `tools/anki-repo` покрывает большую часть минимума ниже и позволяет не
читать JSON вручную:

```bash
# из корня репозитория — там же, где корневой Cargo workspace
cargo run --quiet --bin anki-repo -- inspect  decks/output/Words__N3
cargo run --quiet --bin anki-repo -- stats    decks/output/Words__N3
cargo run --quiet --bin anki-repo -- validate decks/output/Words__N3

# точечная правка значения поля: сначала dry-run, потом запись
cargo run --quiet --bin anki-repo -- edit decks/output/Words__N3 \
  --guid '<guid>' --field 'Значение' --expect '<было>' --set '<стало>'
cargo run --quiet --bin anki-repo -- edit decks/output/Words__N3 \
  --guid '<guid>' --field 'Значение' --expect '<было>' --set '<стало>' --apply
```

`decks/output/Words__N3` здесь — пример текущего состояния рабочей копии, а не
обязательный путь: команды работают с любым каталогом CrowdAnki-экспорта, в котором
лежит `deck.json`. Рабочие колоды живут только в `decks/output/<имя_экспорта>/`,
`decks/input/` — закрытая область будущего доверенного загрузчика, которую агент не
читает и не изменяет, а обе области игнорируются Git и в чистом clone отсутствуют.

Соответствие минимуму ниже:

- пункты 1, 3, 4, 5 (валидный JSON, разрешение `note_model_uuid`, число значений
  `fields`, разрешение `deck_config_uuid`) закрывает `validate`;
- пункт 2 он закрывает частично: проверяются тип корня и вложенных узлов,
  непустое `name` узла, наличие `deck_config_uuid` у узла, а также
  `crowdanki_uuid` у объявленных в узле `note_models` и `deck_configurations`;
- пункты 6 и 7 (неизменность `guid`/UUID и отсутствие случайных массовых
  переформатирований) `validate` закрыть не может: он анализирует один экспорт и
  не сравнивает версии между собой, для них нужен независимый diff —
  `git diff --no-index` по сохранённой копии состояния «до»: `decks/` не
  отслеживается Git, поэтому обычный `git diff` эту правку не покажет;
- `edit` закрывает пункт 7 для своей правки структурно: он пишет только
  канонический `deck.json`, требует `--expect` и проверяет перед записью, что
  изменилось ровно запрошенное число строк и что прирост размера объясняется
  длиной заменённых значений. Изменённое число строк видно в отчёте
  (`changed_lines`), а `git diff --no-index --numstat` по копии «до»
  подтверждает его независимо.
- `create` и `retire` закрывают пункт 7 так же: обе публикуют канонический
  `deck.json`, переразбирают кандидат до записи и подтверждают, что изменилась
  ровно ожидаемая поверхность (`only_notes_and_media_files_appended` /
  `only_tags_appended`), затем сравнивают коды `validation` до и после. Если
  правила явно разрешают проверенные изображения кандзи, `create` сначала
  размещает байты в `media/` и добавляет имена в `media_files`, затем публикует
  `deck.json`.

`validate` возвращает exit code `0`, если в экспорте нет ни одного issue уровня
`ERROR`, и `6`, если хотя бы один есть: проблемы содержимого — включая
`invalid_json`, `root_not_deck` и `schema_invalid` — становятся `ERROR` issues, а
не доменной ошибкой. Код `3` означает, что проверку вообще не удалось начать:
каталог экспорта недоступен, передан не каталог, нет `deck.json` или его нельзя
прочитать. Отсутствие физического media-файла — это `WARNING`, а не `ERROR`.
Полный список кодов и контракт вывода — `tools/anki-repo/README.md`.

Перед правкой зафиксируй `inspect`/`stats` (число заметок, узлов, моделей,
распределение по полям), после правки повтори и сравни. Для точечной работы с
одной заметкой используй `find --guid`, для поиска по значению поля —
`find --field <имя поля> --value <значение> [--match exact|contains]`.

### Через `qa`, `review` и `review-check`

Для поиска проблем в содержимом карточек используй `qa`, а не выборочное чтение
JSON руками:

```bash
# из корня репозитория
cargo run --quiet --bin anki-repo -- qa     decks/output/Words__N3
cargo run --quiet --bin anki-repo -- review decks/output/Words__N3 --qa-code empty_field_value
```

- `qa` детерминированно находит findings по фиксированному реестру правил
  (пустые значения, пробелы по краям, белый `<span>`, дубликаты содержимого
  заметки). Реестр: `empty_field_value`, `leading_whitespace`,
  `trailing_whitespace` (warning), `forbidden_white_span` (error),
  `duplicate_note_content` (warning). Имена полей конкретной модели в реестр не
  входят: «главное поле» — понятие модели заметок, а не CrowdAnki, поэтому у
  toolkit'а нет универсальной семантики такого правила. У `qa` своя шкала
  severity — `error | warning | info`, — и она не связана со шкалой `validate`:
  QA `error` (например, `forbidden_white_span`) означает серьёзный продуктовый
  дефект содержимого, а не структурную ошибку
  экспорта. Такой finding не делает экспорт невалидным, не меняет exit code `qa`
  (он остаётся `0`) и не блокирует `edit`. Структурные причины (неразрешимая
  модель, отсутствующий или неуникальный `guid`) остаются зоной `validate`, а
  `qa` только помечает затронутые findings полем `addressable: false` и считает
  их в `unaddressable_findings`.
- Findings правил-дубликатов описывают группу целиком: `group_size` называет
  размер группы, а `related_note_indices`/`related_guids` у `qa` перечисляют всех
  участников, **включая владельца finding**. Список `related` у `review` — это
  наоборот только *остальные* участники: владелец несёт сам finding. При
  превышении предела видно `related_truncated: true`: группа никогда не
  обрезается молча.
- `review` отдаёт компактный batch заметок по найденной проблеме. Читай batch, а
  не `deck.json`: страница ограничена по умолчанию 25 заметками, и по
  `next_offset` видно, есть ли продолжение. Отбор по `--qa-code` для правил
  групп приводит участников группы, а не только владельца finding; список
  участников ограничен `MAX_RELATED_NOTES` (20), и `related_truncated: true` в
  finding'е владельца говорит, что группа представлена не полностью; заметки
  которые нельзя адресовать, в batch не попадают и посчитаны в
  `excluded_unaddressable`: это заметки без `guid`, с пустым `guid`, с
  повторяющимся `guid` (включая все вхождения такого `guid`) и заметки, модель
  которых не разрешается, — ровно те, для которых `qa` ставит
  `addressable: false`.
- Предложения по содержимому проверяй через `review-check` до любой записи:
  у команды собственный документ предложений (`schema_version: 1`,
  `proposals[]` с `proposal_id`/`guid`/`field`/`expected`/`replacement` и
  необязательным `reason`), а не запрос `edit`. Он ничего не пишет и различает
  `valid`, `already_correct`, `already_applied`, `conflict` и `invalid`. Запрос
  для `edit` берётся из `result.edit_request` и существует только при
  `outcome: ok`, наличии эффективных предложений и правимом исходнике
  (`source_editable: true`); `proposal_id` становится `edit_id`, а `reason` в
  запрос не переносится.
- Предусловия записи (`review-check` проверяет их тем же кодом, что и `edit`):
  неканонический `deck.json`, экспорт с `ERROR` и неоднозначный порядок полей
  модели. Если исходник их не проходит, `review-check` всё равно печатает отчёт
  по предложениям, но запроса не выпускает, называет причины в
  `source_blockers`, ставит `source_editable: false` и возвращает код возврата
  этой причины (важнее итога по предложениям).
- Содержательное суждение о карточке делает внешний агент: `qa` и `review` не
  оценивают смысл, а toolkit не вызывает LLM API.

Порядок работы с содержимым: `qa` → `review` → предложения внешнего агента →
`review-check` → `edit` (dry-run, затем `--apply`) → `validate`.

### Через `edit`

Для правки значения поля существующей заметки предпочитай `edit` ручному
скрипту: он делает то же самое, но с проверками предусловий.

1. Найди заметку и её поле: `find --guid <guid>`.
2. Прогони правку без `--apply` (dry-run) и убедись, что `effective_edits`,
   `changed_lines` и выборки значений совпадают с ожиданием.
3. Выполни ту же команду с `--apply`.
4. Повтори команду: повторный запуск должен дать статус `already_applied`,
   `applied: false` и не изменить `deck.json` (иначе правка не идемпотентна).
5. Проверь `git diff --no-index --numstat` между сохранённой копией состояния «до»
   и текущим `deck.json`: изменённых строк должно быть ровно столько, сколько
   правок реально меняло значение.
6. Прогони `validate` и сравни с результатом до правки: новых `ERROR` быть не
   должно.

`edit` работает только с каноническим `deck.json` и отказывается править экспорт
с `ERROR` или с `conflicting_note_model_definition` — это ожидаемые отказы, а не
повод обходить команду вручную. Что делать с остальными отказами:

- `source_not_canonical` (3) — `deck.json` не в канонической форме. Нормализация
  файла это отдельная задача с отдельным diff, а не побочный эффект правки:
  сначала нормализуй экспорт, потом правь значение.
- `note_not_found` (4) — заметки с таким `guid` в экспорте нет: адресация правки
  неверна, а не файл. Перечитай `guid` через `find`.
- `expected_mismatch` (7) — текущее значение не совпало с `--expect`. Перечитай
  фактическое значение (`find`, `inspect`) и построй запрос заново.
- `source_changed` (7) — `deck.json` изменился между чтением исходника и заменой
  файла. Перечитай состояние и повтори по нему; см. ниже.
- `write_failed` (8) — отказ файловой системы. Менять нужно не команду и не файл,
  а причину отказа (права, место, доступность каталога).

`source_changed` — не повод перезапускать команду «на удачу»: он означает, что
`deck.json` изменился между чтением исходника и заменой файла. Сначала перечитай
текущее состояние (`find`, `inspect`), затем построй запрос заново по нему.
Публикация правки идёт под эксклюзивной блокировкой `deck.json`, поэтому два
одновременных `edit --apply` одного экспорта не могут молча потерять результат
одного из них: проигравший получает `source_changed` и должен быть повторён по
актуальному состоянию.

### Через `create`, `retire`, `migrate-media` и `visual-report`

Появление новой заметки и вывод старой из обращения проверяются тем же порядком,
что и правка: сначала схема, потом dry-run, потом запись, потом валидация.

```bash
EXPORT=decks/output/Words__N1
BEFORE=/tmp/Words__N1-before-migration

# 0. сохрани baseline для фактического отчёта «до / после»; повторный запуск
#    использует прежний снимок, а не вкладывает экспорт в каталог снимка
if [[ -e "$BEFORE" ]]; then
  if [[ ! -f "$BEFORE/deck.json" ]]; then
    echo "каталог BEFORE уже существует, но не содержит deck.json: $BEFORE" >&2
    exit 1
  fi
else
  cp -a "$EXPORT" "$BEFORE"
fi
if ! cargo run --quiet --bin anki-repo -- validate "$BEFORE"; then
  echo "снимок BEFORE не прошёл проверку; сохраните его и разберитесь с ошибкой" >&2
  exit 1
fi

# 1. фактическая схема полей: имена, порядок ord, примеры значений, шаблоны
cargo run --quiet --bin anki-repo -- models "$EXPORT"

# 2. новая заметка: dry-run, запись, переносимый результат
cargo run --quiet --bin anki-repo -- create "$EXPORT" --request create.json
cargo run --quiet --bin anki-repo -- create "$EXPORT" --request create.json --apply \
  --emit-resolved create.resolved.json

# 3. повторный запуск с тем же запросом обязан дать already_applied и не тронуть файл
cargo run --quiet --bin anki-repo -- create "$EXPORT" --request create.resolved.json --apply

# 4. вывод из обращения: тег, а не удаление
cargo run --quiet --bin anki-repo -- retire "$EXPORT" --guid '<guid>' --tag 'archived::auto' --apply

# 5. заметка обязана остаться адресуемой после вывода из обращения
cargo run --quiet --bin anki-repo -- find "$EXPORT" --guid '<guid>'

# 6. валидация и проверка формы
cargo run --quiet --bin anki-repo -- validate "$EXPORT"
cargo run --quiet --bin anki-repo -- qa "$EXPORT"

# 7. отдельное исключение: сначала dry-run, затем доказанная миграция
cargo run --quiet --bin anki-repo -- migrate-media "$EXPORT" \
  --namespace pitch_accent --key 飴 --from 飴.png
cargo run --quiet --bin anki-repo -- migrate-media "$EXPORT" \
  --namespace pitch_accent --key 飴 --from 飴.png --apply

# 8. статический отчёт по фактическим состояниям до и после записи
cargo run --quiet --bin anki-repo -- visual-report \
  --before "$BEFORE" --after "$EXPORT" --out /tmp/Words__N1-migration-report
```

Что именно проверять по отчётам:

- `create`: `notes_created`, `byte_delta`, `checks` (все применимые проверки
  обязаны быть `true`; `media_references_absent` и `only_notes_appended` отражают
  фактический план медиафайлов),
  `validation.before`/`after` — новых `ERROR` быть не должно; затем
  `git diff --no-index --numstat "$BEFORE/deck.json" "$EXPORT/deck.json"` и
  `git diff --no-index --stat "$BEFORE/media" "$EXPORT/media"`: `decks/` не
  отслеживается Git, поэтому ни `git status`, ни обычный `git diff` изменения
  внутри `media/` не показывают. Для явно
  разрешённых медиафайлов
  сверяй точные имена файлов, SHA-256 и объявления из результата `media`; без
  настроенных правил `media/` и `media_files` не меняются.
- `retire`: `notes_retired`, `checks` (все пять), `outcomes[].previous_tags` и
  `outcomes[].tags` — в тегах должен появиться ровно один новый тег, а `fields`
  заметки в diff'е меняться не должны.
- Повторный запуск `edit`, `create` и `retire` обязан быть идемпотентным:
  `already_applied` / `already_retired`, `applied: false`, файл не перезаписан.
- Для `migrate-media` dry-run сверяй доказанную идентичность с точным legacy
  filename и проверяй полный список потребителей: связанные поля заметок,
  `qfmt`, `afmt` и CSS. Любая ссылка, которую обработчик не может заявить,
  включая статического потребителя в модели, должна блокировать всю операцию.
- В отчёте `migrate-media` `legacy_media` и `legacy_declared` — снимки до команды;
  `legacy_media_exists_after` и `legacy_declared_after` — фактическое состояние
  после её завершения. `legacy_released` отмечает только действительно удалённый
  на `--apply` legacy-файл. При повторном запуске сверяй `changed: false` и
  поля фактического состояния после операции, а не считай снимок до неё итогом миграции.
- Проверяй изменения `media_files` по всему дереву `children`: объявление должно
  покрывать поддеревья всех перенесённых заметок, а неоднозначные дубли должны
  блокировать миграцию. Файл `media/<from>` может удаляться только после
  доказанной миграции и публикации нового `deck.json`.

Статический отчёт о различиях двух состояний собирается командой `visual-report`:

```bash
cargo run --quiet --bin anki-repo -- visual-report \
  --before /path/to/эталон --after "$EXPORT" \
  --out /tmp/отчёт --retire-tag 'archived::auto'
```

Отчёт — вспомогательное свидетельство, а не замена проверкам выше: он показывает
превью по фактическим шаблонам модели и перечисляет то, что статически не
вычисляется (`unsupported_constructs`, диагностика `preview_incomplete`). Каталог
отчёта обязан лежать вне `decks/**` и не коммитится: это артефакт прогона. Если
отчёт показывает `removed`, это наблюдение о составе JSON, а не команда удалять
заметку.

### Через `migrate-layout`

Перенос раскладки — не правка JSON, а перемещение каталогов, поэтому проверяется
иначе: команда сама доказывает содержимое каждого экспорта по SHA-256 до переноса и
сверяет отпечаток после. Для приёмки достаточно трёх прогонов:

```bash
anki-repo migrate-layout --root . --json            # план: refused должно быть false
anki-repo migrate-layout --root . --apply --json     # applied: true, summary.applied = N
anki-repo migrate-layout --root . --apply --json     # повтор: summary.exports = 0
```

`content_sha256` каждого экспорта до и после переноса обязан совпасть, а `deck.json`
— остаться байт-в-байт тем же: команда не меняет идентичности. Прежняя раскладка
отслеживалась Git, поэтому после `--apply` её нужно снять из индекса
(`git rm -r --cached decks/<прежняя_область>`): `.gitignore` не отменяет уже
добавленный индекс. Полный контракт и список отказов —
`tools/anki-repo/README.md`.

Отказы, которые не являются поводом обходить команду:

- `unknown_model` (3) — набор имён полей не совпал с моделью колоды (`mode: auto`).
  Перечитай схему через `models`; опечатка в имени поля выглядит именно так.
- `ambiguous_model` (5) / `deck_identity_mismatch` (3) — догадка запрещена:
  назови модель или колоду идентичностью явно.
- `media_forbidden` (3) — для поля и модели нет явного разрешения либо ссылка не
  допускается настроенным обработчиком. Наличие файла в `media/` не заменяет
  правила и свидетельство о проверенном каноническом содержимом. Описание
  создания с медиафайлами и машинно-читаемых причин отказа находится в
  `tools/anki-repo/README.md`.
- `guid_conflict` (6) — заметка с таким `guid` уже есть и отличается от запроса.
  Это задача `edit`, а не `create`.
- `guid_collision` (6) — `guid` новой заметки не свободен: он повторён в самом
  запросе либо, будучи сгенерированным, совпал с существующим, и свободного не
  нашлось. Заметка не добавлена.
- `unresolved_deck_identity` (3) — целевая колода не объявляет `crowdanki_uuid`.
- `invalid_request` (3) с `reason: out_dir_inside_decks` / `out_dir_overlaps_export`
  / `out_dir_not_owned` / `out_dir_manifest_invalid` — каталог отчёта выбран
  неверно: он внутри `decks/`, пересекается с экспортом, не принадлежит этому
  инструменту или содержит испорченный манифест владения. Выбери чистый каталог
  вне репозитория.
- `invalid_request` (3) с `reason: input_area_forbidden` — путь адресует закрытую
  область `decks/input`. Ни одна команда её не читает и не изменяет, и флага-обхода
  нет: для работы с колодами предназначен `decks/output/`.

## Локальный E2E Anki Desktop (вне CI)

Живое поведение группы `anki-repo anki` на настоящей Linux Anki с AnkiConnect и
CrowdAnki проверяет стенд `tools/anki-e2e` — только явной командой
`cargo run -p anki-e2e -- full` (или выборкой сценариев) при доступном Docker.
Он не входит в `cargo test --workspace`, CI, hooks и build scripts; модульные
тесты самого runner Docker не требуют и идут в обычном workspace-наборе.
`BLOCKED` из-за недоступного Docker или неподдержанной версии Anki не равен
`PASS`. Контракт, параметры и отчёт — `tools/anki-e2e/README.md`.

## Каталог бенчмарков

Декларации `benchmarks/` проверяет `cargo run -p benchmark-contract -- validate`,
документы результатов — `cargo run -p benchmark-contract -- check-result <файл>`;
Docker, Anki и Hyperfine для этого не нужны. Тесты `benchmark-contract` входят в
`cargo test --workspace --locked` и
проверяют и настоящий каталог, и учебные фикстуры. Измерения они не запускают.
Правила — `docs/performance/benchmarks.md`, коды возврата —
`tools/benchmark-contract/README.md`.

Локальную историю результатов проверяют тесты `benchmark-history` в том же
наборе: синтетический каталог и хранилище во временном каталоге, восстановление
индекса, перенос и раздел PR, проверенный самим `check_pr_body.py` (нужен
`python3`: без него эта проверка пропускается локально и падает при заданной
переменной `CI`). Целостность
своей истории пользователь проверяет `cargo run -p benchmark-history -- verify`.
Раздел `## Производительность` описания PR проверяет `check_pr_body.py` только по
форме; цифры сверяются с источниками отчёта.

Интеграционные тесты `benchmark-runner` запускают настоящий Hyperfine 2.x на
синтетическом каталоге во временном каталоге; CI ставит Hyperfine 2.0 с
закреплённой суммой SHA-256. Без Hyperfine 2.x тесты пропускаются локально и
падают при заданной переменной `CI`. Ветви cgroup и офлайн проверяют либо
измерение, либо честный отказ — в зависимости от возможностей окружения.
Серии сценариев настоящего каталога `benchmarks/` в `cargo test` и CI не входят;
интерфейс и коды возврата — `tools/benchmark-runner/README.md`.

## Проверки CI

Библиотечный контракт обмена проверяется синтетическими сценариями
`cargo test -p anki-repo --test integration exchange_contract --locked`:
идентичности, A/C/B, цепочка ревизий, повторное открытие состояния, конфликты,
конкурентные вызовы, отказы записи и файловые границы. Эти тесты входят в обычный
workspace-набор; живой Anki и пользовательский `decks/input/` им не нужны.
Полный контракт ревизий и границы доказательств — в `tools/anki-repo/exchange.md`.

`.github/workflows/ci.yml` (workflow «Проверки репозитория») прогоняет те же
проверки, что и локально, но независимо от машины разработчика. Он запускается
на `pull_request`, на `push`, еженедельно по `schedule` и вручную
(`workflow_dispatch`); задание на `push` выполняется только для основной ветки, имя ветки
в workflow не зашито. Push в рабочую ветку оставляет запуск со всеми заданиями
`skipped`: исполнитель он не занимает. CI имеет `permissions: contents: read`:
он не публикует артефакты, не использует секреты и ничего не пишет в репозиторий.

Обязательные контексты ruleset — «Форматирование и Clippy», «Код и тесты»,
«Заявленная MSRV» (`ci.yml`) и «Структура PR» (`pr-body.yml`). Порядок активации
доверенной «Доверенной структуры PR» (`pr-body-trusted.yml`) описан в
[`anki-git-workflow`](../../.agents/skills/anki-git-workflow/references/pr-lifecycle.md#доверенная-проверка-ci).
Имена обязательных заданий — часть
контракта ruleset: переименование или удаление задания оставит PR в вечном
ожидании контекста. Точные команды и флаги определяет сам workflow.

- «Форматирование и Clippy» — единственный владелец проверок, не зависящих от
  данных репозитория: регрессионные тесты `.github/scripts/test_*.py`, проверка
  метаданных и ссылок Agent Skills и локализаций; `actionlint` закреплённой
  версии (официальный релиз, проверенный по SHA-256) по всем workflow, включая
  выражения `${{ }}` и shellcheck скриптов `run:`; затем `cargo fmt --all --check`
  и `cargo clippy --workspace --all-targets --all-features --locked -- -D warnings`.
- «Код и тесты» — `cargo test --workspace --locked --profile ci --no-fail-fast`,
  а также `python3 .github/scripts/check_local_data_untracked.py`: постоянная
  граница пользовательских данных по фактическому индексу Git. Проверок
  содержимого пользовательских областей здесь нет намеренно: в чистом clone их не
  существует, а свой экспорт и свой корпус проверяются локально.
- «Заявленная MSRV» — `check_rust_toolchain.py`: `rust-toolchain.toml`
  закрепляет ровно `[workspace.package] rust-version`, участники рабочей области не
  расходятся, фактический компилятор той же версии. Отдельной сборки задание не
  выполняет: при доказанном совпадении Clippy по всем целям и возможностям в
  «Форматирование и Clippy» уже собирает рабочую область на заявленной MSRV. Если
  закреплённая версия когда-нибудь отойдёт от MSRV, сюда возвращается сборка
  `cargo +<msrv> check --workspace --all-targets --all-features --locked`.

Дополнительные проверки видны на PR, но merge не блокируют, пока сопровождающий
не добавит их в ruleset; их провал — настоящий красный статус, а не предупреждение:

- «Возможности asset-store и Chromium» (`ci.yml`) — тесты возможности Cargo
  `session-rotation-acceptance` (разбор `--acceptance-rotate-after-items`,
  плановая ротация сессии с контрольными точками) и три теста `jpdb::tests::browser_*`,
  которые вне CI помечены `#[ignore]` из-за Chromium. Браузер — Google Chrome
  образа исполнителя (`CHROME_BIN`), страницы синтетические; без браузера задание
  красное. Список обязательных имён проверяет `report_cargo_tests.py --require`:
  тест, который не исполнялся или остался `ignored`, — отказ.
- «Зависимости Rust (cargo-deny)» (`ci.yml`) — политика `deny.toml` по
  фактическому `Cargo.lock`: уведомления RustSec, лицензии, источники и wildcard.
  База уведомлений меняется без коммитов, поэтому её проверяет и еженедельный
  `schedule`. Игнорирование уведомления — только точечно, с идентификатором и причиной.
- «Эталоны KanjiVG и Noto Serif JP» (`reference-catalogs.yml`) — исполняет
  генераторы возможности `reference-generator`: скачивает закреплённые в файлах
  атрибуции исходники, проверяет их SHA-256 и требует побайтового совпадения
  регенерации со встроенными каталогами. Запускается при изменении генераторов,
  каталогов, общих модулей масок, манифестов, `Cargo.lock` и toolchain, раз в
  месяц и вручную; недоступность источника — отказ, а не пропуск. Успех на
  идентичных входных файлах переиспользуется кэш-доказательством (как в
  `renovate-config.yml`): повторные коммиты PR не повторяют регенерацию, а
  `schedule` и `workflow_dispatch` всегда выполняют её полностью.
- CodeQL (`codeql.yml`) анализирует Rust и Actions по затрагиваемым путям и
  еженедельно; из-за `paths` он не годится в обязательные контексты без
  отдельного решения о постоянной отчётности.

Бюджет времени: обязательные задания и дополнительные задания на каждом PR
идут параллельно, и ни одно дополнительное задание не должно быть дольше «Код и
тесты» — тогда оно не увеличивает время ожидания PR. Поэтому дополнительные
задания читают кэш зависимостей `code` (`shared-key`, `save-if: false`) и
sccache с тем же окружением, а не держат свои копии кэша. sccache кэширует
библиотеки (включая крейты рабочей области) между прогонами, но не тестовые бинарники
(`crate-type`), поэтому тестовая сборка asset-store компилируется в каждом
прогоне; задание «Возможности asset-store и Chromium» собирает её с
`opt-level=0`. Новое задание или шаг сначала замеряется по фактическим
шагам GitHub Actions на прогретом кэше; если оно выходит за этот бюджет,
его переносят в путь с фильтром `paths`, кэш-доказательством или `schedule`.

Диагностика компактна и не публикует файлов: Job Summary содержит счётчики
тестов, имена упавших и обязательных тестов, версию браузера, итог cargo-deny и
сравнение SHA-256 эталонов; аннотации указывают на файл и строку для rustc,
rustfmt и actionlint и на имя упавшего теста. Вывод тестов и журналы в сводку не
копируются, `upload-artifact` не используется. Сводка без `--require` не меняет
исход задания.

Версии внешних инструментов (`ACTIONLINT_VERSION`, `CARGO_DENY_VERSION`) Renovate
не отслеживает: версию и SHA-256 из официального релиза обновляют вместе вручную.

Отдельный `.github/workflows/pr-body.yml` проверяет опубликованный body по
контракту `.github/scripts/check_pr_body.py` валидатором из самого PR (проверка
кандидата): лимит 10 000 символов, компактная производительность и структурно
корректная таблица CodeRabbit при наличии раздела. Независимый
`pr-body-trusted.yml` запускает тот же контракт на `pull_request_target`
валидатором из base SHA, без checkout и выполнения кода head, секретов и write
permissions; его права — `contents: read`. Ни одна проверка не требует Gist и не
загружает содержимое по внешним ссылкам. Состояние required contexts
проверяется по реальному ruleset. Тесты скриптов и метаданные
Agent Skills здесь намеренно не дублируются — их выполняет `ci.yml`, который
покрывает и push в основную ветку. Единственный владелец версии MSRV —
`[workspace.package]` корневого `Cargo.toml`.

Локально тот же набор воспроизводится из корня репозитория — сначала
Python-проверки контрактов, затем канонические Cargo-команды из `AGENTS.md`:

```bash
python3 -m unittest discover -s .github/scripts -p 'test_*.py'
python3 .github/scripts/check_skill_contracts.py
python3 .github/scripts/check_local_data_untracked.py
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
```

Блок выше — канонический локальный набор, а не дословная копия CI: вместо
`cargo test --workspace --locked` обязательный CI собирает тесты в профиле
исполнителя и не останавливается на первом упавшем тесте
(`cargo test --workspace --locked --profile ci --no-fail-fast`), а Clippy
дополнительно включает `--all-features`. Строгая локальная репетиция
обязательного CI — те же команды с этими флагами. Дополнительные проверки
воспроизводятся так (браузерным тестам нужен Chromium, `actionlint` и
`cargo-deny` — установленные инструменты):

```bash
actionlint
cargo deny --locked check
cargo test -p asset-store --lib --locked --features session-rotation-acceptance
cargo test -p asset-store --lib --locked jpdb::tests::browser_ -- --ignored
python3 .github/scripts/check_reference_catalogs.py
```

Содержимое пользовательских областей CI не проверяет: в чистом clone `decks/`
и `.asset-store/` отсутствуют, и шаг, который «проверил» бы их
отсутствие, выдал бы пустоту за проверку личных данных. Свой экспорт проверяют
локально (`anki-repo validate` по каталогу `decks/output/<имя_экспорта>`,
`kanji-corpus-gate`, `pitch-corpus-gate`). Вместо этого CI постоянно проверяет
границу: ни один путь внутри этих областей не должен быть отслеживаемым, а правила
игнорирования обязаны быть на месте и не ослаблены повторным включением
(`.github/scripts/check_local_data_untracked.py`). Проверка идёт по фактическому
индексу Git, потому что `.gitignore` не отменяет уже добавленный индекс и обходится
`git add -f`.

Здесь важно не смешивать два разных инварианта:

1. **Default-набор тестов независим от live payload.** Тесты строят собственные
   синтетические экспорты во временных каталогах и `decks/**` не читают: ни одна
   конкретная колода, уровень, note model, имя поля или media не является их
   fixture.
2. **CI проверяет tracked код, документацию и самодостаточные fixtures, а не
   пользовательские данные.** Наличие или отсутствие колод и корпусов в чистом
   clone не является предметом проверки CI и не выдаётся за неё. Постоянная проверка
   CI — граница против случайной публикации пользовательских данных.

Поэтому изменение состава колод, уровней, конкретных note models, имён полей и
media не требует правки CI или default-тестов и не должно начать требовать её: ни
один шаг не называет колоду по имени. Исключение — изменение самого формата или
контракта toolkit'а.

## Минимум после любой правки JSON

1. JSON успешно парсится стандартным парсером.
2. Корневая сущность и ожидаемые основные ключи не потеряны.
3. Все `Note.note_model_uuid` разрешаются в существующую модель заметки.
4. Количество значений в `Note.fields` соответствует модели, если задача не является миграцией схемы.
5. `deck_config_uuid` разрешается в существующую конфигурацию там, где он используется.
6. `guid`/UUID существующих сущностей не изменились; менять их можно только при явной миграции идентичности.
7. Не появились случайные массовые изменения форматирования.

## Для массовой правки заметок

До изменения зафиксировать минимум:

- общее количество заметок;
- количество deck nodes;
- используемые note model UUID;
- распределение количества полей заметок.

После изменения сравнить эти значения с ожидаемым результатом задачи.

Если задача меняет только текст одного или нескольких полей, структурные количества должны остаться прежними.

## Для изменения модели заметки

Дополнительно проверить:

- `flds[].ord`;
- соответствие `fields` новому порядку;
- `tmpls[].qfmt` и `tmpls[].afmt`;
- ссылки на имена полей внутри шаблонов;
- CSS только если он относится к задаче.

## Для media

Если задача касается media, отдельно проверять ссылки `[sound:...]`, `<img src="...">`, шаблоны `qfmt`/`afmt`, CSS и объявления `media_files` во всех узлах дерева.

Отсутствие media-файла в Git-репозитории не считать ошибкой автоматически, пока политика хранения media не определена. Для `migrate-media` ручное изменение `deck.json` или `media/` вместо команды запрещено: только команда может сохранить доказательство пары identity—filename и согласовать дерево объявлений.

## Git-проверка

Git/GitHub lifecycle — branch, staging, commit, push, проверка удалённого
состояния, PR и merge — принадлежит repository skill
`.agents/skills/anki-git-workflow/`; не заводи здесь второй owner этой процедуры.

Отсюда в эту матрицу входит только то, что относится к содержанию изменения:

- итоговый diff должен соответствовать масштабу задачи, а для больших JSON —
  масштабу правки;
- в diff не должны попасть временные файлы и пользовательские локальные данные;
- в PR перечисляются только реально выполненные проверки.

Каталог статического отчёта `visual-report` — временный артефакт прогона: он
лежит вне репозитория (или как минимум вне `decks/**`), не добавляется в коммит и
не заменяет собой проверки выше. Если отчёт всё же понадобился рядом с
репозиторием, он либо игнорируется Git'ом, либо удаляется до `git status`.
