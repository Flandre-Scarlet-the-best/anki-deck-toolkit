Measurements of the benchmark runner itself
([interface and semantics](README.en.md)): how
accurately it measures a workload with a known cost, what exactly each metric
contains and what polling `/proc` and the run's own cgroup cost. General
measurement rules are in the [methodology](../../docs/performance/README.en.md).

## What is measured

The `benchmark-runner.calibration-*` catalog scenarios run `benchmark-workload`
from this package — a synthetic workload whose cost is known in advance. They
do not describe the performance of `asset-store`, `anki-repo` or Anki.

| Scenario | Workload | Expected |
|---|---|---|
| `calibration-noop` | process start and exit | lower bound of time and memory, Hyperfine's cost in group values |
| `calibration-cpu` | one thread, 50 ms of its own CPU time | `time_cpu` ≈ 50 ms plus process start |
| `calibration-cpu-plain` | the same target with Hyperfine metrics only | the comparison shows the cost of extra monitoring |
| `calibration-parallel` | four threads of 1000 ms each | `time_cpu` ≈ 4 s, time ≈ 1 s, group load ≈ 4 cores |
| `calibration-memory` | writes every page of a 256 MiB block, holds it 200 ms | `memory_peak_resident` ≈ 256 MiB plus process base |
| `calibration-io` | new 16 MiB file: write, `fsync`, own-page eviction advice, verified read and removal | positive accounted bytes and operations; physical totals depend on filesystem and devices |

## How to measure

The cost of polling is estimated with pairs of series of the same target: with
`/proc` and cgroup polling and with `--no-sampling`; the cost of the own cgroup
by comparing `calibration-cpu` with `calibration-cpu-plain`. Series alternate so
that CPU frequency drift and background load spread evenly. The contract does
not compare results of different scenarios: such a comparison is a methodology
observation, not a `compare` verdict.

```bash
cargo run -p benchmark-runner -- check benchmark-runner.calibration-cpu --profile warm
cargo run -p benchmark-runner -- run benchmark-runner.calibration-noop --profile warm --runs 30
cargo run -p benchmark-runner -- run benchmark-runner.calibration-cpu --profile warm --runs 30
cargo run -p benchmark-runner -- run benchmark-runner.calibration-cpu --profile warm --runs 30 --no-sampling
cargo run -p benchmark-runner -- run benchmark-runner.calibration-cpu-plain --profile warm --runs 30
cargo run -p benchmark-runner -- run benchmark-runner.calibration-parallel --profile warm --runs 10
cargo run -p benchmark-runner -- run benchmark-runner.calibration-parallel --profile warm --runs 10 --no-sampling
cargo run -p benchmark-runner -- run benchmark-runner.calibration-memory --profile warm --runs 10
cargo run -p benchmark-runner -- run benchmark-runner.calibration-io --profile warm --runs 5
cargo run -p benchmark-history -- list --module benchmark-runner
```

## Calibration findings

The findings below come from accepted JSON results of these scenarios in the
snapshots' reference environment (WSL2, AMD Ryzen 7 5800X3D, 16 logical CPUs,
`perf_event_paranoid = 2`, cgroup delegation via `systemd-run --user`):
alternating series of 30 runs for 50 ms and 10 runs for the parallel and memory
workloads. Full results and their IDs are in the local history and the PR
description.

- **CPU time is accurate.** `time_cpu` of the 50 ms workload is 50.91–51.03 ms:
  0.9–1.0 ms above the target, comparable to the cost of starting an empty
  process (0.73 ms) and creating the worker thread. Four threads of 1 s give 4.0018–4.0019 s, `time_wall_clock`
  1.0017 s.
- **Group values include Hyperfine.** `cpu_time_cgroup` exceeds the target's
  `time_cpu` by ≈ 1.4 ms (52.27–52.48 ms against 50.96–51.03 ms); for the empty
  target the group spends 2.5 ms while the target itself takes 0.73 ms.
- **The group's mean load** is the group's CPU time over its lifetime, i.e. the
  whole Hyperfine invocation. For short targets the group lives noticeably
  longer than the target, so the value is a property of the "target plus
  Hyperfine" pair: 0.16 cores for the empty target, 0.62–0.67 for the 50 ms
  single thread, 3.85–3.88 for four threads of 1 s. Before the fix the
  denominator was the target's own time, and the empty single-threaded target
  got 3.35 cores.
- **Resident memory is accurate; scopes differ.** The 256 MiB block (268.4 MB)
  gave `memory_peak_resident` 270.6–270.9 MB. `memory_peak_cgroup` of the same
  run is ≈ 1 MB lower: pages of the executable already in the page cache are
  charged to another group. The empty target has 3.4 MB RSS and a 0.8 MB group
  peak — different quantities, not an error.
- **`memory_host_peak_increase` is unreliable for conclusions.** For the same
  256 MiB block it gave 98–280 MB (223 ± 55 MB): a finished process's memory
  returns to the system with a delay, so the next run's base point is shifted
  and concurrent releases raise `MemAvailable`. With a 1.5 s hold and frequent
  polling the drop was 242–256 MiB. The metric is a host observation, not a
  bound; series must not be compared by it.
- **Polling and cgroup cost are within noise.** Mean `time_wall_clock` of the
  50 ms target across alternating series: with polling 51.14 and 51.16 ms,
  `--no-sampling` 51.18 and 51.12 ms, Hyperfine metrics only 51.13 and 51.06 ms
  with σ 0.06–0.12 ms. For four threads of 1 s: 1.00172 and 1.00176 s with
  polling, 1.00175 and 1.00183 s without. Differences are below the series
  spread; the effect is under 0.2 % on the short run and not detected on the
  one-second run.
- **Resolution.** `/proc` polling at a 0.05 s interval yields no window on a
  target shorter than the interval: `cpu_utilization_peak@host` of the empty
  target is `unavailable` with a reason, not zero. The `instructions` counter is
  available with `perf_event_paranoid = 2`. Its relative spread depends on the
  workload: about 1.4 % for `calibration-cpu`, 0.9 % for `calibration-parallel`,
  10⁻³ for `calibration-noop` and 4×10⁻⁴ for `calibration-memory`.

Not measured: an environment without WSL2, multi-process workloads, a Docker
container's cgroup (500 ms lookup) and the effect of polling on targets longer
than a few seconds.

The earlier manual observation without original JSON (2026-10-26, synthetic
`overhead.*` catalog) is replaced by the findings above. One design decision
from it is kept: Hyperfine, not the target, is moved into the run's subgroup
before measurement starts — moving a process between groups before it creates
threads cost about 17 ms of kernel waiting and added 20–25 ms to the target's
time.
