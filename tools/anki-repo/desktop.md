# Управляемая интеграция Anki Desktop

Владелец контракта — `anki_repo::desktop` и группа `anki-repo anki`.
Они готовят AnkiConnect и вызывают установленный CrowdAnki. Идентичностями,
ревизиями и обменом владеет [exchange](exchange.md); этот адаптер не переносит
`input ↔ output` и не открывает production `decks/input/`.

## Выбор установки

Rust CLI по-прежнему собирается на Linux. Окружение классифицируется по
нескольким признакам, ни один из которых в отдельности не считается
доказательством, и результат виден в `doctor` как `environment` и
`windows_interop`:

- `wsl_interop` — ядро WSL и успешный короткий запуск `powershell.exe`
  (не дольше 15 с, без ввода и вывода терминала). CLI ищет **Windows Anki** через
  Windows PATH, стандартные каталоги и реестр; Linux Anki в WSL не устанавливается
  и автоматически не выбирается;
- `linux` — обычный Linux: Linux PATH и каталог данных XDG;
- `linux_container_on_wsl_kernel` — изолированный Linux-контейнер на ядре WSL2
  (`/.dockerenv` или `/run/.containerenv` без `WSL_DISTRO_NAME`, `WSL_INTEROP`
  и `/run/WSL`), например E2E-стенд в Docker Engine или Docker Desktop. Interop
  в нём не пробуется, используется Linux Anki;
- `wsl_interop_unavailable` — штатный дистрибутив WSL, но interop отключён,
  отказал или не ответил за срок; `undetermined_wsl_kernel` — ядро WSL с
  отсутствующими или противоречивыми признаками и неответившим interop.

В двух последних случаях молчаливого переключения на Linux Anki нет: любая
команда, включая `doctor`, отказывает с причиной `windows_interop_unavailable`,
результатом пробы (`unavailable`/`failed`/`timed_out`) и обнаруженными Linux-
установками, пока interop не восстановлен или не заданы явно **оба**
`--executable` и `--data-dir`. Перед изменением аддонов окружение
переопределяется заново: если целевая платформа сменилась (например, interop
отказал после выбора Windows Anki), операция отменяется с `environment_changed`.

Работающая Linux Anki распознаётся по `anki` в argv0 или по запуску
интерпретатора Python с опциями (`python3 -u -m aqt`, `python3 -I …/anki`):
разбираются опции интерпретатора до модуля или скрипта, а аргументы самого
приложения не просматриваются. Сам процесс `anki-repo` и его параллельные
запуски процессом Anki не считаются. Для нескольких установок требуется `--executable`; для
нестандартной связи установки и базы — `--data-dir`. Эти параметры позволяют
явно выбрать редкую конфигурацию. `doctor` показывает `target_platform`,
`cli_platform`, executable, фактическую версию, аргументы запуска, базу,
обнаруженные установки и процессы. WSL-путь переводится через `wslpath`.

```bash
anki-repo --json anki doctor
anki-repo --json anki --executable /path/to/anki --data-dir /path/to/Anki2 doctor
anki-repo --json anki --profile 'Selected profile' doctor
```

`--data-dir` — база Anki с `addons21`, не каталог профиля. Временная база через
`-b` запускает ту же установленную программу с отдельными профилями и аддонами.
CLI не переключает профиль уже работающего приложения. Наличие HTTP-порта не
считается доказательством связи с установкой: namespaced handshake проверяет
базу, профиль, challenge и версии. Адрес — только числовой HTTP loopback без
credentials, query или пользовательского пути. Порт берётся из действующей
конфигурации AnkiConnect; его можно явно задать `--endpoint`.
До передачи apiKey/capability проверяется владелец слушающего порта: Windows
PID/executable через системный TCP inventory, Linux socket inode через `/proc`.
Локальный Linux-слушатель, затеняющий Windows-порт в WSL, отвергается.
WSL2 по умолчанию использует NAT, в котором Windows loopback не доступен как
`127.0.0.1` из Linux. Для связи с Windows Anki поддерживаются WSL1 и WSL2 в
режиме mirrored (Windows 11 22H2+): задайте
`[wsl2] networkingMode=mirrored` в `%UserProfile%\.wslconfig` и перезапустите
WSL командой `wsl --shutdown`. `doctor` проверяет режим через `wslinfo` и явно
отказывает в сетевых запросах, если сообщает `nat`, другой неподдерживаемый
режим или не может определить режим.

## Диагностика и совместимость

Диск отдельно подтверждает `installed`, `enabled`, совместимость по метаданным
Anki и поддержку адаптером; `loaded` по диску остаётся `null`. В Anki только
отрицательный `max_point_version` задаёт верхнюю границу — положительное число
не считается запретом более новой Anki. Активный профиль и загрузка модулей
подтверждаются живым API. `http_unreachable`, `wrong_service`, `wrong_profile`,
ошибка авторизации и ошибка handshake разделены в машинном результате.

Поддержка адаптера намеренно ограничена проверенными исходниками: Anki
26.09.2 и 26.09.3 (числовые эквиваленты 26.9.2 и 26.9.3), AnkiConnect API 6
из AnkiWeb с `mod` 1792032779 и CrowdAnki с `mod` 1789725370. Обе версии Anki
подтверждены живым прогоном [E2E-стенда](../anki-e2e/README.md) на Linux Anki. Точный allowlist Python-файлов с
SHA-256 находится в `src/desktop/compatibility.json`. Неизвестные изменения,
включая добавленный Python-файл, приводят к `unsupported`/`incompatible`.
Настройки `meta.json`, конфигурация и пользовательские файлы не заменяются
снимком upstream. Для расширения поддержки нужны проверка новых upstream
контрактов, обновление allowlist и живая приёмка; диапазон версии не угадывается.

Состояния патча: `missing`, `outdated`, `incompatible`, `damaged`; `installed`
означает только исправный диск. После изменения — `pending_restart`.
`ready` требует исправного диска, соответствующего живого handshake, двух
загруженных аддонов и успешно исполненных настоящих export/import в **текущем
процессе и профиле**. Одно восстановление порта этого не подтверждает.

## Первоначальная установка

```bash
anki-repo anki setup
anki-repo --json anki setup --apply
```

План перечисляет недостающие ID, AnkiWeb-источники, последствия и блокеры.
`--apply` означает согласие на загрузку официальных совместимых пакетов и
запуск штатного установщика Anki. Rust проверяет HTTPS-источник, метаданные,
пути ZIP, размеры, полную SHA-256 официального архива и точные Python-хэши.
Он нормализует `manifest.json` с
AnkiWeb ID и метаданными, как штатная AnkiWeb-установка, затем открывает
`.ankiaddon` через Anki. Распаковку и установку выполняет **AddonManager Anki**.

Это управляемый **интерактивный** путь: Anki показывает подтверждение установки.
`awaiting_native_installer` не означает успешную установку;
`automatic_installation` остаётся `false`. Anki принимает один файл на запуск.
Если отсутствуют оба аддона, после первого диалога можно открыть второй
возвращённый пакет через эту же Anki либо штатно закрыть её и повторить
`setup --apply`: здоровый установленный аддон будет пропущен. После перезапуска
проверьте `doctor`. Отмена и ошибка установщика не превращаются в готовность.
Отключённые или неизвестные аддоны setup не перезаписывает и не включает молча.
При работающем приложении возвращается `restart_required`.

## Жизненный цикл патча и восстановление

```bash
anki-repo anki patch status
anki-repo anki patch install
anki-repo anki patch install --apply
anki-repo anki patch repair --apply
anki-repo anki patch remove --apply
anki-repo anki restore BACKUP_ID
anki-repo anki restore BACKUP_ID --apply
```

Изменения разрешены только при остановленной Anki. Одна advisory-блокировка
защищает setup, patch и restore: повторную проверку состояния, backup,
подготовку и публикацию, включая передачу setup штатному установщику. После
запуска установщика изменения блокирует обнаруженный процесс Anki; запуск GUI
не подтверждает установку. Bootstrap вставляется в единственную проверенную
точку перед созданием AnkiConnect. Payload и конфигурация capability находятся в
`AnkiConnect/user_files/toolkit`, а задания и экспорты — в
`Anki2/toolkit-desktop/spool`. При установке/удалении прежний spool безопасно
копируется туда и проверяется; после успешного обновления или удаления add-on
старая копия очищается. Конфликтующий или небезопасный spool останавливает
операцию без удаления исходных заданий. Обычные upstream actions,
API version, конфигурация и сервер остаются upstream; нового сервера нет.
Во время операции CrowdAnki остальные запросы, способные изменить коллекцию,
отклоняются как busy (включая новый RPC API AnkiConnect). JSON-RPC batch
сохраняет ID каждого ответа, а уведомления без ID не получают ответа.
При свободном адаптере запрос целиком передаётся исходному handler upstream.

Повторный install исправного патча ничего не пишет. Repair восстанавливает
стёртый bootstrap только на точном известном upstream, а повреждённый payload
— в собственной области. Неожиданно изменённый bootstrap/upstream не
переписывается. Remove убирает только точный собственный блок и собственную
область payload, сохраняя их в backup. Обновление аддона может стереть bootstrap;
сохранённый `user_files` не считается доказательством загрузки.

До mutation оба аддона копируются в `Anki2/toolkit-desktop/backups/ID`,
включая `meta.json`, конфигурацию, `user_files` и прежний патч; spool не входит,
поскольку живёт отдельно и сохраняется при удалении аддонов. SHA-256 каждого
файла проверяется повторным чтением. Копирование media импорта и файлов
backup использует ограниченный буфер, с проверкой до публикации файла.
Для Windows копирование и SHA-256 выполняет
встроенный PowerShell-адаптер через файловые API Windows, с отказом на reparse
points и сообщениями о продвижении в stderr; Rust управляет операцией и публикует
проверенный manifest. Это сохраняет скрытые файлы и пользовательские снимки без
потерь на множественных переходах через файловую границу WSL.
Backup находится **вне addons21**: uninstall
не обязан сохранять `user_files`. `restore` принимает только ID и проверяет
каждый путь и хэш; заменяет только два разрешённых каталога, предварительно
сохраняя текущее состояние. Ни коллекции, ни другие аддоны не восстанавливаются
и не удаляются. Прежние деревья и backup сохраняются для адресного отката.
Завершающий `snapshot.json` связывает manifest SHA-256 с наличием каждого
аддона, включая исходное отсутствие обоих и пустые каталоги. Восстановление
отсутствия переносит установленное дерево в `displaced`. Старые backups без
этого маркера допускаются при непустом manifest и точном совпадении всего
содержимого; пустой старый снимок неоднозначен и отклоняется до изменений.
Если оставшийся после сбоя lock мешает повтору, сначала подтвердите отсутствие
операции; CLI не снимает неизвестный lock самостоятельно.

## Запуск и перезапуск

```bash
anki-repo anki --profile 'Selected profile' launch --apply
anki-repo anki --profile 'Selected profile' stop --apply
anki-repo anki --profile 'Selected profile' restart --apply
```

Launch разрешён только при отсутствии обнаруженной работающей Anki и сохраняет
секрет владения процессом. Stop/restart требуют совпадения этого секрета в
живом handshake и локальной записи, того же профиля и безопасного состояния
GUI. Во время занятий, фоновой операции или модального окна — отказ.
Используется штатное закрытие AnkiConnect, без kill. CLI ждёт подтверждённого
исчезновения процесса; при неполном закрытии новый экземпляр не запускается.
Если во время ожидания изменилась платформа обнаружения (например, отказал WSL
interop), возвращается `restart_required` с причиной `environment_changed`:
пустой список процессов другой платформы не подтверждает остановку Anki.
Пользовательский процесс получает `restart_required`, не закрывается и не
переключает профиль. После старта `starting` требует продолжить `doctor`.

## Настоящие операции CrowdAnki

```bash
anki-repo anki --profile 'Selected profile' export --deck 'Selected deck'
anki-repo --json anki --profile 'Selected profile' export --deck 'Selected deck' --apply
anki-repo --json anki --profile 'Selected profile' import /path/to/export --apply
anki-repo --json anki --profile 'Selected profile' job JOB_ID
```

Без `--apply` выводится план. Для записи обязательны ожидаемый профиль и
авторизованный handshake. Rust создаёт случайное задание в приватном spool;
для импорта копирует экспорт через существующий typed loader и проверяет
простые имена media, ссылки и каталоги. HTTP принимает только случайный ID,
отдельный capability token и ожидаемую установку/профиль. Пути от HTTP-клиента
не используются. Требуется также обычный upstream apiKey: он читается из
конфигурации или переменной `--api-key-env` (по умолчанию
`ANKICONNECT_API_KEY`). Секреты не попадают в диагностический вывод.
Защита рассчитана на чужой HTTP-клиент, не на враждебный процесс того же
пользователя, имеющий доступ к файлам и коду аддонов.

Actions: `toolkitStatus`, `toolkitExport`, `toolkitImport`, `toolkitJob`,
`toolkitShutdown`. Export вызывает `AnkiJsonExporter.export_to_directory` с
физическим копированием media. Он также сохраняет служебные изменения в
коллекции — это поведение CrowdAnki. Проверяется реальное наличие всех
заявленных media после копирования, включая ошибки, которые upstream печатает
и не выбрасывает. Экспорт попадает только в новый каталог задания.

Import вызывает оригинальный `AnkiJsonImporter.load_deck`, включая штатные
настройки, `import_config.yaml` и backup коллекции. Диалог виден в Anki; HTTP
admission завершается **до** его открытия. `job` возвращает
`prepared`/`queued`/`running`/`succeeded`/`cancelled`/`failed`; отмена не
считается успехом. `prepared` означает, что Anki не приняла задание; операция не
началась, поэтому после проверки причины можно отправить новую команду.
Неоднозначные идентичности/имена моделей и структурные преобразования модели,
для которых upstream открывает дополнительный диалог с неясной отменой,
отклоняются до импорта с диагностикой `*_requires_manual_import`.
Отсутствующая в JSON note не удаляется из Anki. Ошибка после начала upstream
операции может оставить частичные изменения: результат сохраняет
`partial_changes_possible`, backup позволяет штатное восстановление в Anki.
Если финальный `result.json` записать не удалось, текущий процесс сообщает
`interrupted`, `result_persisted: false`, прежнее состояние в `operation_state`
и ошибку `result_persistence_failed`; busy освобождается. На диске может остаться
`running`/`queued`, после перезапуска он также трактуется консервативно.
Автоматического повторения операции нет. `local_export_dir` в живом статусе
возвращается только для успешного export; import этого поля не содержит.

Задание одноразовое. Повторный admission в текущем процессе возвращает то же
задание; после перезапуска незавершённое задание — `interrupted`, автоматического
повторного импорта нет. Явный отказ API возвращается как ошибка, а неподанный
ticket удаляется. При таймауте или обрыве после начала отправки результат —
`submission_unknown`: сначала запросите `job`. Если он вернул `prepared`, Anki
не приняла задание и операция не начиналась; при `queued`/`running`/другом
сохранённом результате сначала учитывайте именно это задание. Недоступный
процесс не позволяет по старому running-файлу заявлять ни успех, ни
подтверждённое прерывание.

## Вывод и проверки

JSON использует обычный envelope `schema_version: 1`, `command: anki`, `result`.
Текстовый режим сохраняет те же факты. `0` — выполненное действие/план;
`doctor` и `patch status` возвращают `6` при неподтверждённой готовности/исправности,
`job` — до `succeeded`, также `6` для требуемого ручного перезапуска или
неизвестного результата отправки. Некорректный запрос — `invalid_request` с
точным `details.reason` и штатным кодом этой ошибки.
Ошибки внешней программы, API или окружения Desktop (например, `desktop_io`,
`http_unreachable`, `windows_probe_failed`, `backup_failed` и
`installer_download_failed`) возвращают `external_failure` и код завершения `9`,
сохраняя машинную причину в `details.reason`. В `doctor` та же ошибка не
прерывает сбор дисковой диагностики: `endpoint` становится `null`, а `live`
содержит `state`, `code` и `message`; команда сохраняет код `6` при неподтверждённой
готовности.

Обычные Cargo-тесты и `.github/scripts/test_desktop_bridge.py` используют
синтетические данные. Они проверяют границы, состояния, backup и отмену, но не
доказывают работу Anki. Живая приёмка отдельно должна проверить Windows/WSL или
Linux Anki, native install/uninstall/reinstall двух аддонов, загрузку bootstrap,
реальный deck + media, импорт/отмену, restart и восстановление настроек.
Локальные свидетельства хранятся вне Git по `anki-live-testing`.

Проверенные upstream-контракты: [AnkiConnect](https://git.sr.ht/~foosoft/anki-connect),
[CrowdAnki](https://github.com/Stvad/CrowdAnki),
[AddonManager Anki](https://github.com/ankitects/anki/blob/26.09.2/qt/aqt/addons.py).
