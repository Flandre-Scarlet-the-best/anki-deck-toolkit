# Программный обмен CrowdAnki и ревизии

`anki_repo::exchange` — исполнимый библиотечный API без зависимости от запущенного
Anki. Это владелец идентичностей обмена, семантических снимков, сравнения A/C/B и
сохраняемого происхождения рабочей копии. CLI `anki-repo` его не вызывает и
по-прежнему отказывает в доступе к `decks/input/`. Программный API не копирует,
не перемещает и не изменяет экспорт, включая `deck.json` и `media/`.

## Идентичность и владение

`ProfileId` — устойчивый непрозрачный ID профиля, который будущий адаптер назначает
и сохраняет независимо от отображаемого имени профиля. `DeckIdentity` — пара
`ProfileId` и корневого `crowdanki_uuid`. Совпадение имени, каталога или байтов
двух колод не означает совпадения идентичностей. Все вложенные колоды также
обязаны иметь непустые уникальные `crowdanki_uuid`; их родительские связи входят
в семантический снимок.

`export_name` преобразует `Parent::Child` в `Parent__Child`, нормализуя Unicode
в NFC. Оно отвергает пустые компоненты, `.`/`..`, разделители файловых путей,
управляющие символы, неоднозначные пробелы и небезопасные символы имени.
Это ограничение снимков распространяется на имена корня и всех вложенных колод:
в компонентах не поддерживаются `/`, `\`, `:`, `?`, `*`, `"`, `<`, `>`, `|`
и завершающая точка; `::` разрешён как разделитель иерархии. Даже допустимые в
Anki имена вроде `Урок 1: введение` и `Что это?` требуют отдельного согласования
имени перед обменом; API не заменяет символы автоматически.
Преобразование не является взаимно однозначным: например, `Parent__Child`
даёт тот же читаемый префикс. Поэтому `DeckIdentity::output_directory` добавляет
полный SHA-256 однозначно сериализованной пары идентичностей. Префикс ограничен
100 байтами UTF-8; итоговый компонент не превышает 166 байт. Разные профили
и разные UUID получают независимые адреса даже при одинаковых именах.
Неоднозначные имена узлов внутри одного экспорта после NFC, приведения регистра
и преобразования `::` отвергаются. Каталоги привязок проверяются также на коллизии
после NFC и приведения регистра.

После регистрации путь `output` закрепляется. Переименование той же колоды
регистрируется как изменение имени при прежней идентичности и прежнем пути.
Автоматического переименования каталога, присвоения существующего экспорта или
миграции старой раскладки этот API не выполняет. Если назначение уже существует,
но базы ещё нет, результат — `untracked_output`; совпадение байтов не даёт права
его присвоить. Для старых рабочих колод понадобится отдельное явное согласование
привязки будущим владельцем.

`input` принадлежит будущему доверенному программному экспортеру: там должен
лежать последний подтверждённый снимок каждой идентичности, без истории всех
версий. `output` — независимая рабочая область агента. `Snapshot::from_bytes`
принимает JSON и полный набор физических media в памяти, не открывая никаких
путей. `Confirmation::from_trusted_owner` — отдельный типизированный вход для
подтверждения экспортера: снимок, монотонный `source_sequence` и непустой ID/ссылка
на свидетельство завершения. Универсальные команды и правила `guard_local_path`
не получают флага обхода, альтернативного loader или доступа к `input`.

Существующий парсер `loader`, структурный валидатор `validate_structure` и
разрешение полей `ExportIndex` используются совместно с обычными операциями.
`validate_structure` проверяет документ в памяти; физические проверки обычного
`validate_document` и их порядок сохранены. Чтение `Snapshot::read_working`
сначала применяет прежний запрет input, затем читает файлы без symlink.

## Семантический снимок и различия

`Snapshot` хранит идентичность, имя, адреса и SHA-256 смысловых единиц. Тексты
полей и полные копии media в метаданные не попадают. Сравниваются:

- дерево колод по UUID, родительские связи, имена, свойства и декларации;
- заметки по GUID независимо от порядка в JSON: принадлежность колоде, модель,
  поля через модель и `ord`, теги как множество без учёта регистра;
- определения моделей и конфигураций по UUID; `flds` и `tmpls` упорядочены по `ord`,
  поэтому перестановка определений в массиве не считается изменением;
- полные определения, включая CSS, шаблоны и неизвестные свойства;
- множества объявлений `media_files` каждого узла и отдельно SHA физических
  байтов всех файлов `media/`, в том числе необъявленных.

JSON-отступы, переводы строк, порядок ключей, заметок и объявлений не влияют на
ревизию. Порядок массивов неизвестного назначения сохраняется как значимый.
Неизвестные свойства не удаляются и не игнорируются: их изменения получают
`opaque_change`, в том числе свойства внутри определений полей и шаблонов
(адресуемые по `ord`). Вложенные объекты без интерпретируемой здесь схемы,
например разделы `new`/`rev`/`lapse` конфигурации, сравниваются консервативно
целиком: любое их изменение недоказанно. Неизменённые неизвестные свойства
не создают различий или блокировки сами по себе.
Отсутствующее объявленное media, неразрешённые ссылки, внешние,
кодированные/неоднозначные и динамические адреса, непроверенные шаблонные
конструкции, активный/незавершённый HTML явно перечисляются в `unproven`. HTML/CSS-ссылки разбираются общими
владельцами `media`/`report::css`; сеть не вызывается. Это консервативная
статическая проверка, без выполнения JavaScript или шаблонов Anki.

`compare(A, C, B)` возвращает детерминированный отчёт с путями, хешами трёх
сторон, конфликтами и разрешёнными именами/моделью/`ord` для полей:

| `disposition` | Состояние |
| --- | --- |
| `unchanged` | C и B равны A |
| `input_only` | изменился только C |
| `working_only` | изменился только B |
| `converged` | обе стороны изменились и пришли к одному результату |
| `diverged` | изменились обе стороны без доказанного пересечения |
| `conflict` | различаются результаты правки одной единицы либо удаление сущности пересеклось с её изменением или созданием/изменением связи с ней |

Модель/конфигурация — консервативная единица сравнения целиком: две разные правки
одной модели могут дать конфликт. Смена или удаление существующей схемы `flds`,
типа модели или состава позиций шаблонов
отмечается отдельно как `incompatible: model_layout:<uuid>`; смена модели
существующей заметки — как `note_model:<path>`. Они требуют другого владельца
миграции. В текущую консервативную схему входит полное определение `flds`,
включая `description`: изменение подписи поля тоже требует отдельного согласования,
хотя подпись не определяет смысл значения поля.
Неоднозначный `ord`, неразрешённая модель, повторный GUID,
отсутствующая идентичность, конфликтующие определения отвергаются ещё при
построении снимка. Идентичности разных профилей/колод сравнивать нельзя.

Слоя merge нет. `removed` в таком отчёте означает отсутствие в JSON; это не
доказательство и не обещание физического удаления заметки в Anki.

## Операции и сохраняемое происхождение

`ExchangeStore::initialize(root)` явно создаёт приватный каталог
`decks/.exchange/` с правами 0700. `open(root)` только открывает существующее
состояние. Единственный постоянный файл — `revisions.json`: метка владельца,
версия схемы 1, случайный ID хранилища, поколение, checksum и потоки по хешу
идентичности. Для каждого потока сохраняются фиксированный путь `output`,
текущий подтверждённый C с номером и свидетельством, база A рабочей копии и
последнее подтверждение публикации B. Число снимков ограничено текущим и базовым
на колоду; это индексы, без истории полных экспортов. Всё состояние игнорируется
Git вместе с `decks/` и не требуется в чистом clone.

Метаданные записываются компактным JSON; прежний JSON с отступами также читается.
Размер общего файла ограничен 256 MiB. Снимки всех колод читаются и сохраняются
вместе, поэтому стоимость операции растёт с суммарным числом смысловых единиц.
Превышение лимита даёт `Blocked` с фактическим и предельным размером до записи,
сохраняя прежнее состояние. Разбиения хранилища по колодам этот API не выполняет.

Последняя публикация различает `based_on_sequence` (исходная база рабочей копии),
`checked_input_sequence` (C, проверенный перед импортом) и `confirmed_sequence`
(подтверждённый readback). Повторное подтверждение семантически того же входа
не подменяет исходное происхождение рабочей копии более поздним номером.

| Операция | Реальное действие |
| --- | --- |
| `read` | перечитать, проверить состояние и выдать `StateView` с CAS-токеном |
| `record_input(token, Confirmation)` | сохранить новый подтверждённый C, сохранив прежнюю базу A |
| `plan_preparation(identity)` | прочитать фактический B и выдать решение, без записи |
| `record_prepared(plan)` | после внешней подготовки проверить token, C и фактический output == C, затем зафиксировать базу |
| `plan_publication(identity)` | проверить актуальность A == C, совместимость и фактический B; выдать permit без объявления успеха |
| `record_published(permit, readback)` | после живого импорта проверить новое подтверждение и фактический B, сохранить успешную публикацию, продвинуть C и базу |

Решения подготовки:

| Предусловия | `action` |
| --- | --- |
| нет базы и output, C доказан | `prepare_first` |
| B == A, изменился только доказанный совместимый C | `refresh_unchanged` |
| C == A, B неизменён или изменён доказанно совместимым образом | `keep` |
| существующий output без базы, пропавший output при наличии базы, обе стороны изменились, несовместимость или недоказанность | `blocked` |

Даже `converged` не продвигает происхождение автоматически. План содержит
наблюдённую ревизию B и путь назначения; его тип нельзя десериализовать как
разрешение, а поля, определяющие допуск, закрыты для изменения.
`record_prepared` принимает только разрешающий план и заново проверяет фактический
output. Будущий владелец переноса обязан до любого изменения получить этот план,
захватить общую `write::ExportLock` и повторно проверить исходник. Чтение плана
само по себе не блокирует параллельное редактирование B до будущей записи.
При вызове методов обмена нельзя уже удерживать `ExportLock`: порядок блокировок
состояние → экспорт; подготовку и подтверждение разделяют отпусканием блокировки.

`record_input` с тем же номером, снимком и свидетельством и свежим токеном даёт
no-op без перезаписи. Меньший номер либо другое содержимое с прежним номером
отвергаются. Новая операция требует токена последнего `read`: просроченные планы
и токены дают `StaleState`. После успешной подготовки повторное планирование
возвращает `keep`. Повторная передача старого permit после изменения поколения
отвергается; после неизвестного результата сначала перечитайте `read` и
сверьте сохранённый номер/свидетельство, вместо слепого повторения операции.

Подтверждение публикации требует readback от доверенного адаптера с той же
идентичностью, новым монотонным номером и семантически ровно отправленным B.
Сам B тоже перечитывается: изменение после permit блокирует подтверждение.
Если Anki преобразовал результат, публикация здесь не объявляется успешной:
зарегистрируйте наблюдённый снимок отдельно как новый C и разберите расхождение.
Без реального адаптера `Confirmation` используется только в синтетических
тестах. Непустая строка `evidence` не устанавливает факт работы живой Anki:
за достоверность подтверждения отвечает вызывающий доверенный компонент.

## Целостность, конкуренция и восстановление

Вся операция чтения/изменения состояния удерживает межпроцессный advisory flock
на устойчивом каталоге `.exchange`, не на заменяемом JSON. Каждая мутация
перечитывает checksum и проверяет CAS-токен всего состояния под этой блокировкой.
Независимые потоки/процессы с одним токеном не могут оба записать результат.
Снимки проверяются по внутренним хешам, идентичностям, происхождению, диапазонам
номеров и соответствию ключей потоков; несовместимая версия, неполное состояние
и коллизии привязок дают отказ. Каталоги привязаны открытыми дескрипторами;
замена `decks` или `.exchange` диагностируется уже открытым хранилищем.

Чтение идёт по dirfd с `NOFOLLOW`, включая все промежуточные компоненты. Symlink,
hardlink файлов, FIFO, устройства, вложенные каталоги media, выходы через `..`
и имена не UTF-8 отвергаются. Физическое чтение ограничено 256 MiB на файл,
1 GiB суммарного media и 16384 файлами. В памяти от доверенного адаптера
принимаются уже собранные данные. `/proc/self/fd` используется только для
собственных дескрипторов при листинге и общей атомарной записи проекта.

Запись использует существующий `write::replace_document_atomically`: уникальный
temp рядом с целью, полный `write`, `sync_all`, атомарный `rename`; обмен
дополнительно требует успешного `sync_all` каталога. До rename прежний JSON
сохраняется; после ошибки sync результат может быть уже опубликован — сначала
нужно перечитать состояние. Рабочие данные API не пишет даже при отказе.
Остатки temp после аварийного завершения не являются состоянием и не принимаются
как подтверждение; текущий файл перечитывается отдельно. Автоматической очистки
чужих/неполных каталогов и автоматического сброса метаданных нет.

Это граница программного владения, а не OS-level sandbox. Код под тем же
пользователем способен напрямую читать `input`, подделать свидетельства,
переписать метаданные или игнорировать advisory lock. SHA обнаруживает случайное
повреждение, но не заменяет аутентификацию. Полностью согласованный откат всего
файла состояния без внешнего известного номера невозможно отличить от прошлого
состояния; доверенный адаптер обязан сохранять собственный монотонный номер.
При повреждении следует сохранить артефакт для диагностики и восстановить
проверенную резервную копию либо явно заново согласовать базу с экспортами;
назначать существующую рабочую копию новой базой по догадке нельзя.

## Проверка и будущая интеграция

`cargo test -p anki-repo --test integration exchange_contract --locked` исполняет
синтетический цикл V1→V2→V3, A/C/B, перезапуск, идемпотентный вход, конкуренцию,
повреждения/устаревание, переименование, разделение профилей, файловые границы,
отказы записи и подтверждение публикации. Фикстуры создаются в системном temp;
тесты не читают фактические `decks/**` или `.asset-store/`. Общий workspace-набор
продолжает проверять запрет input для существующего CLI.

Будущие отдельные компоненты: экспортер Anki→input, владелец подготовки
input→output, импортер output→Anki и подтверждённый readback, привязка старых
экспортов, миграция схем/путей и содержательное согласование конфликтов. Сейчас
нет AnkiConnect, CrowdAnki Python, запуска Desktop, автоматического переноса,
импорта, auto-merge или обхода запрета input.
