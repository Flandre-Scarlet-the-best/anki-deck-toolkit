# Локальная история бенчмарков: `benchmark-history`

**Русский** · [English](README.en.md) · [简体中文](README.zh-CN.md)

`benchmark-history` хранит у каждого пользователя его собственную историю
проверенных результатов бенчмарков, находит в ней базу для сравнения,
сопоставляет «до» и «после» и готовит из результатов раздел
`## Производительность` для описания PR и снимки для страниц производительности
модулей в `tools/<модуль>/performance.md` и их переводов. Он ничего не измеряет:
серии выполняет [`benchmark-runner`](../benchmark-runner/README.md), а модель
результата, его проверку и правила сопоставимости задаёт
[`benchmark-contract`](../benchmark-contract/README.md). Второго формата
результатов и второго измерительного движка здесь нет.

Работает полностью локально: без сети, токенов GitHub, сервера и общей базы.
История одного клона не синхронизируется с чужими, и ни один замер не
публикуется автоматически: раздел PR вставляется в описание PR обычным
процессом [`anki-git-workflow`](../../.agents/skills/anki-git-workflow/SKILL.md), а
снимок документации записывается только по явному `--apply`.

## Где лежит история

| Источник | Путь |
|---|---|
| `--store DIR` | `DIR` |
| `BENCHMARK_HISTORY_DIR` | значение переменной |
| `XDG_DATA_HOME` | `$XDG_DATA_HOME/anki-deck-toolkit/benchmark-history` |
| иначе | `~/.local/share/anki-deck-toolkit/benchmark-history` |

Путь должен быть абсолютным и без компонентов `..`; относительный
`XDG_DATA_HOME` по спецификации XDG недействителен и пропускается. Хранилище внутри рабочей копии Git
отвергается до создания файлов: локальные результаты не должны попадать в `git status` и в коммит.
Проверяется сам путь — ближайший существующий предок с разрешёнными символическими
ссылками и любой каталог выше него с `.git` (клон, worktree, подмодуль), — поэтому
отказ не зависит от текущего каталога, каталога сценариев и того, задан путь
`--store`, `BENCHMARK_HISTORY_DIR` или XDG. То же правило действует для каталога
`backup`.
Ни WSL2, ни Windows-пути, ни systemd не требуются.

```text
<хранилище>/
├── store.json          # формат и версия раскладки архива
├── results/<ab>/<id>.json  # исходные результаты — источник истины
├── index.sqlite        # индекс SQLite — восстанавливаемая проекция архива
├── lock                # исключительная блокировка операций
├── corrupt/            # повреждённые копии, заменённые при restore
└── tmp/                # временные файлы атомарной записи
```

## Архив и индекс

- **Приём.** Документ принимается, только если его пропускает
  `benchmark_contract::result::check` вместе с каталогом `benchmarks/`
  (историческая ревизия сценария допустима с предупреждением, неизвестный
  сценарий — нет). Версия схемы, прогоны, доступность метрик, provenance,
  входы, профиль и окружение сохраняются как есть.
- **Идентификатор** записи — SHA-256 канонической формы JSON (ключи
  отсортированы, без пробелов). Повторный приём того же результата, в том числе
  с другими отступами, пробелами и порядком ключей, дубликата не создаёт. Числа
  не нормализуются: `1` и `1.0` — разные канонические формы и разные ID;
  нормализация изменила бы ID уже принятых записей.
- **Неизменяемость.** Файл хранится побайтно так, как был принят. Имя
  занимается жёсткой ссылкой на полностью записанный и сброшенный на диск
  временный файл: запись атомарна, существующая копия не перезаписывается.
  Повреждённая копия при повторном приёме не заменяется — это ошибка с
  указанием на `verify`.
- **Итоги серий.** Принимаются и `partial`, `failure`, `unsupported`: история не
  скрывает неудачные запуски, но базой для сравнения такие результаты не
  становятся.
- **Индекс SQLite** — производная архива. Сначала пишется архивная копия,
  затем строка индекса; прерывание между ними оставляет запись без строки, и
  следующая команда её доиндексирует. Строка без архивной копии удаляется с
  сообщением. Повреждённый индекс откладывается как `index.sqlite.corrupt` и
  строится заново из архива. Устаревшая схема индекса (`PRAGMA user_version`)
  мигрирует пересборкой из архива; схема новее поддерживаемой — отказ, после
  которого индекс пересобирает `reindex`.
- **Целостность проекции.** `quick_check` и номер схемы не доказывают, что
  проекция цела, поэтому при каждом открытии схема файла сверяется с ожидаемой
  (недостающая или лишняя таблица — схема создаётся заново и заполняется из
  архива), а строки каждой записи — с её контрольной суммой
  `projection_sha256`: запись с несовпавшей суммой удаляется из индекса и
  строится заново из архивной копии. Проверка стоит одного прохода по таблицам
  индекса без чтения JSON. Полную сверку индекса с проекцией архивных JSON
  делает `verify`; расхождение устраняет `reindex`. Архив при этом не
  переписывается.

## Команды

```bash
cargo run -p benchmark-history -- status
cargo run -p benchmark-history -- import target/benchmark-runner/runs
cargo run -p benchmark-history -- list --scenario anki-repo.validate --profile warm --since 2026-10-01
cargo run -p benchmark-history -- show 1a2b3c4d
cargo run -p benchmark-history -- baseline 1a2b3c4d
cargo run -p benchmark-history -- compare 5e6f7a8b 1a2b3c4d
cargo run -p benchmark-history -- report 1a2b3c4d
cargo run -p benchmark-history -- snapshot 1a2b3c4d --page tools/anki-repo/performance.md
cargo run -p benchmark-history -- verify
cargo run -p benchmark-history -- backup /path/to/backup
cargo run -p benchmark-history -- restore /path/to/backup
```

| Команда | Что делает |
|---|---|
| `status` | путь хранилища, источник пути и число записей; хранилище не создаёт |
| `import <путь>...` | принимает файлы результатов; каталоги обходятся рекурсивно, из них берутся только документы, похожие на результат, а `*.rejected.json` исполнителя и символические ссылки на каталоги внутри обхода пропускаются |
| `list` | записи от новых к старым с фильтрами `--scenario`, `--module`, `--revision`, `--profile`, `--outcome`, `--since`, `--until`, `--module-version`, `--commit`, `--input` (префикс идентичности входа), `--env имя=значение`, `--limit` |
| `show <ID>` | сводка записи; `--raw` — исходный JSON архивной копии |
| `baseline <ID>` | каждый кандидат в базу с причинами, почему он подходит или нет, и выбранная база; `--commit` сужает выбор |
| `compare <база> <результат>` | вердикт `benchmark-contract`, «до/после», разности и оценка относительно разброса |
| `report <ID>...` | Markdown-раздел `## Производительность` для PR; `--baseline ID` (на пару «сценарий × профиль»), `--first` или `--commit` |
| `snapshot <ID> --page P` | снимок для страницы модуля `tools/<модуль>/performance.md` и переводов `performance.en.md`, `performance.zh-CN.md`; без `--apply` только показывает |
| `verify` | сверка каждой архивной копии с её идентификатором и контрактом и индекса — с проекцией архива; архив не меняет и хранилище не создаёт (его отсутствие — код 3); что согласование индекса при открытии исправило до сверки, показывается и даёт код 1 |
| `reindex` | пересборка индекса из архива |
| `backup <каталог>` | копия архива в новый или пустой каталог для переноса на другую машину Linux |
| `restore <каталог>` | приём записей резервной копии по инвентарю `backup.json`: имя каждой записи обязано совпадать с SHA-256 её содержимого |

ID принимается полностью или префиксом не короче шести символов. Глобальные
параметры: `--store`, `--catalog` (по умолчанию `benchmarks/` ближайшего
родителя текущего каталога), `--json` — стабильный JSON в stdout.

Перенос: `backup` на одной машине, перенос каталога любым способом (`tar`,
`rsync`), `restore` на другой. Каталог при восстановлении не нужен: совпадение
имени и содержимого доказывает, что запись не изменилась с момента приёма.
`backup` последним атомарно записывает `backup.json` — формат, версию раскладки
и полный инвентарь записей; каталог без него (в том числе прерванная копия) —
не резервная копия, а отдельные `result.json` принимает `import`. `restore`
сверяет состав копии с инвентарём: запись, файла которой нет, изменённая или не
перечисленная в инвентаре, не принимается и указывается в отчёте (`missing`,
`problems`), исправные записи принимаются, а перенос помечается неполным
(`complete: false`, код `4`). Повреждённую локальную копию записи `restore`
заменяет проверенной копией из резервной (`replaced`), а прежний файл
откладывает в `corrupt/`, не удаляя. Повторный `restore` идемпотентен.

Каталог `backup` и источник `restore` не пересекаются с хранилищем: путь,
совпадающий с ним, лежащий внутри него (например, `<хранилище>/results/backup`)
или содержащий его, отвергается до любой записи с кодом `2`. Пути сравниваются
по компонентам после разрешения символических ссылок, включая несуществующий
остаток пути, и по идентичности существующих каталогов: на файловой системе
без учёта регистра (`/mnt/c` в WSL) `STORE/results` — тот же каталог, что
`store/results`. Висячая ссылка отвергается, потому что запись через неё ушла
бы по её цели. Архив, индекс и место назначения при отказе не меняются.

## Автоматическое сохранение из `benchmark-runner`

`benchmark-runner run` после записи принятого результата сам передаёт его в
историю тем же контрактом и каталогом, без повторного измерения. Итог —
поле `history` сводки: `archived`, `already-archived`, `disabled`
(`--no-history`), `failed` с причиной или `not-recorded`, если принятого
результата нет. Отказ истории не стирает `result.json` и не меняет код
возврата серии, но печатается предупреждением и попадает в `warnings`:
результат можно сохранить позже командой `import`.

## База и сравнение

Сопоставимость решает только `benchmark_contract::comparability::compare`:
один сценарий и ревизия, один профиль, одинаковые определения метрик, нагрузка
и значимые факты окружения. Различие входа-`subject` (изменённый код) —
ожидаемое отличие, различие входа-`workload` делает результаты несопоставимыми.

Правило автоматического выбора базы: **самый поздний успешный результат того же
сценария и профиля, записанный раньше проверяемого, с доказанно другим
состоянием кода, если между коммитами изменена не только документация, и
сопоставимый по контракту**. Отличие состояния доказывают разные
`source_tree_sha256`, а если дерево записано не в обоих результатах — разные
коммиты, оба измеренные без изменений рабочей копии (с оговоркой в отчёте).
Отсутствие сведений не считается отличием.

`source_tree_sha256` и коммит описывают весь репозиторий, а не собранную
программу: идентичности исполняемого артефакта в результате нет. Поэтому для
пары коммитов чистых рабочих копий история сверяет состав изменений по Git
репозитория каталога (`git diff --name-only`), сетью не пользуясь. Каждый
кандидат получает поле `code`:

| `code.kind` | Значение | Автоматическая база |
|---|---|---|
| `documentation-only` | изменены только файлы Markdown или ничего: та же реализация, это повтор измерения | нет |
| `files` | изменены и другие файлы; затронута ли измеряемая реализация, данные не доказывают | да, с оговоркой |
| `unverified` | коммита нет в клоне, Git недоступен или измерена рабочая копия с изменениями | да, с оговоркой |
| `not-proven` | отличие состояния не доказано | нет |

`baseline` показывает каждого кандидата и причину отказа: `partial`/`failure`/`unsupported`,
записан позже, тот же `source_tree_sha256` или тот же коммит без изменений
(повтор, а не «до»), отличие кода не доказано, изменена только документация,
блокеры сопоставимости — и общую оговорку: различие состояний репозитория не
доказывает замену измеряемой реализации. Та же оговорка входит в «Вывод»
раздела PR. Конкретную базу можно указать явно (`report --baseline ID`), в том
числе вне правила; отступления от правила перечисляются в отчёте, а база,
совпадающая с проверяемым результатом, отвергается и там, и в `compare`.
Сопоставимость по-прежнему решает только `benchmark-contract`.

- Разность считается по средним успешных прогонов; относительная — только при
  ненулевой базе, в одной единице и одном scope.
- Направление улучшения: для времени, памяти, процессорного времени, диска,
  инструкций, циклов и промахов меньше — лучше; для загрузки ядер, обращений к
  кэшу и счётчиков модуля направление не оценивается.
- Оценка: `в пределах разброса`, если |Δ| не больше суммы стандартных
  отклонений; `сверх разброса` — иначе; `мало повторов`, если хотя бы с одной
  стороны меньше двух измерений. Это **не** проверка статистической
  значимости, и `statistically_supported` контракта означает лишь достаточное
  для оценки разброса число измерений.
- Несопоставимые результаты выводов не получают; `unavailable`, `unsupported`,
  `failed` показываются статусом с причиной, а не нулём.

## Раздел PR

`report` строит раздел по контракту
[`pr-body.md`](../../.agents/skills/anki-git-workflow/references/pr-body.md):
`Статус: измерено` с полями «Сценарий», «Измеренный код» (коммит, признак
изменений, дерево исходников), «Нагрузка» (идентичность и объём входов),
«Окружение», «Прогоны», «База», «Сопоставимость», таблицей метрик, «Вывод»,
«Ограничения» и «Источники» (полные ID записей). Без базы раздел
различает новую функциональность (`--first`: «до» не существует) и
отсутствие пригодной базы. Результат `failure` или `unsupported` даёт
`Статус: не измерено` с причиной, диагностикой и строкой
«Доказательство производительности: отсутствует». Раздел печатается в stdout и
вставляется в описание PR вручную; сам инструмент в GitHub не пишет.

## Снимок документации

`snapshot` заменяет на странице модуля блок той же пары «сценарий × профиль» и
одновременно его переводы (`performance.en.md`, `performance.zh-CN.md`); новая пара
добавляется перед строкой `<!-- benchmark-snapshot:anchor -->`. В блоке — дата,
версии, факты окружения, объём нагрузки, записанные параметры, влияющие на
сопоставимость (например, `writers`), и метрики, но не коммит, не ID записи,
не идентичность входа и не пути. Параметры входят в маркер как часть
определения нагрузки: снимок с другими их значениями прежний не заменяет без
`--replace-workload`. Отказ без записи:

- итог не `success` или результат устаревшей ревизии сценария;
- рабочая копия с изменениями или без записанного состояния (разрешает
  `--allow-dirty`, и это видно в блоке);
- эталонное окружение не определено: неизвестен аппаратный или платформенный
  факт (`os`, `arch`, `virtualization`, `cpu_model`, `logical_cpus`,
  `memory_total_bytes`) или факт сопоставимости сценария;
- на странице снимок из другого эталонного окружения (смену эталона
  подтверждает `--replace-environment`), на нагрузке, тождество которой с
  новой не доказано (подтверждает `--replace-workload`), или более новое
  измерение.

Одинаковый объём нагрузки тождества входа не доказывает: два разных экспорта
могут совпадать по байтам и числу заметок. Идентичности входов на странице не
хранятся, поэтому доказательство — результат прежнего снимка в локальной
истории: другой результат той же пары, который даёт в точности блок на
странице (маркер с моментом записи, эталонным окружением и объёмом нагрузки,
версии, метрики), с теми же идентичностями входов роли `workload`. Публикуемый
результат доказательством не служит, даже если он в истории: иначе новый
результат того же объёма, записанный в ту же секунду, подтвердил бы прежний
снимок сам. Если такой результат есть и идентичности совпали, снимок
заменяется без флага. Нужен `--replace-workload`, если идентичности
различаются; блок на странице дают несколько результатов истории с разной
нагрузкой; результата нет в истории (другая машина, очищенная история); блок
не совпадает ни с одним результатом (изменён вручную или сгенерирован другой
версией генератора); маркер без записанной нагрузки. Совпавший текст блока
проверку не обходит: повторный `snapshot` уже опубликованного результата без
другого результата истории с тем же блоком отказывает, а с
`--replace-workload` сообщает, что снимок уже актуален, и ничего не пишет.
Сообщение отказа называет только ID входов, без идентичностей. Действие плана
(`plan.action`: `added`, `replaced`, `unchanged`) и его основание
(`--json`: `plan.workload`; текст: строка `нагрузка:`) — `new`, `no-workload`,
`proven-by-history` или `confirmed-replacement`; основание указывают в PR
вместе с применёнными флагами.

Эталонное окружение снимка шире условия сопоставимости: аппаратные и
платформенные факты входят в него всегда, даже если сценарий их не сравнивает,
поэтому измерение на другом процессоре, с другим объёмом памяти или после
смены WSL2 на Linux без виртуализации прежний публичный эталон молча не
заменяет, а сравнение результатов от этого не становится строже. Факт,
которого нет в прежнем маркере, и маркер без записанной нагрузки
совпадающими не считаются: замену подтверждает соответствующий флаг.

Три страницы записываются согласованно: пока не подготовлены временные копии
всех трёх, ни одна страница не меняется; затем они заменяются по одной
переименованием (RU, EN, zh-CN), и при отказе уже заменённые возвращаются к
прежнему тексту. Если не удался и возврат, ошибка называет обновлённые и
необновлённые страницы. Страница, изменённая после подготовки, не
перезаписывается. Прерванный между переименованиями процесс оставляет переводы
с отметкой `i18n-source-git-blob` прежнего русского текста, и это видит
проверка документации.

Отметка `i18n-source-git-blob` переводов обновляется, только если перевод был
подтверждён для прежнего русского текста.

## Коды возврата

| Код | Значение |
|---|---|
| `0` | успех |
| `1` | отрицательный ответ: несопоставимо, пригодной базы нет, `verify` или `reindex` нашли проблемы, снимок отвергнут |
| `2` | неверные аргументы, неизвестный или неоднозначный ID, хранилище или резервная копия внутри рабочей копии Git, резервная копия пересекается с хранилищем, база совпадает с проверяемым результатом |
| `3` | хранилище, индекс или каталог недоступны |
| `4` | документ отвергнут контрактом и не принят; резервная копия перенесена не полностью |
| `5` | архивная копия записана, индекс не обновлён: выполните `reindex` |

## Приватность

Принимаемый результат уже прошёл проверку контракта: абсолютных путей,
секретов и сырого вывода в нём нет. Хранилище — локальные данные пользователя
вне репозитория; его не коммитят и не публикуют. В раздел PR попадают коммит
и идентичности входов (их в PR указывать допустимо и полезно), в
документацию — нет.

## Проверки

Тесты (`tests/history.rs`) строят синтетический каталог и результаты во
временном каталоге: идемпотентный приём и исходные байты, отказ невалидным,
чувствительным и неизвестным документам, удалённый, повреждённый, устаревший и
слишком новый индекс, индекс без обязательной таблицы и с подменённой строкой,
прерванная запись и посторонние файлы, повреждённая архивная копия, перенос
через `backup`/`restore` в другое хранилище и неполная или изменённая копия,
резервная копия внутри хранилища, через символическую ссылку, висячую ссылку,
путь в другом регистре на файловой системе без учёта регистра (каталог задаёт
`BENCHMARK_HISTORY_TEST_CASE_INSENSITIVE_DIR`, иначе проверяется системный
временный каталог, а с учётом регистра проверка пропускается с сообщением)
и в каталог-предок без изменения архива, хранилище внутри рабочей копии Git
при запуске из внешнего каталога, правила выбора базы и доказательство
отличия кода, изменение только документации против изменения кода в настоящем
репозитории Git, неизвестный коммит и явная база, единицы, нулевая база и
разброс, раздел PR во всех ветках с проверкой настоящим
`.github/scripts/check_pr_body.py`, снимок документации с отдельным эталонным
оборудованием, маркером без записанной нагрузки, тождеством нагрузки
одинакового объёма, отказом считать публикуемый результат доказательством
прежнего снимка, совпавшим блоком при другой нагрузке, сценарием без нагрузки
и отказом записи одной из трёх страниц и CLI целиком. `decks/**` и каталог данных пользователя тесты не читают.
