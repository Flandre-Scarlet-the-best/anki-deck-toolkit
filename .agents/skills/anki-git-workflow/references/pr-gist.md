# Подробный отчёт в Gist для PR

Это справочный документ skill `anki-git-workflow`. Смысловую структуру body
задаёт [`pr-body.md`](pr-body.md), публикацию PR — [`pr-lifecycle.md`](pr-lifecycle.md).
Этот файл описывает исключительно подробное приложение в GitHub Gist.

## Когда выносить подробности

Используй Gist, если описание распухло из-за нескольких серий бенчмарков,
обширной технической диагностики, длинной истории исправлений или повторяющихся
таблиц. Для небольших PR Gist не нужен. **Сначала проверь, нет ли подходящих
постоянных страниц `docs/` или `tools/*/performance*.md` в репозитории**:
канонические результаты лучше не копировать в сторонний документ.

Основное тело PR остаётся самостоятельным: цель, границы изменений, важнейшие
инженерные решения, реально выполненные проверки, значимые результаты,
ограничения, CI и готовность должны пониматься **без переходов по ссылкам**.
Не сокращай PR до пары строк. Не удаляй обязательные заголовки. При
`Статус: измерено` оставляй в PR проверенные отчёты, покрывающие основные
изменённые пути и существенные регрессии: валидатор требует все поля и таблицу
с числовыми значениями для каждого оставленного измеренного `###`-сценария.
Ссылка не заменяет evidence, не прячь ухудшения в приложении.

**Для CodeRabbit действует обязательное исключение:** полный накопительный
журнал и таблицу держи **в Gist**, а в PR оставляй короткую сводку по
[`pr-body.md`](pr-body.md). Уже существующую таблицу в PR переносить
только после верификации полного содержимого опубликованного Gist.

## Приватность и допуск к публикации

`gh gist create` без `--public` создаёт **Secret Gist**. Он не включён в
публичный каталог, но доступен любому обладателю ссылки: из публичного PR
его может прочитать любой. Аккаунт автора Gist тоже виден. Это не хранилище
секретов. История правок может сохранить раннюю версию текста.

Перед отправкой проверь содержимое на токены, ключи, cookie, приватные email,
персональные пути, имена пользователей, hostname, IP/геолокацию, реальные
колоды и данные пользователя. Не включай локальные логи целиком без проверки.
Сохраняй только технические параметры, действительно важные для
воспроизводимости, и прямо отмечай редактирование несущественных идентификаторов.
Если непонятно, безопасен ли текст, **не публикуй**.

## Структура полного Markdown-отчёта

Создавай **один Gist на work item** и обновляй его в следующих итерациях.
Для общего отчёта используй `details.md`, для CodeRabbit —
`coderabbit-review.md` **в том же Gist**. При отсутствии общего отчёта
Gist может содержать только `coderabbit-review.md`.
Не создавай новый Gist из-за очередной итерации.

- Заголовок `# Подробный технический отчёт: <суть>`, короткое назначение,
  ссылка на существующий PR либо репозиторий и указание, что сводка — в PR.
- Для длинного текста — оглавление с Markdown-якорями и тематические разделы.
- Технический контекст, архитектурные решения, сравнение вариантов.
- Полные проверки с указанием исходного HEAD, команд, реально полученных
  результатов и источников. Не подменяй `NOT_RUN` словом `PASS`.
- Дополнительные измерения с ревизией сценария, нагрузкой, базой,
  единицами, происхождением результатов, выводами и ограничениями.
- Содержательная история исправлений, воспроизводимость и остаточные риски;
  отличай гипотезы от подтверждённых фактов.

### Полный накопительный журнал CodeRabbit

Файл `coderabbit-review.md` в существующем Gist хранит **единственную
полную таблицу** для текущего PR, с заголовком:

```markdown
| Итерация / reviewed HEAD | Уровень | Путь | Влияние | Решение | Исправление |
| --- | --- | --- | --- | --- | --- |
| 1 · `abcdef012345` | major | `src/example.rs` | Возможная потеря данных | confirmed | Исправлено в `1234567abcde` |
```

После каждой completed iteration **добавляй** новые записи, сохраняя старые:
номер итерации и фактически проверенный HEAD, provider severity, путь,
технический эффект, независимое disposition (`confirmed`,
`partial`, `false positive`, `stale/repeated`), реальный результат
и fix/marker commit. Для завершённого `0 findings` запиши одну строку
с `clean` и опубликованным marker commit; если findings были отклонены,
оставь их строками с фактическим решением. Не записывай сырой transcript и
`codegenInstructions`. Коммит исправления текущей итерации не является
её reviewed HEAD.

При миграции старого PR с таблицей: считай весь опубликованный body,
перенеси **каждую** исходную строку (включая пустые ревью и повторы) в
`coderabbit-review.md`, сравни число и содержание записей с первоисточником;
только после проверенного Gist убирай таблицу из PR. Если в PR было несколько
таблиц (например, отдельные циклы), сохрани их порядок и границы циклов
подзаголовками в одном журнале, не выбрасывай прежние итерации.

Если уже существует Gist с техническим отчётом, **добавь файл** к нему,
а не заменяй `details.md`. Если Gist содержит журнал, используй его как
recovery baseline и согласуй с локальными данными до правки. Не повторяй
публикацию вслепую после неизвестного результата API.

Не дублируй целиком код, README или данные, уже доступные по постоянным
ссылкам в репозитории. Пиши по-русски, машинные идентификаторы не переводи.
В списке `All gists` показывается лишь короткое превью: читай отдельный Gist.

## Команды `gh` в Linux/WSL2

Перед созданием проверь активный GitHub аккаунт и доступные команды:

```bash
gh auth status
gh gist create --help
gh gist edit --help
gh gist view --help
```

Если не хватает разрешения `gist`, штатный способ —
`gh auth refresh -s gist`. Не печатай токены или переменные окружения с ними.

Подготовь Markdown в локальном **игнорируемом Git** файле
`.codex/local/pr/<task>/details.md`. Перед отправкой проверь, что он не
отслеживается (`git check-ignore -v`, `git ls-files`), перечитай его и
проверь приватность. Не добавляй его в commit.

Для новой публикации (Bash в Linux/WSL2):

```bash
DETAIL_FILE=".codex/local/pr/<task>/details.md"
GIST_URL="$(gh gist create "$DETAIL_FILE" --desc "Подробный технический отчёт к PR")"
gh gist view "$GIST_URL" --raw --filename "$(basename "$DETAIL_FILE")"
```

По умолчанию Gist секретный, **не добавляй `--public` автоматически**.
Убедись, что URL действительно возвращён, Gist доступен, а `--raw`
совпадает с исходным текстом. При сетевой ошибке сначала проверь через
`gh gist list --secret`, не создавай дубликат вслепую.

Следующие исправления **в том же Gist**, не новая публикация:

```bash
gh gist edit "$GIST_URL" --filename "$(basename "$DETAIL_FILE")" "$DETAIL_FILE"
gh gist view "$GIST_URL" --raw --filename "$(basename "$DETAIL_FILE")"
```

Для CodeRabbit-файла: если файл уже есть, обнови его через
`gh gist edit "$GIST_URL" --filename coderabbit-review.md "$REVIEW_FILE"`;
если его ещё нет в **существующем** Gist, используй
`gh gist edit "$GIST_URL" --add "$REVIEW_FILE"`, предварительно
установив поддержку флага установленной версией и проверив имя добавленного
файла (`gh gist view "$GIST_URL" --files`). Для нового Gist можно вызвать
`gh gist create "$REVIEW_FILE" --desc "Журнал CodeRabbit к PR"`.
После каждого действия считай `gh gist view "$GIST_URL" --raw --filename
coderabbit-review.md` и сравни с локальным Markdown. `REVIEW_FILE` — локальный
игнорируемый Git файл `.codex/local/pr/<task>/coderabbit-review.md`.

Перед edit получи и сохрани текущий Gist и проверь, что никто не внёс
неизвестные изменения; после edit сравни опубликованный текст с локальным.
При изменении имени файла учти флаги фактической версии CLI.

Если PR ещё не создан, опубликуй отчёт без фиктивного PR-URL, создай PR со
ссылкой на реальный Gist, затем при необходимости добавь обратную ссылку
на PR в Gist. Если PR открыт, используй его фактический URL сразу.

## Согласование с PR, проверка и восстановление

1. Сохрани полный актуальный body PR локально вместе со старой таблицей
   CodeRabbit, если она есть; сравни с рабочим source. Считай также текущий
   Gist и сохрани его содержимое до edit.
2. Перенеси в Gist подробности и весь журнал CodeRabbit, оставив в PR ключевые
   инженерные выводы, ограничения, доказательства и контекстные ссылки.
3. Дай ссылки с конкретным названием, например «Дополнительные серии
   измерений»; предпочитай ссылку на каноническую документацию, если она есть.
4. После read-back полного Gist сверь число и состав строк журнала,
   отсутствие потерь/дубликатов и фактические решения. Запусти
   `python3 .github/scripts/check_pr_body.py --body-file <путь>`
   для полного локального PR body. Проверь смысловые факты отдельно.
5. Убедись в доступности Gist и отсутствии фиктивных ссылок **до** изменения
   PR. Публикуй body только из проверенного Markdown-файла штатным
   `gh pr create/edit --body-file` либо через GitHub-коннектор с read-back.
6. После mutation перечитай полный опубликованный PR, проверь exact base/head,
   Draft/Ready, ссылки, статус hosted CI, краткую сводку CodeRabbit и совпадение
   текста с источником. Повторно сверь удалённый Gist. Локальный PASS не
   означает hosted PASS.

Если Gist невозможно создать из текущей среды (например, коннектор GitHub не
умеет записывать Gist), не утверждай, что операция выполнена, и не помещай в
PR несуществующий URL. Сохрани черновик, сообщи ограничение либо используй
уже существующие документы. Смена на Google Drive без поручения не допускается.
