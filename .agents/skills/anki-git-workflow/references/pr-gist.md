# Подробный отчёт и журнал CodeRabbit в Gist

Это справочник `anki-git-workflow` о формате, безопасности, публикации и
восстановлении GitHub Gist. Структуру PR body задаёт [`pr-body.md`](pr-body.md),
а порядок GitHub-операций, источник body и его повторное чтение —
[`pr-lifecycle.md`](pr-lifecycle.md).

## Обязательный Gist

Каждый содержательный ручной PR имеет один актуализируемый Gist независимо
от размера, наличия CodeRabbit, измерений или документации. Короткий body без
Gist и длинный body со ссылкой одинаково не соответствуют контракту.
Постоянные страницы docs остаются владельцами постоянной документации;
Gist хранит подробности и подтверждения конкретной задачи.

Тело PR самодостаточно: цель, решения, результаты, все существенные ухудшения,
ограничения, CI и готовность понятны без перехода по ссылке.

## Состав публичного отчёта: без служебной информации

Gist — инженерный отчёт для читателя PR. **Служебную информацию агента
публиковать запрещено**: сырой stdout/stderr тестовых раннеров, логи сборки,
source-audit/diff, ответы GitHub API, снимки ruleset, транспортные payload,
внутренние планы, временные пути и журналы действий. Эти подтверждения остаются
локальными. Не добавляй файлы `python-tests.txt`, `cargo-tests.txt`,
`source-audit.txt` и их аналоги под другим названием.

В Gist оставляй только содержательный `details.md`, компактный `manifest.md`,
неизменённые исходные benchmark-отчёты и, после завершённых итераций,
`coderabbit-review.md`. Результаты проверок описывай кратко в details; manifest
фиксирует их сводку и хеши локальных подтверждений, а не публикует их содержимое.
Исходный body сохраняй локально; не дублируй его целиком в Gist, когда его
существенное содержание уже перенесено в отчёт. Не превращай details в
копию служебных файлов. Перед публикацией проверь полезность каждого файла
для читателя, убери дублирование и внутреннюю кухню.

## Приватность

`gh gist create` без `--public` создаёт Secret Gist. Он не включён в публичный
каталог, но доступен любому обладателю URL; ссылка в публичном PR делает его
доступным читателям PR. Secret Gist — не хранилище секретов, а история правок
может сохранить прежние версии.

Перед публикацией проверь весь локальный материал на токены, ключи, cookie,
персональные данные и пути, имена пользователей, hostname, IP/геолокацию,
реальные колоды и данные пользователя. Не выгружай локальные логи целиком без
проверки. Если безопасность содержимого неясна — не публикуй его.

## Формат файлов

Создавай **один Gist на задачу** и обновляй его при последующих изменениях:

- `details.md` — обязательный содержательный технический отчёт;
- `manifest.md` — обязательный инвентарь подтверждений по контракту ниже;
- `coderabbit-review.md` — единственная полная накопительная таблица замечаний CodeRabbit.

Gist только с `coderabbit-review.md` не допускается. Если в Gist уже есть `details.md`,
добавь к нему файл журнала, не заменяй и не удаляй остальные файлы.

Технический отчёт содержит назначение, ссылки на репозиторий/PR (только если они
уже существуют), команды и фактические результаты проверок, дополнительные
измерения, выводы и ограничения. Не записывай гипотезы как подтверждённые факты.

Журнал CodeRabbit сохраняет все итерации и замечания провайдера, включая
`false positive`, `stale/repeated` и `clean`, в исходном порядке:

```markdown
| Итерация / reviewed HEAD | Уровень | Путь | Влияние | Решение | Исправление |
| --- | --- | --- | --- | --- | --- |
| 1 · `abcdef012345` | major | `src/example.rs` | Возможная потеря данных | confirmed | Исправлено в `1234567abcde` |
```

После каждой завершённой итерации добавляй все замечания с фактическими severity,
путём, эффектом, независимым disposition и результатом/commit исправления. Для
`0 findings` добавь одну строку `clean` с опубликованным commit-маркером. Если
исправлений нет, укажи commit-маркер в колонке «Исправление» хотя бы одной строки
итерации, включая итерации только с отклонёнными замечаниями. Не записывай
сырой transcript или `codegenInstructions`; commit исправления не является reviewed
HEAD этой же итерации.

При переносе старой таблицы PR сначала сохрани каждую строку и границы её таблиц
в Gist, включая повторы и пустые итерации. Сверь состав и порядок с body и только
после повторного чтения Gist переходи на компактную сводку PR. Не веди две авторитетные
таблицы параллельно.

## Проверяемый Markdown-индекс

**Все опубликованные файлы Gist — только `.md`.** JSON, TXT, LOG, ZIP и
другие служебные вложения запрещены. Запрещено обходить это переименованием
сырых логов, diff или API-ответов в `.md`. Машинный индекс тоже читаемый
Markdown, без JSON, замаскированного расширением.

`details.md` раскрывает назначение, технические результаты, существенные
проверки и ограничения. Нужны заполненные `## Назначение`, `## Технические
результаты`, `## Проверки и источники`, `## Ограничения`, связь с repository,
задачей, текущим полным HEAD и — после создания PR — его точным URL
`https://github.com/<owner/repo>/pull/<number>`. Убирай дубли и служебную хронологию.

`manifest.md` — компактный индекс подтверждений со строками `Схема: 2`,
`Репозиторий: owner/repo`, `PR: число` (до создания — `не создан`), `HEAD: полный
SHA`, `База: ref`, `Ветка: ref`, `Задача: назначение` и таблицами:

- `## Файлы`: `Файл | Тип | Commit | SHA-256`. Все файлы кроме самого индекса
  ровно один раз. Типы только `details`, `benchmark-report`, `review-log`.
- `## Проверки`: `Проверка | Commit | Код | SHA-256 локального подтверждения`.
  Краткий результат и хеш реального локального вывода; сам вывод не публикуется.
- `## Измерения`: `Файл | Сценарий | База | Кандидат | Результат | Регрессии`.
  Полные SHA измеренных состояний, компактный числовой результат как в PR,
  все существенные ухудшения (фрагменты исходного отчёта разделены точкой с запятой
  и одним пробелом; либо `нет`). Фрагменты не должны содержать символ `|`:
  валидатор также сопоставляет их с исходным текстом отчёта.
  Без базы — `нет`. Исходные ID серий уже находятся в полных benchmark-отчётах.
- `## CodeRabbit`: `Итерация | Reviewed commit | Published commit | Строк журнала`.
  Все завершённые итерации по порядку и фактическое число их строк; при нуле
  итераций таблица без данных, фиктивный журнал не создаётся.

Таблица всегда имеет заголовок и Markdown-разделитель, даже при отсутствии
строк. Исходники выбирай по реальным результатам команд и истории; не составляй
ожидаемый состав только по тексту модели. Полные benchmark-отчёты сохраняй без
изменения чисел. Полезность отчёта, полноту регрессий и связь измеренного кода
с текущей реализацией проверяют агент и ревьюер.

`check_pr_gist.py` различает два вопроса, и успех одного не подменяет другой.

Проверка **кандидата** до изменения существующего PR: локальный body сверяется
с Gist и текущими HEAD/refs PR; опубликованное описание при этом может ещё быть
прежним, и вывод прямо говорит, что оно не проверялось:

```bash
python3 .github/scripts/check_pr_gist.py --body-file <body.md> \
  --repository <owner/repo> --pr-number <number> \
  --expected-manifest <manifest.md> --source-dir <каталог-отчётов> \
  --check-sources <локальный-индекс-логов.json>
```

Проверка **опубликованной пары** после `create/edit`: те же аргументы и
`--published`. Тогда проверяется фактически опубликованный body, а локальный
кандидат обязан с ним совпасть (с точностью до переводов строк и завершающего
перевода строки); расхождение — отказ «опубликованное описание отличается от
локального кандидата». Без `--body-file` проверяется только опубликованное
состояние. Завершённой публикацию делает только успех с `--published`.

Локальный JSON сопоставляет имена проверок с путями к исходным выводам команд.
Он остаётся локальным; пути и логи не попадают в Gist. Gate сверяет их SHA-256,
публичные Markdown-файлы и весь ожидаемый индекс. CI без локальных источников
проверяет структуру, привязки и инвентарь; хеш не доказывает истинность вывода.

До создания PR вместо номера передай `--head-sha`, `--base-ref`, `--head-ref`:
gate проверяет кандидата по реальной опубликованной ветке, в manifest при этом
`PR: не создан`. Переход к финальному состоянию — по § «Связь Gist и PR».

GitHub REST API читается только как данные. Repository endpoints используют
GH_TOKEN/GITHUB_TOKEN; доступный по URL Gist читается без токена. Сеть, 403/404,
rate limit, неверные полномочия, повреждённые/частичные ответы, redirect и
truncated дают отказ. Усечённый ответ не объявляется полным. CI-раздел body
содержит актуальный HEAD в code span не короче 12 hex.

Два GET должны вернуть одинаковые файлы и одну версию Gist; PR не должен менять
body/HEAD/refs/state. Перед edit сравни предыдущую удалённую базу, сохраняй чужие
правки. API edit не является атомарным compare-and-swap; при гонке повтори полную
проверку. Смысловую и абсолютную полноту эти проверки не доказывают.

В CI (`--event-path`) событие задаёт только идентичность PR и HEAD, проверяется
опубликованное состояние. Публикация commit и актуализация Gist/body — отдельные
шаги, поэтому распознанное переходное состояние того же HEAD (раздел CI ещё
называет прежний HEAD; manifest описывает предыдущий commit этой ветки, что
подтверждается сравнением через API; manifest ещё без номера созданного PR;
body/Gist изменились во время чтения) перечитывается не дольше 180 секунд с
интервалом 20 секунд. Успех — только полная проверка того же HEAD, что и событие;
по истечении окна — отказ. Смена HEAD, невалидный body, порча или отсутствие
файлов Gist, commit вне истории ветки, сеть и полномочия отказывают сразу.

## Подготовка и интерфейс `gh`

Создавай локальные файлы только при реальной операции публикации. Храни их в
игнорируемом Git каталоге, например `.codex/local/pr/<task>/`; до использования
проверь ignore-правило (`git check-ignore -v`) и отсутствие файла в индексе Git.
Не добавляй эти файлы в commit.

Проверь активную учётную запись и фактический интерфейс установленной версии:

```bash
gh auth status
gh gist create --help
gh gist edit --help
gh gist list --help
gh gist view --help
```

Если у токена нет разрешения `gist`, штатный способ запросить его — `gh auth refresh -s gist`.
Не выводи токены или содержащие их переменные окружения. Примеры ниже приведены
для Bash в Linux/WSL2; требования к подтверждению, сравнению и сохранности файлов
не зависят от оболочки. Для PowerShell используй эквивалентное сохранение вывода
и побайтовое сравнение, не печатай тело Gist при успешной проверке.

## Повторное чтение без вывода полного журнала

После чтения или каждой операции сохраняй **полный удалённый файл** в игнорируемый
локальный путь и сравнивай его целиком с исходником. Одного кода возврата операции,
checksum без сравнения с исходным файлом или количества строк недостаточно.

Пример для одного файла в Bash:

```bash
set -euo pipefail
TASK_DIR=".codex/local/pr/<task>"
REVIEW_FILE="$TASK_DIR/coderabbit-review.md"
REMOTE_FILE="$TASK_DIR/remote-coderabbit-review.md"
GIST_URL="<проверенный Gist URL>"

gh gist view "$GIST_URL" --files
gh gist view "$GIST_URL" --raw --filename "coderabbit-review.md" > "$REMOTE_FILE"
if cmp -s -- "$REVIEW_FILE" "$REMOTE_FILE"; then
  printf 'Повторно считанный coderabbit-review.md совпадает с локальным источником.\n'
else
  printf 'Считанный файл различается; публикацию не считать подтверждённой.\n' >&2
  diff -u -- "$REVIEW_FILE" "$REMOTE_FILE" | sed -n '1,100p' || true
  exit 1
fi
```

При успехе в вывод попадает только итог. При расхождении покажи ограниченный
дифф для диагностики; полное содержимое читай только если оно необходимо для
согласования конфликта. Для Gist с несколькими локально управляемыми файлами
повтори чтение и полное сравнение отдельно для **каждого** файла. Сначала
проверь `gh gist view <id-or-url> --files`; неизвестные файлы сохраняй и не
удаляй. Не затирай `details.md` при обновлении журнала.

## Создание и обновление

Публикуй только после проверки приватности и подготовки полного Markdown-исходника.
Без `--public` Gist остаётся Secret. Для первого создания передай обязательные
`details.md` и `manifest.md` и, если итерации ревью уже завершены, журнал и
прочие необходимые отчёты. Имена файлов берутся из их basename:

```bash
TASK_DIR=".codex/local/pr/<task>"
GIST_URL="$(gh gist create "$TASK_DIR/details.md" "$TASK_DIR/manifest.md" --desc "Подробный отчёт задачи")"
printf 'Gist создан: %s\n' "$GIST_URL"
```

При нуле итераций `coderabbit-review.md` не создаётся. Если итерации или
измерения уже есть, добавь соответствующие подготовленные Markdown-файлы в
тот же вызов создания, чтобы manifest описывал фактический состав.

Сразу проверь файлы и повторно прочитай их по процедуре выше. Сохрани реальный ID/URL в заметках задачи; не публикуй PR со ссылкой до
подтверждённого сравнения.

Перед edit сначала прочитай список файлов и сохрани локально каждый нужный
удалённый файл. Сверь удалённую версию с локальной базой. Если в Gist появились
неизвестные правки или локальная история с ней расходится, остановись и явно
согласуй версии; не перезаписывай изменения и не переставляй/дублируй замечания.
Подготовь новый полный исходник с сохранением прежних строк в прежнем порядке,
затем обновляй только нужный файл:

```bash
# Заменить существующий файл журнала
gh gist edit "$GIST_URL" --filename coderabbit-review.md "$REVIEW_FILE"

# Добавить журнал к Gist, в котором уже есть details.md, если файла журнала нет
gh gist edit "$GIST_URL" --add "$REVIEW_FILE"
```

Поддержку `--add` проверяй по `gh gist edit --help` установленной версии. После
edit повторно проверь имена файлов и побайтовое совпадение каждого управляемого
исходника. Код возврата edit не заменяет повторное чтение.

## Неизвестный исход и восстановление без дубликатов

После тайм-аута, сетевой ошибки или неясного результата `create`/`edit` не делай
вывод, что Gist отсутствует, и не повторяй операцию вслепую.

1. **ID/URL известны:** сначала прочитай именно этот Gist (`--files` и нужные
   `--raw --filename`), сохрани все файлы локально и сравни каждый с соответствующим
   исходником или известной базой. Если операция уже применена — зафиксируй это;
   если содержимое отличается, остановись и согласуй версии. Повторять операцию
   можно только после выяснения фактического удалённого состояния.
2. **ID неизвестен:** ищи Gist активной учётной записи с явно заданным
   `--limit`, например `gh gist list --limit 1000` (без фильтра по видимости).
   При необходимости уточни поиск по именам файлов через `--filter`; для
   содержимого добавь `--include-content` либо используй API с полной пагинацией.
   Выдачу `--include-content` перенаправляй в игнорируемый локальный файл, чтобы журнал не
   печатался в контекст. `gh gist list` по умолчанию
   ограничен 10 результатами; пустая или достигшая лимита выдача не доказывает,
   что Gist отсутствует.
3. Для подходящих вариантов сверяй назначение, имена файлов и полный текст
   с сохранённым локальным исходником/базой, а не только с описанием. Читай
   каждый вариант по известному ID, сохраняя raw в игнорируемый файл и сравнивая
   через `cmp -s`; не печатай его целиком без необходимости.
4. Создавай новый Gist только после исчерпывающего поиска в доступной области,
   когда установлено, что совпадающего Gist нет. При ограниченном поиске,
   неоднозначности или неразрешённом расхождении остановись с диагностикой —
   дубликат журнала недопустим.

Если `gh gist create` завершился неопределённо и URL не был сохранён, не теряй
подготовленный исходник. Используй поиск выше; если найден ровно один подходящий Gist,
прочитай и сверь его перед продолжением. При нескольких кандидатах не выбирай
самый похожий по заголовку и не создавай новый.

## Связь Gist и PR

Связь Gist и PR проходит два состояния, и порядок не цикличен:

1. **Переходное, до создания PR.** Номер и URL PR неизвестны: в `manifest.md`
   `PR: не создан`, в `details.md` ссылки на PR нет, достаточно repository, задачи
   и HEAD. Не выдумывай номер. Кандидата проверяй режимом без `--pr-number`, затем
   создай PR с реальным URL Gist.
2. **Финальное, после создания PR.** Обратная ссылка обязательна: в `manifest.md`
   строка `PR: <номер>`, в `details.md` точный URL
   `https://github.com/<owner/repo>/pull/<номер>`. Изменение `details.md` меняет
   его SHA-256, поэтому обнови строку `## Файлы` в manifest, опубликуй оба файла
   и сверь повторным чтением. Затем выполни проверку опубликованной пары с
   `--published`. Gist без номера или без ссылки при существующем PR — отказ.

Для уже существующего PR сразу используй фактический номер и URL из удалённого
состояния. Канонический порядок операций задаёт [`pr-lifecycle.md`](pr-lifecycle.md).
