# Описание PR

Этот файл — владелец **содержательной структуры** PR body и формата накопительной
таблицы CodeRabbit для `anki-git-workflow`. Источник body, публикация body и
комментария, повторное чтение, Draft/Ready, merge и очистка принадлежат `pr-lifecycle.md`.

## 1. Главный принцип

**Жёсткий предел PR body — 10 000 символов Unicode** после нормализации переводов строк CRLF/CR в LF, включая Markdown. Gist не создаётся и не требуется: содержательные решения, данные ревью и компактные фактические результаты находятся в самом PR.


Пиши для человека, который не читал чат и видит только PR. Body должен быстро
отвечать на вопросы: зачем существует изменение, что именно изменилось, как это
проверено, в каком состоянии CI/review и какие ограничения остаются.

Заголовок и обычный текст — на русском; точные имена API, CLI, файлов, классов,
команд, кодов причин и CI jobs сохраняются.

Body строится по **фактическому состоянию** текущего work item. Не копируй
исходный prompt, transcript агента, полный журнал команд, временный roadmap или
старое состояние, которое уже не соответствует HEAD.

## 2. Обязательная структура содержательного PR

Любой **содержательный PR текущего work item** использует реальные
Markdown-заголовки второго уровня. Это относится не только к коду, tests,
config, workflow и repository skills, но и к документации и другим
отслеживаемым изменениям репозитория. Пользовательские колоды, ресурсы,
содержимое карточек, note models и media через Git не публикуются и в описании
PR не фигурируют:

```text
## Цель
## Область изменений
## Реализация
## Проверки
## Производительность
## CI
## Готовность
## Ограничения
```

Перед публикацией и после read-back запускай на полном Markdown body
`python3 .github/scripts/check_pr_body.py --body-file <путь-к-body.md>`.
GitHub Actions повторяет эту проверку на событиях PR дважды: «Структура PR»
исполняет валидатор из самого PR, а «Доверенная структура PR» — валидатор из
base SHA, который PR подменить не может (`pr-lifecycle.md`, § «Доверенная
проверка CI»). PR, меняющий валидатор, до merge обязан удовлетворять и правилам
base. Не объявляй успешным
результат без проверки и не подменяй автоматически проверяемые заголовки
субъективной оценкой. Автоматизация проверяет структуру и непустоту разделов,
но не доказывает достоверность заявленных тестов, CI и цифр производительности —
эти факты сверяются отдельно. Зависимые PR проверенных Renovate/Dependabot аккаунтов исключены
только при совпадении имени бота и префикса его ветки.

Не заменяй эту структуру одним сплошным текстом, подписями вида `Проверки:`
или единственным списком. Разделы должны быть визуально отделены именно
`##`-заголовками. Исключение — только действительно служебная mutation без
содержательного repository diff; обычная правка кода, документации или
конфигурации исключением не является.

### `## Цель`

1–3 плотных предложения:

- какую проблему или capability закрывает PR;
- почему изменение нужно;
- какое наблюдаемое состояние должно быть после merge.

### `## Область изменений`

Кратко фиксируй фактическую границу:

- основные подсистемы, owners и типы изменённых артефактов;
- repository/base/head branch;
- exact base SHA и текущий HEAD, когда они доступны и полезны для проверки;
- важный out-of-scope только если без него граница неочевидна.

Не превращай раздел в полный список файлов.

### `## Реализация`

Опиши существенные инженерные решения и их причины:

- владельца данных/поведения;
- изменённый flow или contract;
- важные failure/recovery semantics;
- сохранённые инварианты.

Пиши о результатах, а не о последовательности действий агента.

### `## Проверки`

Только фактически выполненные проверки и их результаты. Для каждой существенной
проверки должно быть понятно, что именно она подтверждает. Честно указывай
непройденную или недоступную проверку; не выдавай planned check за выполненный.

### `## Производительность`

Обязательный **короткий** раздел: не более **2 200 символов** вместе с разметкой; длинные таблицы, необработанный `benchmark-history report`, stdout, метаданные всех прогонов и длинные перечни окружения сюда не копировать. Отчёт и локальные доказательства остаются в рабочем каталоге задачи, а решение и значимые результаты — **в теле PR**.

Используй ровно один `Статус:`:

Для `не применимо` и `не измерено` весь раздел — не более **650 символов**.

- `не применимо` — строка `Причина:` с конкретным объяснением отсутствия влияния на runtime. Не использовать для изменений исполняемого кода, влияющих на производительность.
- `не измерено` — короткие `Причина:`, `Диагностика:` и `Доказательство производительности: отсутствует`. Не выдавать отсутствие измерений за проверенный результат.
- `измерено` — по каждому существенному сценарию, в отдельном `###`-подразделе, не более шести содержательных строк:
  `Сценарий:` (ID, профиль, нагрузка и n);
  `База:` (измеренный commit/SHA или «первая реализация»);
  `Кандидат:` (измеренный commit/SHA);
  `Результат:` (метрика, единицы, до → после, Δ/%, разброс при наличии);
  `Вывод:` (сопоставимость и интерпретация);
  `Регрессии:` (все существенные ухудшения или явное «нет существенных»).
  Если отдельный сценарий не удалось измерить, подзаголовок `### … — не измерено` и причина, диагностика, отсутствие доказательства. Не скрывай ухудшения ради компактности.

Первичные отчёты, полная методика и артефакты остаются локально для перепроверки; ссылку на Gist не требуй. В PR должны остаться проверяемые идентификаторы, числа, существенные регрессии и ограничения, достаточные для инженерного вывода. Нет места для важных фактов — сокращай дублирование в остальных разделах, а не выбрасывай результаты. Контракт сопоставимости описывают [`benchmark-history`](../../../../docs/ru/benchmark-history/README.md) и [`performance-benchmarking`](../../performance-benchmarking/SKILL.md).

### `## CI`

Укажи состояние hosted checks относительно **текущего PR HEAD**:

- exact HEAD, если он нужен для исключения stale evidence;
- обязательные jobs/contexts и их состояние;
- `pending` / `NOT_RUN` / недоступность, если финального результата ещё нет.

Не называй зелёным CI от предыдущего HEAD.

### `## Готовность`

Кратко зафиксируй terminal state work item:

- реализация завершена или что ещё осталось;
- Draft/Ready;
- состояние обязательного review;
- merge не выполнен без отдельного разрешения пользователя.

### `## Ограничения`

Только реальные ограничения, риски, недоступные проверки или препятствия.
Если существенных ограничений нет, скажи это одной строкой вместо искусственного
списка.

## 3. Условные разделы

Добавляй отдельные `##`-разделы, когда они действительно применимы.

### `## Live acceptance`

Используй, когда выполнялся реальный runtime/browser/Anki/media acceptance,
который существенно сильнее статических tests. Опиши сценарий, наблюдаемый
результат и cleanup временных данных.

### `## Безопасность / проверка секретов`

Используй, когда задача затрагивает trust boundary, filesystem/network input,
secrets либо когда выполнялся отдельный security/secret scan.

### `## Миграция / откат`

Используй для migration, compatibility window, recovery/rollback или изменения
persistent/runtime contract, где это реально имеет смысл.

### `## Внешняя проверка`

Используй для внешнего reviewer, который не имеет собственного более точного
раздела.

## 4. Накопительная таблица CodeRabbit

После каждой фактически завершённой итерации `anki-coderabbit-review` публикуй
содержательные результаты в **одном** top-level issue-комментарии автора PR во
вкладке Conversation, не в inline review thread и не в сообщении бота. Комментарий
содержит точный служебный маркер `<!-- coderabbit-disposition -->` отдельной
строкой и одну видимую накопительную таблицу вне fenced-блоков и HTML-комментариев;
проверка фактического автора и безопасная публикация — в
[`pr-lifecycle.md`](pr-lifecycle.md). Без проведённого CodeRabbit фиктивная
таблица не нужна. Body остаётся самостоятельным: таблица и ссылка на неё в нём
не обязательны; после миграции старый раздел не занимает в нём место.

Используй **одну связную GFM-таблицу** на весь цикл:

```markdown
<!-- coderabbit-disposition -->

| Итерация / reviewed HEAD | Уровень | Путь | Влияние | Решение | Исправление |
| --- | --- | --- | --- | --- | --- |
| 1 · `0123456` | major | `path/to/file` | <технический эффект> | confirmed | <что исправлено и каким commit опубликовано> |
```

Правила таблицы:

- заголовок ровно один, сразу за ним строка-разделитель из шести ячеек дефисов
  с необязательным выравниванием `:`; все строки данных следуют подряд, без
  разрыва, повторного заголовка и оторванных строк. В каждой из шести ячеек
  должно быть непустое значение; необработанный `|` внутри ячейки экранируй;
- хотя бы одна строка завершённой итерации обязательна; её первая ячейка —
  положительный номер итерации, `·` и reviewed HEAD в code span: от 7 до 40
  строчных шестнадцатеричных символов;
- после **каждой завершённой итерации** добавляй новые строки в эту же таблицу;
  предыдущие строки не удаляй и не переписывай ради красивого итога;
- первая колонка однозначно связывает строки с номером итерации и
  **reviewed HEAD**, то есть состоянием, которое действительно видел провайдер;
- на каждое замечание провайдера сохраняй его фактический `severity`, путь,
  технический эффект, итоговое решение и результат;
- допустимые решения определяет `anki-coderabbit-review`; не превращай
  `false positive` или `stale/repeated` в якобы выполненное исправление;
- если итерация действительно завершилась с 0 замечаний, добавь одну
  итоговую строку с `—` в `Уровень` и `Путь`, `clean` в `Решение` и
  укажи опубликованный маркерный коммит в `Исправление`;
- если замечания были, но все оказались `false positive` или `stale/repeated`, строки всё равно
  остаются в таблице с честным решением;
- новый коммит после исправлений **не** выдаётся за reviewed HEAD той же итерации:
  следующая итерация проверяет уже новое опубликованное состояние;
- сырой вывод ревьюера, промпты и длинные `codegenInstructions` не копируй.

Лимит body 10 000 символов не является лимитом комментария. Если опубликованная
таблица не помещается в доступный комментарий, не удаляй и не объединяй строки и
не создавай второй журнал: остановись и сообщи пользователю о препятствии.
Синтаксическая проверка не доказывает достоверность замечаний или исправлений.

Skill CodeRabbit определяет, **когда** итерация завершена, как оцениваются
замечания и какие данные должны попасть в строки. Этот файл владеет форматом;
`pr-lifecycle.md` — публикацией, миграцией и повторным чтением.

## 5. Плотность и читаемость

Обычно достаточно короткого абзаца или 2–6 содержательных пунктов на раздел.
Это ориентир, не квота. Для крупной архитектурной работы раздел может быть
длиннее, но стену текста разбивай по смыслу.

Предпочитай:

- короткие абзацы;
- списки для независимых фактов;
- таблицы только для действительно табличных данных;
- code spans для путей, команд, SHA и identifiers.

Не вставляй повтор одного и того же evidence в несколько разделов.

## 6. Актуализация body

Body — живое описание PR, а не текст только на момент создания.

При изменении фактов:

1. сначала обнови repository-local `.codex/local/pr/<task>/body.md`;
2. перечитай полный файл и проверь структуру этого документа;
3. опубликуй его способом из `pr-lifecycle.md`;
4. перечитай опубликованный PR и сравни полный body с локальным источником.

После завершённой итерации CodeRabbit обновление накопительной таблицы решений в
комментарии и успешное повторное чтение являются частью завершения итерации;
следующая итерация не начинается, пока предыдущая не подтверждена.
