# Описание PR

Этот файл задаёт **содержательную структуру** PR body для
`anki-git-workflow`. Источник файла body, способ публикации, повторное чтение,
Draft/Ready, merge и очистка описаны в `pr-lifecycle.md`.

## 1. Главный принцип

Пиши для человека, который не читал чат и видит только PR. Body должен быстро
отвечать на вопросы: зачем существует изменение, что именно изменилось, как это
проверено, в каком состоянии CI/review и какие ограничения остаются.

Заголовок и обычный текст — на русском; точные имена API, CLI, файлов, классов,
команд, кодов причин и CI jobs сохраняются.

Описание строится по **фактическому состоянию** текущей задачи. Не копируй
исходный prompt, transcript агента, полный журнал команд, временный roadmap или
старое состояние, которое уже не соответствует HEAD.

**Тело PR самодостаточно.** Даже для крупной задачи это не пара строк и не
набор внешних ссылок: в самом PR остаются смысл изменения, основные решения,
существенные проверки, реальные результаты, ограничения и готовность. Полные
серии, диагностику и хронологию можно вынести в Gist, сохранив здесь
проверяемую сводку и контекстные ссылки.

## 2. Обязательная структура содержательного PR

Любой **содержательный PR по текущей задаче** использует реальные
Markdown-заголовки второго уровня. Это относится не только к программному коду,
тестам, конфигурации, рабочим сценариям и навыкам репозитория, но и к документации и другим
отслеживаемым изменениям репозитория. Пользовательские колоды, ресурсы,
содержимое карточек, note models и media через Git не публикуются и в описании
PR не фигурируют:

```text
## Цель
## Область изменений
## Реализация
## Проверки
## Производительность
## CI
## Готовность
## Ограничения
```

Перед публикацией и после read-back запускай на полном Markdown body
`python3 .github/scripts/check_pr_body.py --body-file <путь-к-body.md>`.
GitHub Actions повторяет эту проверку на событиях PR. Не объявляй успешным
результат без проверки и не подменяй автоматически проверяемые заголовки
субъективной оценкой. Автоматизация проверяет структуру и непустоту разделов,
но не доказывает достоверность заявленных тестов, CI и цифр производительности —
эти факты сверяются отдельно. Зависимые PR проверенных Renovate/Dependabot аккаунтов исключены
только при совпадении имени бота и префикса его ветки.

Не заменяй эту структуру одним сплошным текстом, подписями вида `Проверки:`
или единственным списком. Разделы должны быть визуально отделены именно
`##`-заголовками. Исключение — только действительно служебная операция без
содержательного repository diff; обычная правка кода, документации или
конфигурации исключением не является.

### `## Цель`

1–3 плотных предложения:

- какую проблему или capability закрывает PR;
- почему изменение нужно;
- какое наблюдаемое состояние должно быть после merge.

### `## Область изменений`

Кратко фиксируй фактическую границу:

- основные подсистемы, owners и типы изменённых артефактов;
- repository/base/head branch;
- exact base SHA и текущий HEAD, когда они доступны и полезны для проверки;
- важный out-of-scope только если без него граница неочевидна.

Не превращай раздел в полный список файлов.

### `## Реализация`

Опиши существенные инженерные решения и их причины:

- владельца данных/поведения;
- изменённый flow или contract;
- важные failure/recovery semantics;
- сохранённые инварианты.

Пиши о результатах, а не о последовательности действий агента.

### `## Проверки`

Только фактически выполненные проверки и их результаты. Для каждой существенной
проверки должно быть понятно, что именно она подтверждает. Честно указывай
непройденную или недоступную проверку; не выдавай planned check за выполненный.

### `## Производительность`

Раздел обязателен как **решение о применимости** замера. Ровно одна строка
`Статус:` с одним из трёх значений:

- **`измерено`** — обязательно, когда PR добавляет функциональность или может
  повлиять на время выполнения: новые или изменённые алгоритмы, разбор, ввод-вывод,
  кэши, производительно значимый рефакторинг, оптимизации. Раздел готовит
  `benchmark-history report` из проверенных результатов
  [`benchmark-runner`](../../../../tools/benchmark-runner/README.md), а не
  агент из памяти: строки «Сценарий», «Измеренный код», «Нагрузка»,
  «Окружение», «Прогоны», «База», «Сопоставимость», таблица `| Метрика | … |`,
  «Вывод», «Ограничения» и «Источники». Сгенерированный текст не
  переписывается вручную; при новом HEAD отчёт строится заново. Контракт
  выбора базы и сравнения — [`benchmark-history`](../../../../tools/benchmark-history/README.md).
- **`не применимо`** — только для изменений без влияния на выполнение (переводы,
  документация, тексты, метаданные CI без смены исполняемого кода). Строка
  `Причина:` называет конкретно, почему runtime не затронут; «N/A», «нет» и
  пустая причина не принимаются.
- **`не измерено`** — измерение нужно, но объективно невозможно в доступном
  окружении. Строки `Причина:` (блокирующая причина), `Диагностика:`
  (проверенная диагностика, например итог `unsupported` исполнителя или код
  `check`) и `Доказательство производительности: отсутствует`. Такой PR не
  объявляется проверенным по производительности.

При большом числе измерений оставляй в основном PR отчёты, представляющие
существенно разные затронутые пути и выявленные регрессии; дополнительные
результаты можно вынести в Gist или уже существующую документацию. Сокращение
не должно скрывать ухудшение. Ссылка не заменяет полей и числовой таблицы
оставленного измеренного `###`-блока: валидатор проверяет каждый такой блок.
Не исправляй исходные числовые результаты ради компактности.

Выбирай сценарии по затронутому пути исполнения, а не все сценарии каталога.
Долгий `anki-e2e.full` для каждого PR не запускается; для него допустим
одиночный или частичный прогон, если декларация это разрешает, либо
`не измерено` с диагностикой. Новая функциональность сравнивать не с чем —
`report --first`; оптимизация сравнивается с пригодной базой из истории.
Как получить базу прежней реализации, сопоставимую серию и честный вывод —
skill [`performance-benchmarking`](../../performance-benchmarking/SKILL.md); этот документ задаёт только форму раздела.

`check_pr_body.py` проверяет только форму: статус, непустые обязательные строки,
отсутствие шаблонных заглушек и наличие таблицы с числовыми значениями вне
код-блоков и HTML-комментариев. Подлинность цифр, уместность сценария,
воспроизводимость и статистические выводы проверяют агент и ревьюер по
источникам отчёта; произвольная таблица сама не доказывает выполненного замера.
Требование действует для уже открытых ручных PR со следующего события
`edited`/`synchronize`: без раздела проверка не проходит и подсказывает, как его
добавить. PR проверенных dependency-ботов по-прежнему исключены.

### `## CI`

Укажи состояние hosted checks относительно **текущего PR HEAD**:

- exact HEAD, если он нужен для исключения stale evidence;
- обязательные jobs/contexts и их состояние;
- `pending` / `NOT_RUN` / недоступность, если финального результата ещё нет.

Не называй зелёным CI от предыдущего HEAD.

### `## Готовность`

Кратко зафиксируй итоговое состояние задачи:

- реализация завершена или что ещё осталось;
- Draft/Ready;
- состояние обязательного review;
- merge не выполнен без отдельного разрешения пользователя.

### `## Ограничения`

Только реальные ограничения, риски, недоступные проверки или препятствия.
Если существенных ограничений нет, скажи это одной строкой вместо искусственного
списка.

## 3. Условные разделы

Добавляй отдельные `##`-разделы, когда они действительно применимы.

### `## Live acceptance`

Используй, когда выполнялся реальный runtime/browser/Anki/media acceptance,
который существенно сильнее статических tests. Опиши сценарий, наблюдаемый
результат и cleanup временных данных.

### `## Безопасность / проверка секретов`

Используй, когда задача затрагивает trust boundary, filesystem/network input,
secrets либо когда выполнялся отдельный security/secret scan.

### `## Миграция / откат`

Используй для migration, compatibility window, recovery/rollback или изменения
persistent/runtime contract, где это реально имеет смысл.

### `## Внешняя проверка`

Используй для внешнего reviewer, который не имеет собственного более точного
раздела.

### `## CodeRabbit review и disposition`

После фактически завершённой итерации `anki-coderabbit-review` этот раздел обязателен.
В PR хранится **короткая актуальная сводка**, а **вся накопительная история**
CodeRabbit — в одном постоянно обновляемом GitHub Gist текущей задачи.
Gist содержит таблицу всех итераций и всех замечаний провайдера, включая
`false positive`, `stale/repeated` и `clean`. Не теряй старые строки и
не создавай Gist заново для каждой итерации.

Формат раздела PR (данные ниже — только пример, подставляй проверенные факты):

```markdown
## CodeRabbit review и disposition

- **Прогресс:** 3 завершённые итерации; последнее ревью: `abcdef012345`
  (итерация 3); опубликован `1234567abcde` (ещё не проверен CodeRabbit).
- **Итог:** confirmed — 4 (исправлены); false positive — 1;
  stale/repeated — 2; clean — 1; нерешённых блокирующих — 0.
- **Существенное:** устранён риск потери данных в `src/example.rs`
  (исправление `1234567abcde`). Если значимых находок нет, так и укажи.
- **Полный журнал:** [все итерации, замечания и решения](https://gist.github.com/owner/0123456789abcdef0123456789abcdef).
```

Требования к компактной сводке:

- `Прогресс` — количество завершённых итераций, номер последней итерации,
  **reviewed HEAD** и опубликованный после неё HEAD. Не называй fix/marker
  commit проверенным той же итерацией.
- `Итог` — проверенные накопительные количества и текущие нерешённые риски.
  Нулевые замечания отличай от отклонённых находок; не объявляй `clean`,
  если provider находил false positive или повторы.
- `Существенное` — только важные подтверждённые ошибки, исправления и
  оставшиеся риски (с путём и коммитом по необходимости), без перечисления
  всех trivial/minor замечаний. При отсутствии значимого — явно укажи это.
- `Полный журнал` — реальная проверенная ссылка на **один Gist**, а не на
  временный файл, placeholder или несуществующий URL. Когда технический отчёт
  уже размещён в Gist, добавь в него отдельный `coderabbit-review.md`,
  не создавай второй Gist для той же задачи.
- Если Gist пока создать или подтвердить нельзя, не заменяй старый журнал
  ссылкой-заглушкой и не объявляй итерацию завершённой. Сохрани данные
  локально, сообщи о препятствии и повтори операцию после восстановления.
- Для старого PR с полной таблицей сохраняй совместимость; при следующем
  обновлении перенеси историю в Gist и замени таблицу компактной сводкой. Не веди
  два авторитетных журнала одновременно.

Формат полного журнала, миграция, безопасность и восстановление принадлежат
[`pr-gist.md`](pr-gist.md); последовательность GitHub-операций и read-back —
[`pr-lifecycle.md`](pr-lifecycle.md). Skill CodeRabbit владеет завершением
итерации и независимым triage; этот раздел задаёт только представление в PR.

## 4. Плотность и читаемость

Обычно достаточно короткого абзаца или 2–6 содержательных пунктов на раздел.
Это ориентир, не квота. Для крупной архитектурной работы раздел может быть
длиннее, но стену текста разбивай по смыслу. Не вводи жёсткий лимит длины: важные доказательства должны остаться
в PR, но полный журнал CodeRabbit хранится в Gist.

Предпочитай:

- короткие абзацы;
- списки для независимых фактов;
- таблицы только для действительно табличных данных;
- code spans для путей, команд, SHA и identifiers.

Не вставляй повтор одного и того же evidence в несколько разделов.

### Подробный отчёт и ссылки

Предпочитай ссылки на первичные результаты и существующую документацию
репозитория. Если объёмный дополнительный материал действительно нужен, используй
один актуализируемый Gist на задачу; он не заменяет выводы и ограничения PR.
Подписывай ссылки по назначению. Формат, приватность и публикацию Gist задаёт
[`pr-gist.md`](pr-gist.md). Secret Gist доступен любому обладателю URL.

## 5. Актуализация body

Body — живое описание PR и отражает факты текущего состояния, а не только
исходный замысел. После CodeRabbit-итерации здесь остаётся компактная сводка с
verified HEAD, текущими итогами и реальной ссылкой; полная история находится в
Gist по правилам этого раздела.

Источник body, порядок публикации и read-back принадлежат
[`pr-lifecycle.md`](pr-lifecycle.md); безопасность, обновление и проверка файлов
Gist — [`pr-gist.md`](pr-gist.md). Завершённая CodeRabbit-итерация требует
подтверждённого read-back обоих источников; сам порядок здесь не дублируется.
