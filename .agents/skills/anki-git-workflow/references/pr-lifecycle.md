# Жизненный цикл PR: описание, Draft/Ready, merge, конфликты, уборка

Этот файл владеет порядком действий после подтверждённой публикации commit'а.
Контракт и границы задаёт `SKILL.md`; постусловие push описано в
[`publication.md`](publication.md).

## 1. Идентичность PR

У обычной самостоятельной задачи репозитория **один** PR.

1. Установи текущий репозиторий, ожидаемые base и head, включая репозиторий владельца
   head. Перечисли открытые PR по base/head через GitHub API/коннектор либо
   `gh pr list --base <base> --head <head> --limit <достаточный лимит> --json number,baseRefName,headRefName,headRepository,headRepositoryOwner`.
   Проверь полноту выдачи и фактические репозиторий/base/head каждого кандидата:
   одинаковые имена веток в разных форках не доказывают идентичность. `gh pr view`
   без номера показывает один PR ветки и не доказывает единственность.
2. Для выбора существующего PR требуется ровно одно совпадение. При нуле,
   неоднозначности или неполной выдаче останови операцию над существующим PR;
   не угадывай и не переключайся на другой PR. При единственном совпадении
   перечитай его по номеру и используй этот номер для дальнейших операций.
3. Для отдельной операции создания нового PR отсутствие совпадений сначала
   устанавливается полной выдачей; дубликат для той же пары не создавай. Пока не
   создавай PR: сначала подготовь и проверь описание по порядку ниже. Отсутствующий
   PR — допустимое состояние подготовки нового PR.

Не создавай новый PR только потому, что началась следующая фаза той же рабочей
задачи, и не переключайся на другой PR.

## 2. Источник описания PR

При работе с локальной рабочей копией источник описания (body) — локальный
Markdown-файл внутри репозитория, который **не** отслеживается Git:

```text
.codex/local/pr/<task>/body.md
```

`<task>` — короткий смысловой идентификатор текущей рабочей задачи, а не номер PR,
SHA или номер этапа. Содержимое описывает фактическое состояние задачи, но не
хранит временных идентификаторов вне описания PR, разового плана и стенограммы.

Правила:

- такой тип артефактов закрыт правилом игнорирования в `.gitignore`; правило должно
  быть минимально достаточным и не скрывать потенциально важные отслеживаемые файлы;
- путь действительно игнорируется Git и не отслеживается — это проверяется
  фактом (`git check-ignore -v <путь>`, `git ls-files <путь>`), а не
  предположением;
- генератор, схема или шаблонизатор описания на Python/Rust не вводится: Markdown-файла
  достаточно;
- файл полностью формируется и **перечитывается** до публикации;
- файл сохраняется минимум до подтверждённого повторного чтения опубликованного PR
  и не удаляется, пока результат операции неизвестен.

### Восстановление источника для уже существующего PR

Локальный игнорируемый файл — рабочий источник, но опубликованный PR нельзя
реконструировать по памяти, промпту или краткому отчёту.

Если PR уже существует, а локального источника описания нет либо текущая рабочая
копия ещё не доказала его совпадение с опубликованным описанием:

1. прочитай **полное** текущее описание удалённого PR;
2. создай отсутствующий локальный `.codex/local/pr/<task>/body.md` из этого описания
   без потери существующих разделов, таблиц и текста;
3. перечитай локальный файл и только после этого вноси новое изменение.

Если локальный файл существует, но отличается от удалённого PR, и неизвестно,
какая сторона новее, не перезаписывай ни одну сторону автоматически: сравни их и
явно примири различия. Для уже опубликованного состояния удалённое описание —
основа восстановления, а не повод затереть доказанные локальные изменения.

Перед публикацией проверь локальный файл описания: реально выполненные проверки и
фактические ограничения. Заголовок, base и head в этом файле не хранятся: сверь их
отдельно с аргументами вызова и фактическим состоянием по § 1. Содержательную
структуру описания сверь с [`pr-body.md`](pr-body.md) и запусти
`python3 .github/scripts/check_pr_body.py --body-file <путь>`.

Если задача явно выполняется **только через GitHub MCP/API**, без доступной
локальной рабочей копии и `gh`, сохрани исходный Markdown во временном рабочем файле
агентской среды (не в Git). Получи через API `.github/scripts/check_pr_body.py` из
точного head SHA публикуемой ветки во временный файл там же и проверь им исходный
файл; если PR меняет валидатор, проверь файл и валидатором из точного base SHA
(§ «Доверенная проверка CI»). Затем передай полное содержимое в GitHub API и
прочитай обратно. В этом режиме
коннектор — транспорт, а не второй владелец формата и не разрешение обойти
валидацию и повторное чтение. Если проверку выполнить невозможно, честно
назови это препятствием и не объявляй PR соответствующим контракту.

## 3. Структура описания

Содержательной структурой описания PR владеет отдельный справочник
[`pr-body.md`](pr-body.md). Перед каждым `create/edit` описание должно
соответствовать ему по фактическому состоянию текущей рабочей задачи.

Для обычного содержательного PR нужны настоящие Markdown-заголовки `## Цель`,
`## Область изменений`, `## Реализация`, `## Проверки`, `## Производительность`,
`## CI`, `## Готовность` и `## Ограничения`, а не пара сплошных абзацев с подписью
`Проверки:`. Условные разделы добавляются только при необходимости; цикл
CodeRabbit использует накопительный раздел и таблицу, определённые в `pr-body.md`.

Описание отражает **фактическое** состояние рабочей задачи, а не исходный замысел,
который уже разошёлся с реализацией. Факты не выдумываются, честные пропуски
проверок называются прямо. В описание не попадают номер этапа, разовый план, полный
журнал команд и сырая стенограмма ревью.

### Порядок публикации описания

Для каждого содержательного ручного PR соблюдай один порядок и для нового, и для
существующего PR:

1. Установи репозиторий, base, head и наличие PR; не создавай второй.
2. Подготовь локальное описание. Для существующего PR сначала восстанови его по § 2.
3. Проверь полный файл валидатором (`check_pr_body.py --body-file`, максимум
   10 000 символов) и содержательно — по `pr-body.md`, затем создай
   отсутствующий PR (Draft) либо обнови существующий.
4. Прочитай PR обратно по § 5. Gist не создаётся и не проверяется: все
   содержательные результаты, включая таблицу CodeRabbit, находятся в описании.

## 4. Создание и редактирование

Новый PR по умолчанию создаётся **Draft** и остаётся Draft до финального
ревью пользователя, если пользователь не дал другую явную команду.

```bash
gh pr create --draft --base <base> --head <branch> --title <title> --body-file <путь>
gh pr edit <number> --title <title> --body-file <путь>
```

Интерфейс `gh` зависит от версии: флаги и способы передать описание проверяй по
выводу `gh pr create --help` / `gh pr edit --help` фактически установленной версии, а
не по памяти. Не полагайся на интерактивные запросы: описание передаётся файлом.

При работе через локальный `gh` описание публикуется только файлом. Встроенный
`--body`, `--body-file -` со stdin и heredoc непосредственно в вызове
провайдера запрещены: они разрывают связь между проверенным локальным
файлом и опубликованным описанием. В режиме GitHub MCP/API без локального
`gh` допустима передача проверенного полного описания через структурированный
параметр API с обязательным повторным чтением, как описано в § 2.

## 5. Повторное чтение опубликованного PR

После создания или каждого изменения PR (`gh` либо GitHub MCP/API) перечитай опубликованный PR и
проверь:

```text
репозиторий
base
head
состояние Draft/Ready
заголовок
описание
```

Сравни опубликованное описание с локальным файлом с учётом допустимой нормализации
переводов строк (например CRLF/LF, завершающий перевод строки). Прочие расхождения
означают, что PR не соответствует локальному источнику, и должны быть устранены,
а не проигнорированы.

Отдельно проверь, что опубликованный head — это именно ожидаемый HEAD текущей
рабочей задачи, а не устаревшее состояние.

## 6. Ready

Draft переводится в Ready только по явной команде пользователя либо когда это
следует из явно определённого контракта текущей рабочей задачи. Успешный push,
зелёный CI или сам факт созданного Draft PR не переводят PR в Ready и тем более
не разрешают merge.

```bash
gh pr ready <number>
```

## 7. Merge

```text
успешный push ≠ разрешение на merge
зелёный CI ≠ разрешение на merge
созданный Draft PR ≠ разрешение на merge
```

Merge выполняется **только** после отдельной текущей явной команды пользователя
на конкретный PR. Разрешение, выданное ранее и относящееся к другому состоянию
рабочей задачи, не переиспользуется.

Перед merge заново проверь:

- репозиторий, base/head и точный текущий HEAD PR
  (установленную версию `gh` см. в `gh pr view --help`);
- актуальность обязательных проверок и ревью относительно **текущего** HEAD:
  после любого изменения HEAD прежние доказательства считаются устаревшими;
- что merge не обходит проверки: `--admin` и любые механизмы принудительного
  слияния запрещены; auto-merge требует того же отдельного разрешения, а ожидающий
  auto-merge **не** считается выполненным merge.

Способ merge выбирай безопасный и согласующийся с фактической политикой
репозитория. Не закрепляй squash жёстко: сверься с фактическим состоянием репозитория и
интерфейсом установленного `gh` (`gh pr merge --help`). Историческая конвенция этого
репозитория — один squash-commit вида `<заголовок> (#<номер>)`, но это наблюдение
о фактических данных, а не вечный контракт: перед merge политика перепроверяется.

Если установленная версия `gh` умеет привязывать merge к ожидаемому HEAD
(например `--match-head-commit <sha>`), используй эту возможность, чтобы не слить
PR, head которого сдвинулся между проверкой и merge; доступность флага
подтверждается по `gh pr merge --help`.

После merge прочитай фактический конечный статус PR (`merged`) и merge SHA: сам
код завершения команды не подтверждает удалённый результат. Дальше переходи к уборке
(§ 9).

## 8. Продвижение base и конфликты

Если base продвинулась или возник конфликт:

1. Установи общий предок и фактическое изменение обеих сторон (`git merge-base`,
   diff каждой стороны) до любых правок.
2. Разрешай конфликт по смыслу: стратегии целого файла `ours`/`theirs` и общий выбор
   «своей» стороны как механический приём не применяются. Чужие изменения не
   удаляются.
3. Сгенерированный или производный файл, у которого есть владелец-источник,
   пересоздаётся из источника, а не правится вручную.
4. Опубликованная ветка обновляется merge актуальной base, без force и без
   переписывания истории; rebase допустим только для ещё не опубликованной истории.
5. После разрешения проверь отсутствие неслитых путей (unmerged paths) и незавершённых
   merge/rebase, а также происхождение новой базы и итоговый diff.
6. После изменения HEAD считай прежние результаты CI и ревью устаревшими
   относительно нового commit и проверь состояние заново: сначала обнови локальный
   файл описания, затем опубликуй и перечитай его.
7. Не делай force-push опубликованной ветки только ради удобства.

## 9. Уборка после merge

После **подтверждённого** merge допустима обычная уборка собственной рабочей задачи:
удаление собственной рабочей ветки и локальных временных артефактов (включая
локальный файл описания в репозитории).

Ограничения:

- удаляй ветку только после доказанного сохранения результата: локальную —
  через `git branch -d`, удалённую — после подтверждения её принадлежности этой
  рабочей задаче и факта merge;
- не удаляй чужую работу и чужие артефакты;
- если squash-merge мешает `git branch -d`, оставь ветку и сообщи ограничение:
  автоматический переход к `-D` и принудительному удалению запрещён;
- уборка не входит в автоматический жизненный цикл: она выполняется после
  подтверждённого merge, а не вместо проверок.

## 10. Завершённое состояние рабочей задачи

```text
commit опубликован и удалённый SHA подтверждён
PR существует в единственном экземпляре для текущей рабочей ветки
PR перечитан после последнего изменения и соответствует локальному файлу описания
состояние Draft/Ready соответствует ожидаемому
merge не выполнен, пока нет отдельной текущей явной команды
```

До отдельного разрешения на merge конечный результат обычной задачи — проверенный
Draft PR. Результат передаётся пользователю на ревью; merge остаётся за
пользователем.

## Доверенная проверка CI

«Структура PR» (`pr-body.yml`, `pull_request`) исполняет валидатор из самого PR:
это проверка кандидата, и её успех не доказывает соответствие контракту, если
PR меняет `check_pr_body.py`. Независимая «Доверенная структура PR»
(`pr-body-trusted.yml`) выполняется на `pull_request_target`: workflow берётся
из base, валидатор — из точного base SHA. Checkout head, запуск кода PR, секреты
и права записи запрещены; описание и метаданные события читаются только как
данные. Изменение валидатора в PR не меняет доверенную проверку до merge в base.

Проверь фактические ruleset/branch protection и обязательные контексты. Новую проверку
делай обязательной **только после** появления workflow в base и подтверждённого
успешного запуска именно этого workflow из доверенной base на PR. Наличие YAML
в head, локальная проверка кандидата и успешная «Структура PR» этого условия
не заменяют. Нельзя создавать циклическую зависимость, в которой PR требует
статус workflow, впервые вводимого этим же PR.

Порядок ввода: подготовить workflow в PR → выполнить проверки и повторное чтение →
после отдельно разрешённого merge убедиться в наличии workflow в base → получить
успешный запуск на подходящем PR → при наличии полномочий добавить обязательный
контекст, сохранив все остальные правила и исключения (bypass actors) → перечитать ruleset.
До подтверждённого запуска сохраняй действующие обязательные проверки и явно указывай,
что независимая проверка подготовлена, но ещё не активирована. Без полномочий назови
точную оставшуюся настройку. Не выдавай отсутствующий статус за ожидающий запуск.

GitHub допускает `pull_request_target` как источник обязательной проверки, см.
[диагностику обязательных проверок](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks).
Перед активацией проверь также применимые политики событий Actions; не ослабляй
их и не считай новый workflow исполнившимся без фактического запуска. Обязательный
контекст сопоставляется по имени задания: изменение файлов `.github/workflows/`
в PR проверяй при ревью отдельно, потому что новый workflow PR способен создать
задание с тем же именем.
