# Жизненный цикл PR: описание, Draft/Ready, merge, конфликты, очистка

Этот файл владеет порядком действий после подтверждённой публикации commit'а.
Контракт и границы задаёт `SKILL.md`; условие подтверждённой публикации push описано в
[`publication.md`](publication.md).

## 1. Идентификация PR

Обычная самостоятельная задача репозитория имеет **один** PR.

1. Установи текущий repository, ожидаемые base и head, включая repository владельца
   head. Перечисли открытые PR по base/head через GitHub API/connector либо
   `gh pr list --base <base> --head <head> --limit <достаточный лимит> --json number,baseRefName,headRefName,headRepository,headRepositoryOwner`.
   Проверь полноту выдачи и фактические repository/base/head каждого кандидата:
   одинаковые имена веток в разных fork не доказывают идентичность. `gh pr view`
   без номера показывает один PR ветки и не доказывает единственность.
2. Для выбора существующего PR требуется ровно одно совпадение. При нуле,
   неоднозначности или неполной выдаче останови операцию над существующим PR;
   не угадывай и не переключайся на другой PR. При единственном совпадении
   перечитай его по номеру и используй этот номер для дальнейших операций.
3. Для отдельной операции создания нового PR отсутствие совпадений сначала
   устанавливается полной выдачей; дубликат для той же пары не создавай. Пока не
   создавай PR: сначала подготовь body и опубликуй/проверь нужный Gist по порядку
   ниже. Отсутствующий PR — допустимое состояние подготовки нового PR, а не повод
   для фиктивной ссылки.

Не создавай новый PR только потому, что началась следующая фаза той же задачи,
и не переключайся на другой PR.

## 2. Локальный источник описания PR

При работе с локальной рабочей копией источником body служит Markdown-файл
в каталоге репозитория, который **не** отслеживается Git:

```text
.codex/local/pr/<task>/body.md
```

`<task>` — короткое смысловое имя текущей задачи, а не номер PR, SHA или номер
stage. Не оставляй в имени или содержимом снимок текущей задачи.

Правила:

- такой тип артефактов закрыт ignore-правилом в `.gitignore`; правило должно быть
  минимально достаточным и не скрывать потенциально важные tracked-файлы;
- путь действительно игнорируется Git и не является tracked — это проверяется
  фактом (`git check-ignore -v <путь>`, `git ls-files <путь>`), а не
  предположением;
- генератор body на Python/Rust, схема или шаблонизатор не вводятся: достаточно
  Markdown-файла;
- файл полностью формируется и **перечитывается** до публикации;
- файл сохраняется минимум до подтверждённого повторного чтения опубликованного PR
  и не удаляется, пока результат операции неизвестен.

### Восстановление источника для уже существующего PR

Локальный игнорируемый файл — рабочий источник, но опубликованный PR нельзя
восстанавливать по памяти, prompt'у или краткому отчёту.

Если PR уже существует, а локального источника body нет или рабочая копия ещё не
подтвердила его синхронность с опубликованным описанием:

1. прочитай **полный** текущий body удалённого PR;
2. создай отсутствующий локальный `.codex/local/pr/<task>/body.md` из этого body
   без потери существующих разделов, таблиц и текста;
3. перечитай локальный файл и только после этого вноси новое изменение.

Если локальный файл существует, но отличается от удалённого PR, и неизвестно,
какая сторона новее, не перезаписывай ни одну сторону автоматически: сравни их и
явно согласуй различия. Для уже опубликованного PR удалённое описание — исходная
база восстановления, а не повод затереть подтверждённые локальные изменения.

Перед публикацией проверь по локальному файлу: заголовок, body, base/head, реально
выполненные проверки и фактические ограничения. Содержательную структуру body
сверь с [`pr-body.md`](pr-body.md) и запусти
`python3 .github/scripts/check_pr_body.py --body-file <путь>`.

Если задача явно выполняется **только через GitHub MCP/API**, без доступной
локальной рабочей копии и `gh`, сохрани исходный Markdown во временном рабочем файле
агентской среды (не в Git), проверь этот исходный файл тем же валидатором, передай
его полное содержимое в GitHub API и прочитай обратно. В этом режиме
коннектор — транспорт, а не второй владелец формата или разрешение обойти
валидацию и повторное чтение. При отсутствии возможности выполнить проверку честно
назови это препятствием, не объявляй PR соответствующим контракту.

## 3. Структура body

Структурой PR body владеет отдельный справочник [`pr-body.md`](pr-body.md).
Перед каждым `create/edit` описание должно соответствовать ему и фактическому
состоянию текущей задачи.

Для обычного содержательного PR нужны реальные Markdown-заголовки `## Цель`,
`## Область изменений`, `## Реализация`, `## Проверки`, `## Производительность`,
`## CI`, `## Готовность` и `## Ограничения`, а не пара сплошных абзацев с подписью
`Проверки:`. Условные разделы добавляются только при необходимости; в цикле
CodeRabbit в PR остаётся компактная сводка, а полный журнал — в Gist по
`pr-body.md` и `pr-gist.md`.

Описание отражает **фактическое** состояние задачи, а не исходный замысел,
который уже разошёлся с реализацией. Факты не выдумываются, честные пропуски
проверок называются прямо. В body не попадают номер stage, разовый план, полный
журнал команд и сырой transcript review.

### Порядок Gist и PR

Для каждого содержательного ручного PR соблюдай один порядок и для нового, и для
существующего PR:

1. Установи идентификаторы repository/base/head и наличие PR; не создавай второй.
2. Подготовь локальный полный файл Gist и описание PR. Для существующего PR сначала
   восстанови описание по § 2; для нового не выдумывай URL.
3. Проверь содержимое и структуру локальных файлов. Если сводка требует URL,
   которого ещё нет, не подставляй фиктивную ссылку: предварительно проверь другие
   части body, а полную обязательную валидацию запусти после получения URL и до
   изменения PR.
4. Создай или обнови Gist и подтверди каждый полный файл сравнением с локальным
   исходником по [`pr-gist.md`](pr-gist.md). При неизвестном результате сначала
   прочитай фактическое состояние; не повторяй операцию вслепую.
5. Вставь единственный проверенный URL в компактный body (максимум 6 000 символов),
   запусти локальный gate и remote Gist-preflight с локальным manifest/исходниками
   по `pr-gist.md`, затем создай отсутствующий PR (Draft) либо обнови существующий.
6. Прочитай обратно PR и Gist; проверь текст, файлы, repository/base/head и
   Draft/Ready. Повтори оба gate на опубликованных данных и сверку всех файлов
   с локальными исходниками. При новом PR сначала дополни Gist фактическим номером.
   Ошибка Gist останавливает публикацию/завершение; нельзя убрать ссылку или вернуть
   полный отчёт в body. Повторное чтение PR и Gist проверяются независимо.

Если создание или подтверждение Gist недоступно, не публикуй placeholder и не
объявляй описание проверенным. Оставь исходник локально и сообщи о препятствии.

## 4. Создание и редактирование

Новый PR по умолчанию создаётся **Draft** и остаётся Draft до финального
пользовательского review, если пользователь не дал другую явную команду.

```bash
gh pr create --draft --base <base> --head <branch> --title <title> --body-file <путь>
gh pr edit <number> --title <title> --body-file <путь>
```

Интерфейс `gh` зависит от версии: доступные флаги и способы передать body
проверяй по `gh pr create --help` и `gh pr edit --help` установленной версии,
а не по памяти. Не полагайся на интерактивные запросы: body передаётся файлом.

В локальной процедуре `gh` body публикуется только из файла. Инлайновый `--body`,
`--body-file -` со stdin и heredoc непосредственно в вызове `gh pr create/edit`
запрещены: они разрывают связь между проверенным локальным файлом и опубликованным
описанием. В режиме GitHub MCP/API без локального `gh` допустима передача
проверенного полного body через структурированный параметр API с обязательным
повторным чтением, как описано в § 2.

## 5. Повторное чтение опубликованного PR

После создания или каждого изменения PR (`gh` либо GitHub MCP/API) — перечитай опубликованный PR и
проверь:

```text
repository
base
head
Draft/Ready state
title
body
```

Сравни опубликованный body с локальным файлом с учётом допустимой нормализации
переводов строк (например CRLF/LF, завершающий перевод строки). Прочие расхождения
означают, что PR не соответствует локальному источнику, и должны быть устранены,
а не проигнорированы.

Отдельно проверь, что опубликованный head — это именно ожидаемый HEAD текущей
задачи, а не устаревшее состояние.

## 6. Ready

Draft переводится в Ready только по явной команде пользователя либо когда это
следует из явно определённого контракта текущей задачи. Успешный push,
зелёный CI или сам факт созданного Draft PR не переводят PR в Ready и тем более
не разрешают merge.

```bash
gh pr ready <number>
```

## 7. Merge

```text
успешный push ≠ разрешение на merge
зелёный CI ≠ разрешение на merge
созданный Draft PR ≠ разрешение на merge
```

Merge выполняется **только** после отдельной текущей явной команды пользователя
на конкретный PR. Разрешение, выданное ранее и относящееся к другому состоянию
задачи, не переиспользуется.

Перед merge заново проверь:

- репозиторий, base/head и точный текущий HEAD PR
  (установленную версию `gh` см. в `gh pr view --help`);
- актуальность обязательных проверок и ревью относительно **текущего** HEAD:
  после любого изменения HEAD прежние подтверждения считаются устаревшими;
- что merge не обходит проверки: `--admin` и любые force-механизмы запрещены;
  auto-merge требует того же отдельного разрешения, а ожидающее auto-merge
  **не** считается выполненным merge.

Безопасный способ merge выбирай с учётом фактической политики репозитория. Не
хардкодь squash: сверься с текущими правилами репозитория и интерфейсом установленного
`gh` (`gh pr merge --help`). Историческая конвенция этого
репозитория — один squash-commit вида `<заголовок> (#<номер>)`, но это наблюдение
о фактических данных, а не вечный контракт: перед merge политика перепроверяется.

Если установленная версия `gh` умеет привязывать merge к ожидаемому HEAD
(например `--match-head-commit <sha>`), используй эту возможность, чтобы не слить
PR, head которого сдвинулся между проверкой и merge; доступность флага
подтверждается по `gh pr merge --help`.

После merge прочитай фактический конечный статус PR (`merged`) и merge SHA: сам
код возврата команды не подтверждает удалённый результат. Дальше переходи к очистке
(§ 9).

## 8. Продвижение base и конфликты

Если base продвинулась или возник конфликт:

1. Установи общий предок и фактическое изменение обеих сторон (`git merge-base`,
   diff каждой стороны) до любых правок.
2. Разрешай конфликт по смыслу: стратегии замены целого файла `ours`/`theirs` и общий выбор
   «своей» стороны как механический приём не применяются. Чужие изменения не
   удаляются.
3. Сгенерированный файл с отдельным исходным файлом-владельцем пересоздаётся из него,
   а не редактируется вручную.
4. Опубликованная ветка обновляется merge актуальной base, без force и без
   переписывания истории; rebase допустим только для ещё не опубликованной истории.
5. После разрешения проверь отсутствие неразрешённых путей и активной merge/rebase, а
   также происхождение новой базы и итоговый diff.
6. После изменения HEAD прежние подтверждения CI и ревью считай устаревшими
   относительно нового commit и проверь состояние заново: сначала обнови локальный
   файл body, затем опубликуй и перечитай его.
7. Не делай force-push опубликованной ветки только ради удобства.

## 9. Очистка после merge

После **подтверждённого** merge допустима обычная очистка локальных артефактов
этой работы: собственной ветки задачи и временных файлов (включая файл body из
игнорируемого каталога репозитория).

Ограничения:

- удаляй ветку только после доказанного сохранения результата: локальную —
  через `git branch -d`, удалённую — после подтверждения её принадлежности этой
  задаче и факта merge;
- не удаляй чужую работу и чужие артефакты;
- если squash-merge мешает `git branch -d`, оставь ветку и сообщи ограничение:
  автоматический переход к `-D` и принудительному удалению запрещён;
- очистка не является частью автоматического жизненного цикла: она выполняется
  после подтверждённого merge, а не вместо проверок.

## 10. Завершённое состояние задачи

```text
commit опубликован и удалённый SHA подтверждён
PR существует в единственном экземпляре для ветки текущей задачи
PR перечитан после последнего изменения и соответствует локальному body-файлу
Состояние Draft/Ready соответствует ожидаемому
merge не выполнен, пока нет отдельной текущей явной команды
```

До отдельного разрешения на merge конечный результат обычной задачи — проверенный
Draft PR. Результат передаётся пользователю на review; merge остаётся за
пользователем.

## Доверенная проверка CI

«Структура PR» проверяет кандидатный валидатор и опубликованную пару.
Независимая «Пара PR и Gist» (`pr-gist-trusted.yml`) выполняется на
`pull_request_target` из точного base SHA: checkout head, запуск кода PR,
секреты и write permissions запрещены. Body и Gist читаются только как данные.
Изменение валидатора в PR не изменяет доверенный gate до merge в base.

Проверь фактический ruleset/branch protection и required contexts. При наличии
полномочий добавь «Пара PR и Gist», сохранив все остальные rules и bypass actors;
перечитай результат. Без прав укажи точную оставшуюся настройку. Не называй gate
обязательным, пока это не подтверждено. Новый trusted workflow активируется лишь
после попадания в base: для PR, вводящего его, честно зафиксируй bootstrap-границу
и выполни локальный remote-preflight/read-back, не обходя required checks.

GitHub допускает `pull_request_target` как источник required check, см.
[диагностику обязательных проверок](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks).
Перед активацией проверь также применимые Actions event policies; не ослабляй
их и не считай новый workflow исполнившимся без фактического run.
Gist не создаёт PR-событие сам: после его изменения повтори gate и required
check, перед разрешённым merge ещё раз сверь актуальные файлы и HEAD.
