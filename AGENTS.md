# Инструкции для агентов Anki-decks

## 1. Назначение

Этот репозиторий — инструментарий и агентский workflow для локальных Anki-колод в JSON-формате CrowdAnki: анализ, проверка, точечное редактирование и создание карточек. Пользовательские колоды, ресурсы и приватный журнал операций остаются локальными данными и через Git не публикуются: репозиторий не является Git-хранилищем пользовательских колод.

Отвечай пользователю, пиши документацию и сообщения коммитов на русском языке. Точные имена JSON-ключей, путей, UUID, HTML/CSS, японских выражений и внешних инструментов сохраняй без перевода.

## 2. Источники истины

Для задачи над конкретной колодой используй источники в таком порядке:

1. целевой CrowdAnki JSON в текущей ветке;
2. связанные с ним `note_models`, `deck_configurations`, дерево `children` и сами `notes`;
3. относящиеся к задаче документы `.codex/context/`;
4. официальная документация CrowdAnki/Anki, только если требуется уточнить внешний формат или поведение.

Контекстные документы помогают навигации, но не заменяют проверку фактического JSON.

## 3. Маршрутизация

Перед работой с колодой:

1. прочитай `.codex/context/INDEX.md` — он владеет картой владельцев и тем, какие вопросы кому принадлежат;
2. определи область изменения;
3. открой только тех владельцев, которые владеют этой областью;
4. не загружай большой JSON целиком, если задача решается точечным поиском или скриптом.

Владельцы деталей (пересказ их контракта здесь второго источника истины не создаёт):

- контракты инструментов: `docs/ru/anki-repo/README.md`, `docs/ru/asset-store/README.md`, `docs/ru/japanese-lexicon/README.md`;
- обмен с Anki Desktop: `docs/ru/anki-repo/desktop.md`, `input-export.md`, `roundtrip.md`, `exchange.md`;
- стенды и измерения: `docs/ru/anki-e2e/README.md` (локальный opt-in E2E в Docker, браузерные наборы Forvo-Brave и ручной Real-Site стенд на настоящем forvo.com; в CI и `cargo test` не запускаются), `docs/ru/performance/README.md`, `docs/ru/performance/benchmarks.md`, `docs/ru/benchmark-contract/README.md`, `docs/ru/benchmark-runner/README.md`, `docs/ru/benchmark-history/README.md`;
- обслуживание: `docs/ru/repository-maintenance/README.md`;
- процедуры: `.agents/skills/<name>/` — `anki-card-create`, `anki-git-workflow`, `anki-code-review`, `anki-coderabbit-review`, `anki-live-testing`, `performance-benchmarking`.

Процедурой каждого рабочего процесса владеет сам его владелец. Не дублируй её здесь, не переноси в `.codex/context/` и не создавай второго владельца той же процедуры.

Для структурного анализа экспорта, проверки содержимого карточек и точечной правки значения поля существующей заметки используй набор инструментов `tools/anki-repo`, а не ручное чтение или правку многомегабайтного `deck.json`. Команды работы с локальными экспортами не вызывают LLM API, не ходят в сеть и меняют `deck.json` только по явному `--apply`; содержательное суждение о карточке делает внешний агент, а не набор инструментов.

Мутирующих команд в наборе инструментов четыре, и каждая работает по тем же правилам (режим без записи по умолчанию, запись только по явному `--apply`, канонический `deck.json`, отказ при невалидном результате):

- `edit` — значение существующего поля существующей заметки;
- `create` — новая заметка в **уже существующей** колоде **уже существующей** модели. Перед ним смотри фактическую схему полей через `models`: имя поля — свойство конкретного экспорта, а не контракт репозитория. По умолчанию значения новых полей не содержат ссылок на медиа; правила могут явно разрешить проверенные изображения кандзи и высотного ударения только для сочетания UUID модели и точного имени поля;
- `retire` — вывод заметки из обращения одним тегом. Физического удаления заметок в наборе инструментов нет: заметку, которую пора убрать из работы, помечают и удаляют вручную в Anki, когда это действительно нужно;
- `migrate-media` — перевод ссылок на старое имя файла потребителя на текущее каноническое имя домена.

`migrate-media` — **единственное** и узкое исключение из правила «существующие заметки не меняются»: команда правит только те ссылки, чью семантику доказала (поле принадлежит владельцу канонического имени, форма ссылки — та самая, которую он распознаёт), и отказывает целиком, если доказать не удалось. Обход этого пути — ручная правка `deck.json`, переименование файлов в `media/`, замена слова в запросе лишь бы конфликт не возник — не годится: он не оставляет ни доказательства семантики, ни согласованного `media_files`.

Изменения экспорта показывай до записи детерминированным diff (те же команды в режиме без записи), а после — статическим отчётом `visual-report` между состоянием до и после. Каталог отчёта — артефакт прогона: он обязан лежать вне `decks/**` (там лежат игнорируемые Git пользовательские данные), не попадать в коммит и не заменять собой проверку фактического JSON. Маршрут «создать и проверить» и владелец контракта каждой из этих команд — `docs/ru/anki-repo/README.md`.

Группа `anki-repo anki` управляет интеграцией Desktop через установленный AnkiConnect и оригинальный CrowdAnki (контракт — `docs/ru/anki-repo/desktop.md`). В WSL выбирается Windows Anki, в обычном Linux — Linux Anki; при неоднозначности нужен явный выбор установки. Эта группа использует сеть для локального API и официальных пакетов AnkiWeb. Единственный доверенный путь Anki → `decks/input/` принадлежит закрытому владельцу `desktop::input`, командам `anki sync-input` и `anki input-status`; обычным командам это доступа к закрытой области не даёт. Тот же владелец ведёт явный цикл `anki prepare-output` / `publish-output` / `exchange-status` с подтверждённым readback.

Отдельно от этих четырёх команд `migrate-layout` переносит раскладку в плоский `decks/output/` по `--apply`, доказывая содержимое каждого экспорта по SHA-256 и не меняя `deck.json` и идентичности, а группа `maintenance` управляет пользовательским таймером `systemd --user` и хранит выбор в приватном файле вне экспорта, поэтому правила `--apply` и канонического `deck.json` к ней не относятся. Контракты обеих — `docs/ru/anki-repo/README.md` и `docs/ru/repository-maintenance/README.md`.

## 4. Инварианты CrowdAnki

- Не меняй `crowdanki_uuid`, `guid`, `note_model_uuid` и `deck_config_uuid` без явной причины.
- Не меняй порядок полей заметки вслепую: сначала разреши `note_model_uuid` и сопоставь `fields` с `note_models[].flds[].ord`.
- Не считай `media_files` содержимым медиа: это список ссылок/имён файлов, а не бинарные данные.
- Не смешивай правку лингвистического содержимого с изменением модели карточки, HTML/CSS или настроек планировщика, если задача этого не требует.
- При массовой правке используй детерминированный скрипт или точечное преобразование; избегай ручного переписывания многомегабайтного JSON.
- Сохраняй существующее форматирование JSON, если нет отдельной задачи на нормализацию.
- Не удаляй неизвестные ключи только потому, что они не нужны текущей задаче.

## 5. Данные и контракт репозитория

Репозиторий — это инструментарий и агентский workflow для локальных колод, а не Git-хранилище пользовательских колод. Пользовательские данные живут в игнорируемых Git областях, и ни одна из них не публикуется через Git:

- `decks/input/` — закрытая область доверенного программного экспортера; последний подтверждённый снимок пары профиль/колода публикует только `desktop::input` через живой Anki export. Агент не читает, не редактирует и не наполняет эту область файловыми средствами. Синтетические тесты вне пользовательских данных и контейнерный E2E проверяют её только через доверенного владельца. `anki input-status` возвращает проверенные хеши и ревизии без содержимого карточек. Библиотечный `anki_repo::exchange` принимает подтверждения в памяти и не открывает `input` обычным командам;
- `decks/output/<имя_экспорта>/` — плоский список рабочих локальных колод, с которыми работают команды `anki-repo`. Иерархия Anki выражается именем каталога (`Words__N5`), дополнительных каталогов-организаторов нет, а внутренняя структура экспорта (`deck.json`, `media/` и штатные файлы) не меняется;
- `.asset-store/` — локальное доверенное хранилище ресурсов (kanji, pitch-accent). `manifest.json` и `.owner.json` остаются важнейшими файлами локального доверенного состояния; проверенный корпус у каждого пользователя свой.

`decks/.exchange/revisions.json` — приватное состояние программного обмена: идентичности профилей/колод, привязки output, актуальный вход, база рабочей копии и последнее подтверждение публикации. Оно игнорируется вместе со всем `decks/`. Владелец контракта — `docs/ru/anki-repo/exchange.md`. Слой не переносит экспорты и не выполняет импорт Anki; ограничения Rust API и advisory-блокировки не являются OS-level изоляцией от того же пользователя.

Каталог `decks/` игнорируется Git целиком: отслеживаемым внутри него не может быть ни один путь, а не только две названные подобласти. Прежняя раскладка с каталогами группировки, в том числе `decks/japanese/words/Words__N1…N5/`, — состояние прошлых ревизий, а не основание что-то публиковать и не контракт.

Отсутствие корпуса или колод в чистом clone — нормальное состояние, а не повод что-то публиковать. Пользовательские колоды, ресурсы и приватный журнал операций никогда не публикуются через Git; обычная публикация исходного кода через `anki-git-workflow` это не затрагивает.

Состав рабочих колод — это данные, а не контракт репозитория. Не закрепляй текущие колоды, уровни, имена моделей и имена полей как обязательный контракт в коде, тестах и CI: изменение, перемещение или временное отсутствие колоды не должно требовать их правки. Документация может описывать текущее состояние `decks/output/` как пример навигации, но обязана помечать его состоянием на сегодня, а не требованием к репозиторию; источник истины — фактический JSON.

После добавления или замены экспорта сверяй фактический `note_model_uuid` и `note_models[].flds`, а не предполагай их. Описание текущей модели — удобная карта навигации, а не лицензия на предположение.

Отсюда два инварианта, которые нельзя смешивать:

- набор тестов по умолчанию независим от фактических данных репозитория: тесты строят собственные синтетические экспорты и `decks/**` не читают;
- CI проверяет не пользовательские данные, а tracked код, документацию и самодостаточные fixtures вне пользовательских каталогов, плюс постоянную границу против случайной публикации пользовательских данных. Наличие или отсутствие колод и корпусов в чистом clone не является предметом проверки CI и не выдаётся за неё.

## 6. Изменения и Git

- Одна самостоятельная задача — одна рабочая ветка и один PR.
- Не работай напрямую в `main`.
- Жизненный цикл работы с Git/GitHub, формат и безопасная публикация PR body принадлежат `.agents/skills/anki-git-workflow/`. Локальный commit не завершает обычную публикуемую задачу: публикация доводится до проверенного удалённого состояния.
- Каждый содержательный ручной PR требует самодостаточный Markdown body (максимум **10 000 символов Unicode после нормализации LF**); Gist необязателен и не создаётся штатным workflow. Ключевые факты, результаты проверок и компактное решение о производительности публикуются в body; полная накопительная таблица CodeRabbit — в единственном комментарии автора PR в Conversation.
- Перед созданием и каждым изменением PR проверь полный body по `references/pr-body.md` и опубликованное состояние повторным чтением. Независимая проверка `.github/scripts/check_pr_body.py` не заменяет содержательную проверку фактов.
- Merge выполняется только по отдельной текущей явной команде пользователя.
- В PR описывай фактический набор изменений и выполненные проверки.
- Не добавляй в постоянный контекст номер текущего PR, SHA, временный план или разовые результаты ревью.
- Не оставляй в постоянном коде, тестах, CI и документации временных идентификаторов: номеров этапов, номеров PR, SHA, абсолютных локальных путей и имён авторов.

## 7. Проверки и CI

Единственная точка сборки — корневое рабочее пространство Cargo. Оттуда же запускаются проверки:

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
```

`.github/workflows/ci.yml` выполняет те же проверки независимо от локального окружения и дополнительно проверяет контракты скриптов, метаданные Agent Skills, workflow через `actionlint`, целостность локальных ссылок отслеживаемого Markdown и совпадение MSRV с `rust-toolchain.toml`. Необязательные задания исполняют зависящие от возможностей Cargo и браузерные тесты `asset-store` и политику зависимостей `deny.toml` (cargo-deny), а `reference-catalogs.yml` — воспроизводимость встроенных эталонов кандзи. `.github/workflows/pr-body.yml` проверяет опубликованный body и служебный комментарий CodeRabbit, а независимый `pr-body-trusted.yml` на `pull_request_target` проверяет те же данные валидатором из base SHA, не исполняя код PR; изменение `issue_comment` само по себе не обновляет required check на PR HEAD. CI не требует Gist, не называет ни одной колоды, уровня, модели или поля по имени и не принимает заметки агента, временный план и разовые результаты ревью.

CI проверяет отслеживаемый код, документацию и самодостаточные fixtures, а не пользовательские данные. Колоды, ресурсы и корпуса лежат в игнорируемых Git областях (`decks/` целиком, `.asset-store/`) и в чистом clone отсутствуют — это нормальное состояние, а не результат проверки. Вместо этого CI постоянно проверяет саму границу: ни один путь внутри этих областей не должен быть отслеживаемым, а правила игнорирования обязаны быть на месте и не ослаблены повторным включением (`.github/scripts/check_local_data_untracked.py`). Проверка идёт по фактическому индексу Git, потому что `.gitignore` не отменяет уже добавленный индекс и обходится `git add -f`.

Канонический владелец MSRV — `[workspace.package] rust-version` корневого `Cargo.toml`; участники наследуют её. `rust-toolchain.toml` отражает эту же версию для rustup, а CI проверяет их совпадение и фактический компилятор. Не вводи независимых копий версии в workflow, скриптах или документации.

Детали проверок, кодов возврата и локального воспроизведения набора — `.codex/context/03-VERIFICATION.md`.

## 8. Skills

`.agents/skills/` содержит skills репозитория — по одному каталогу `.agents/skills/<name>/SKILL.md` на skill, с собственными справочными файлами. Claude Code находит те же skills через символические ссылки `.claude/skills/<name>` на эти каталоги; второй копии инструкций нет. Назначение, условия применения и порядок работы каждого skill описаны в его `SKILL.md`: применяй подходящий и не дублируй его процедуру здесь.

- Живая/смок-проверка по `anki-live-testing` не запускается автоматически вместо независимого ревью, штатных Cargo-тестов или CodeRabbit. Если она нужна как отдельная фаза разработки, применяй skill, сохраняя прежних владельцев Git/PR и проверки CI.
- Маршрут определяется намерением с учётом отрицания и порядка действий. Само упоминание CodeRabbit не разрешает его запуск: «сделай код-ревью без CodeRabbit» и «проверь самостоятельно, не запускай CodeRabbit» остаются в `anki-code-review`.
- При запросе независимого ревью с последующим сравнением сначала заверши и зафиксируй собственный анализ, затем читай внешний результат по контракту `anki-code-review`. Сравнение с доступным результатом не разрешает новый запуск CodeRabbit; последующая фаза `anki-coderabbit-review` требует явного положительного поручения его запустить. Задача по изменению самого skill ревью не является просьбой запустить ревью.
- Новые skills и изменения существующих добавляй только по явной просьбе пользователя, не придумывая преждевременную автоматизацию.
