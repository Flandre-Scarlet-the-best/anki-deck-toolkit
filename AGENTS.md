# Инструкции для агентов Anki-decks

## 1. Назначение и язык

Этот репозиторий — инструментарий и агентские процедуры для локальных Anki-колод в JSON-формате CrowdAnki: анализ, проверка, точечное редактирование и создание карточек. Пользовательские колоды, ресурсы и приватный журнал операций остаются локальными данными и через Git не публикуются: репозиторий не является хранилищем пользовательских колод.

Отвечай пользователю, веди документацию `docs/ru/` и `README.md`, пиши сообщения коммитов и описания PR на русском; комментарии, человекочитаемые сообщения CLI и логи проекта — тоже. Исключение — диагностика разбора аргументов: её печатает сам парсер `clap` на английском, и она не локализуется. Русский остаётся каноническим языком проекта: при расхождении технических контрактов приоритет у русского оригинала. Локализации `README.en.md`, `README.zh-CN.md`, `docs/en/` и `docs/zh-CN/` редактируй на их собственном языке: синхронизировать переводы одновременно не требуется (владелец правила — `docs/ru/contributing/translations.md`).

Точные контракты не переводятся: имена команд, флагов, пакетов и переменных, JSON-ключи, UUID, пути, HTML/CSS, японские выражения, машинные коды причин, схемы вывода CLI/JSON и публичные строки внешнего протокола. Человекочитаемое сообщение не является API: контракт несут коды и структурированные поля (`docs/ru/anki-repo/README.md`).

## 2. Источники истины

Для задачи над конкретной колодой порядок источников такой: 1) целевой CrowdAnki JSON в текущей ветке; 2) связанные с ним `note_models`, `deck_configurations`, дерево `children` и сами `notes`; 3) относящиеся к задаче документы `.codex/context/`; 4) официальная документация CrowdAnki/Anki, если нужно уточнить внешний формат или поведение. Контекстные документы помогают навигации, но не заменяют проверку фактического JSON.

## 3. Маршрутизация

Перед работой с колодой прочитай `.codex/context/INDEX.md` — он владеет картой владельцев и тем, какие вопросы кому принадлежат, — определи область изменения, открой только владельцев этой области и не загружай большой JSON целиком, если задача решается точечным поиском или скриптом.

Владельцы деталей (пересказ их контракта здесь второго источника истины не создаёт):

- контракты инструментов и обмена: `docs/ru/anki-repo/README.md` (там же `desktop.md`, `input-export.md`, `roundtrip.md`, `exchange.md`), `docs/ru/asset-store/README.md`, `docs/ru/japanese-lexicon/README.md`;
- стенды и измерения: `docs/ru/anki-e2e/README.md` (локальный стенд в Docker — только по явному запросу, вне CI и `cargo test`), `docs/ru/performance/` (`README.md`, `benchmarks.md`), `docs/ru/benchmark-contract/README.md`, `docs/ru/benchmark-runner/README.md`, `docs/ru/benchmark-history/README.md`;
- обслуживание: `docs/ru/repository-maintenance/README.md`;
- процедуры: `.agents/skills/<имя>/SKILL.md` — `anki-card-create`, `anki-git-workflow`, `anki-code-review`, `anki-coderabbit-review`, `anki-live-testing`, `performance-benchmarking`.

Процедурой каждого рабочего процесса владеет сам его владелец. Не дублируй её здесь, не переноси в `.codex/context/` и не создавай второго владельца той же процедуры.

### 3.1. Работа с экспортом через `tools/anki-repo`

Для анализа экспорта, проверки содержимого карточек и точечной правки значения поля используй `tools/anki-repo`, а не ручное чтение или правку многомегабайтного `deck.json`. Команды не вызывают LLM API, не ходят в сеть и меняют `deck.json` только по явному `--apply`; содержательное суждение о карточке делает внешний агент, а не набор инструментов. Контракт команд, границы записи и маршрут «создать и проверить» — `docs/ru/anki-repo/README.md`.

Содержимое экспорта меняют ровно четыре команды; каждая работает по тем же правилам — режим без записи по умолчанию, запись только по явному `--apply`, канонический `deck.json`, отказ при невалидном результате:

- `edit` — значение существующего поля существующей заметки. Ему доступны только значения: структура экспорта, идентификаторы, `tags`, `media_files` и `media/` закрыты;
- `create` — новая заметка в **уже существующей** колоде **уже существующей** модели. Перед ним смотри фактическую схему полей через `models`: имя поля — свойство конкретного экспорта, а не контракт репозитория. Ссылки на медиа по умолчанию запрещены; правила могут явно разрешить только проверенные изображения кандзи и высотного ударения — по сочетанию UUID модели и точного имени поля;
- `retire` — вывод заметки из обращения одним тегом. Физического удаления заметок нет: заметку, которую пора убрать, помечают и удаляют вручную в Anki;
- `migrate-media` — перевод ссылок на старое имя файла потребителя на текущее каноническое имя домена.

Это команды, меняющие содержимое экспорта, а не все изменяющие операции CLI: `migrate-layout` переносит раскладку, не меняя содержимое экспорта (доказательство по SHA-256), а `maintenance` управляет пользовательским таймером `systemd --user` и с экспортом не работает. Контракты — `docs/ru/anki-repo/README.md`, `docs/ru/repository-maintenance/README.md`.

**Существующие заметки.** `edit` и `retire` разрешены в границах выше — это операции общей работы с экспортом. Медиассылку существующей заметки может изменить только `migrate-media` и только при доказанной семантике (поле принадлежит владельцу канонического имени, форма ссылки — распознаваемая им); иначе команда отказывает целиком. Обход — ручная правка `deck.json`, переименование в `media/`, замена слова в запросе — не годится: он не оставляет ни доказательства семантики, ни согласованного `media_files`.

Процесс `anki-card-create` создаёт **новые** заметки и не является режимом редактирования прежних: правило «существующие заметки не меняются» действует внутри него, и его единственное исключение — `migrate-media` при доказанном конфликте прежних имён.

Изменения экспорта показывай до записи детерминированным diff тех же команд без записи, а после — статическим отчётом `visual-report`; каталог отчёта лежит вне `decks/**`, не попадает в коммит и не заменяет проверку фактического JSON.

### 3.2. Интеграция с Anki Desktop

Группа `anki-repo anki` управляет интеграцией Desktop через AnkiConnect и оригинальный CrowdAnki (контракт — `docs/ru/anki-repo/desktop.md`): в WSL — Windows Anki, в обычном Linux — Linux Anki, при неоднозначности нужен явный выбор; сеть используется для локального API и официальных пакетов AnkiWeb. Единственный доверенный путь Anki → `decks/input/` принадлежит закрытому владельцу `desktop::input`, командам `anki sync-input` и `anki input-status`, и обычным командам доступа к закрытой области не даёт. Тот же владелец ведёт цикл `anki prepare-output` / `publish-output` / `exchange-status` с подтверждённым обратным чтением из Anki.

## 4. Инварианты CrowdAnki

- Не меняй `crowdanki_uuid`, `guid`, `note_model_uuid` и `deck_config_uuid` без явной причины.
- Не меняй порядок полей заметки вслепую: сначала разреши `note_model_uuid` и сопоставь `fields` с `note_models[].flds[].ord`.
- Не считай `media_files` содержимым медиа: это список ссылок/имён файлов, а не бинарные данные.
- Не смешивай правку лингвистического содержимого с изменением модели карточки, HTML/CSS или настроек планировщика, если задача этого не требует.
- При массовой правке используй детерминированный скрипт или точечное преобразование; избегай ручного переписывания многомегабайтного JSON.
- Сохраняй существующее форматирование JSON, если нет отдельной задачи на нормализацию.
- Не удаляй неизвестные ключи только потому, что они не нужны текущей задаче.

## 5. Данные и границы репозитория

Пользовательские данные живут в игнорируемых Git областях, и ни одна из них не публикуется через Git:

- `decks/input/` — закрытая область доверенного программного экспортера. Агент не читает, не редактирует и не наполняет её файловыми средствами: последний подтверждённый снимок пары профиль/колода публикует только `desktop::input` через живой export из Anki. `anki input-status` возвращает проверенные хеши и ревизии без содержимого карточек; стенд и синтетические тесты проверяют область только через доверенного владельца, а `anki_repo::exchange` принимает подтверждения в памяти и не открывает `input` обычным командам;
- `decks/output/<имя_экспорта>/` — плоский список рабочих локальных колод для команд `anki-repo`. Иерархия Anki выражается именем каталога, каталогов-организаторов нет, а внутренняя структура экспорта (`deck.json`, `media/`) не меняется;
- `.asset-store/` — локальное доверенное хранилище ресурсов (kanji, pitch-accent); `manifest.json` и `.owner.json` — важнейшие файлы локального доверенного состояния, а проверенный корпус у каждого пользователя свой.

`decks/.exchange/revisions.json` — приватное состояние программного обмена (владелец — `docs/ru/anki-repo/exchange.md`). Слой не переносит экспорты и не выполняет импорт в Anki; ограничения Rust API и advisory-блокировки не являются изоляцией уровня операционной системы от того же пользователя.

Каталог `decks/` игнорируется Git целиком: отслеживаемым внутри него не может быть ни один путь, а не только `decks/input/` и `decks/output/`. В свежем клоне отсутствие корпуса или колод — нормальное состояние, а не повод что-то публиковать; обычная публикация исходного кода через `anki-git-workflow` пользовательских данных не затрагивает.

Состав рабочих колод — данные, а не контракт: не закрепляй текущие колоды, уровни, имена моделей и полей в коде, тестах и CI, чтобы изменение, перемещение или временное отсутствие колоды не требовало их правки. Документация может описывать состояние `decks/output/` как пример на сегодня, а не как требование к репозиторию; источник истины — фактический JSON.

После добавления или замены экспорта сверяй фактический `note_model_uuid` и `note_models[].flds`, а не предполагай их. Набор тестов по умолчанию независим от фактических данных репозитория: тесты строят собственные синтетические экспорты и `decks/**` не читают.

## 6. Изменения и Git

- Одна самостоятельная задача — одна рабочая ветка и один PR; напрямую в `main` не работай.
- Жизненный цикл Git/GitHub, структура и безопасная публикация описания PR принадлежат `.agents/skills/anki-git-workflow/`. Локальный commit не завершает публикуемую задачу: публикация доводится до проверенного удалённого состояния.
- Содержательный ручной PR требует самодостаточное Markdown-описание (максимум **10 000 символов Unicode после нормализации LF**); Gist необязателен и штатной процедурой не создаётся. Ключевые факты, результаты проверок и компактное решение о производительности — в описании PR, накопительная таблица CodeRabbit — в единственном комментарии автора.
- Перед созданием и каждым изменением PR проверь полный текст описания по `.agents/skills/anki-git-workflow/references/pr-body.md` и опубликованное состояние повторным чтением: `.github/scripts/check_pr_body.py` проверяет структуру, но не факты.
- Merge выполняется только по отдельной текущей явной команде пользователя.
- В PR описывай фактический набор изменений и выполненные проверки. Не добавляй в постоянный контекст номер текущего PR, SHA, временный план или разовые результаты ревью и не оставляй в постоянном коде, тестах, CI и документации временных идентификаторов: номеров этапов и PR, SHA, абсолютных локальных путей и имён авторов.

## 7. Проверки и CI

Единственная точка сборки — корневое рабочее пространство Cargo; оттуда же запускаются проверки:

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
```

`.github/workflows/ci.yml` повторяет их независимо от локального окружения и дополнительно проверяет контракты скриптов, метаданные Agent Skills, workflow через `actionlint`, локальные ссылки отслеживаемого Markdown и совпадение MSRV с `rust-toolchain.toml`; необязательные задания — возможности `asset-store`, политику зависимостей `deny.toml` (cargo-deny), а `.github/workflows/reference-catalogs.yml` — эталоны кандзи. `.github/workflows/pr-body.yml` проверяет описание PR и служебный комментарий CodeRabbit, а `.github/workflows/pr-body-trusted.yml` на `pull_request_target` — те же данные валидатором из base SHA, не исполняя код PR; изменение `issue_comment` само по себе не обновляет обязательную проверку на HEAD PR.

CI проверяет отслеживаемый код, документацию и самодостаточные тестовые данные, а не пользовательские данные: ни один путь внутри `decks/` (целиком) и `.asset-store/` не должен быть отслеживаемым, а правила игнорирования обязаны быть на месте и не ослаблены повторным включением (`.github/scripts/check_local_data_untracked.py`). Проверка идёт по фактическому индексу Git, потому что `.gitignore` не отменяет уже добавленный индекс и обходится `git add -f`. Отсутствие колод и корпусов в свежем клоне — нормальное состояние, а не предмет проверки: CI не требует Gist, не называет ни одной колоды, уровня, модели или поля по имени и не принимает заметки агента, временный план и разовые результаты ревью.

Канонический владелец MSRV — `[workspace.package] rust-version` корневого `Cargo.toml`, участники наследуют её; `rust-toolchain.toml` отражает ту же версию для rustup, и CI проверяет их совпадение и фактический компилятор. Независимых копий версии в workflow, скриптах и документации быть не должно.

Детали проверок, кодов возврата и локального воспроизведения набора — `.codex/context/03-VERIFICATION.md`.

## 8. Skills

`.agents/skills/` содержит skills репозитория: один каталог `.agents/skills/<имя>/SKILL.md` на skill со своими справочными файлами. Claude Code находит их же через символические ссылки `.claude/skills/<имя>`; второй копии инструкций нет. Назначение, условия применения и порядок работы описаны в `SKILL.md`: применяй подходящий skill и не дублируй его процедуру здесь.

- Событие Forvo `human_interaction_required` требует штатного интерактивного инструмента ответа пользователя в текущем клиенте и событийного ожидания без цикла генерации модели. Процесс сохраняется до подтверждённого CLI исхода; сроки ожидания сообщаются явно. Подробный протокол — в `anki-live-testing`; без инструмента агент честно сообщает ограничение и использует обычный диалог.
- Живая/смок-проверка `anki-live-testing` не запускается автоматически вместо независимого ревью, штатных Cargo-тестов или CodeRabbit; как отдельная фаза она сохраняет прежних владельцев Git/PR и проверки CI.
- Маршрут определяется намерением с учётом отрицания и порядка действий: само упоминание CodeRabbit не разрешает его запуск — «сделай код-ревью без CodeRabbit» и «проверь самостоятельно, не запускай CodeRabbit» остаются в `anki-code-review`.
- При независимом ревью с последующим сравнением сначала заверши и зафиксируй собственный анализ, затем читай внешний результат по контракту `anki-code-review`. Сравнение не разрешает новый запуск CodeRabbit: фаза `anki-coderabbit-review` требует явного положительного поручения его запустить. Задача по изменению самого skill ревью не является просьбой запустить ревью.
- Новые skills и изменения существующих добавляй только по явной просьбе пользователя, не придумывая преждевременную автоматизацию.
